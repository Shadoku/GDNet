## Key question 1 — Godot 4 built-in high-level multiplayer: API shapes, extension points, documented and reported weaknesses

### Takeaway
Godot 4's built-in stack is a server-authoritative-by-default, node-path-addressed RPC system (`@rpc` on Node methods, `rpc_config()` for scripts/extensions) plus two property-replication nodes (`MultiplayerSpawner`, `MultiplayerSynchronizer`) that talk to the `MultiplayerAPI` only through `object_configuration_add/remove`. It is fully pluggable at two levels (`MultiplayerPeerExtension` for the transport, `MultiplayerAPIExtension` for the whole RPC/replication protocol), but it ships **no** client prediction, reconciliation, lag compensation, snapshot interpolation, or tick loop; those are left to user code and addons, and the recurring user complaints (through Godot 4.6.2 threads in 2026) are about authority propagation on spawn, RigidBody "authority fighting", synchronizer jitter, and visibility/spawner interactions.

### Cited Findings

**RPCs (`@rpc`, `rpc_config`)**
- `@rpc` defaults are equivalent to `@rpc("authority", "call_remote", "reliable", 0)`. `mode` is `"authority"` (only the node's multiplayer authority may call remotely; the server is the authority by default, changeable per node with `Node.set_multiplayer_authority`) or `"any_peer"`; `sync` is `"call_remote"` (skips the local peer) or `"call_local"`; `transfer_mode` is `"reliable"` (resend until acked, ordered, "at a significant performance cost"), `"unreliable"`, or `"unreliable_ordered"` (packets arriving after a later-sent packet are dropped); `transfer_channel` is an int, default 0, and must be the last argument. "Channel 0 is actually three channels, one per transfer mode." — [High-level multiplayer tutorial](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)
- `rpc()` on a method calls it on every peer; `rpc_id(peer_id)` targets one peer (`rpc_id(1)` = the server); inside the callee `multiplayer.get_remote_sender_id()` gives the sender. — [High-level multiplayer tutorial](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)
- Documented caveats: every RPC in a script must be declared on both client and server scripts, "even unused ones", because all RPCs are checksummed together; the signature covers the `@rpc` declaration, function, return type and NodePath; the node must be at the same path on both sides; argument types are not checked; RPCs do not serialise Objects or Callables; RPC methods must be on Node-derived classes (Resource methods error at runtime); for remote calls use `add_child(node, true)` (`force_readable_name`) so names match. — [High-level multiplayer tutorial](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)
- Non-GDScript shape: `void Node.rpc_config(method: StringName, config: Variant)` where `config` is `null` (disabled, the default) or a Dictionary with keys `rpc_mode` (RPCMode), `transfer_mode` (TransferMode), `call_local` (bool), `channel` (int); `Error rpc(method: StringName, ...)` vararg and `Error rpc_id(peer_id: int, method: StringName, ...)` vararg; `set_multiplayer_authority(id: int, recursive: bool = true)`, `int get_multiplayer_authority()`, `bool is_multiplayer_authority()`. Docs warn: "This does **not** automatically replicate the new authority to other peers" and "the parent's authority does **not** propagate to newly added children." — [Node class reference](https://docs.godotengine.org/en/stable/classes/class_node.html)
- `MultiplayerAPI.RPCMode`: `RPC_MODE_DISABLED = 0` (default), `RPC_MODE_ANY_PEER = 1`, `RPC_MODE_AUTHORITY = 2`. — [MultiplayerAPI class reference](https://docs.godotengine.org/en/stable/classes/class_multiplayerapi.html)

**MultiplayerAPI / SceneMultiplayer**
- `MultiplayerAPI` (RefCounted) is "the base class for high-level multiplayer implementations"; inherited by `MultiplayerAPIExtension` and `SceneMultiplayer`. Methods: static `create_default_interface() -> MultiplayerAPI`, static `get_default_interface() -> StringName` (normally `"SceneMultiplayer"`), static `set_default_interface(interface_name: StringName)` ("Used by modules and extensions"), `get_peers() -> PackedInt32Array`, `get_remote_sender_id() -> int` (0 outside an RPC), `get_unique_id() -> int`, `has_multiplayer_peer() -> bool`, `is_server() -> bool`, `object_configuration_add(object: Object, configuration: Variant) -> Error`, `object_configuration_remove(object: Object, configuration: Variant) -> Error`, `poll() -> Error` (only needed if `SceneTree.multiplayer_poll` is false), `rpc(peer: int, object: Object, method: StringName, arguments: Array = []) -> Error`. Property `multiplayer_peer: MultiplayerPeer`. Signals `connected_to_server()`, `connection_failed()`, `peer_connected(id)`, `peer_disconnected(id)`, `server_disconnected()`. A branch of the tree can use a different instance through `SceneTree.set_multiplayer()`, "which allows a client and a server to run in the same scene." — [MultiplayerAPI class reference](https://docs.godotengine.org/en/stable/classes/class_multiplayerapi.html)
- `SceneMultiplayer` properties and defaults: `allow_object_decoding = false` (deserialised objects can run code), `auth_callback = Callable()`, `auth_timeout = 3.0`, `max_delta_packet_size = 65535`, `max_sync_packet_size = 1350` ("Larger values make full updates more likely in one frame but raise the risk of packet loss"), `refuse_new_connections = false`, `root_path = NodePath("")`, `server_relay = true` (server relays messages and peer lists between clients; "support depends on the MultiplayerPeer configuration"). Methods: `clear()`, `complete_auth(id) -> Error`, `disconnect_peer(id)`, `get_authenticating_peers() -> PackedInt32Array`, `send_auth(id, data: PackedByteArray) -> Error`, `send_bytes(bytes: PackedByteArray, id: int = 0, mode: TransferMode = 2, channel: int = 0) -> Error`. Signals: `peer_authenticating(id)`, `peer_authentication_failed(id)`, `peer_packet(id, packet)`. — [SceneMultiplayer class reference](https://docs.godotengine.org/en/stable/classes/class_scenemultiplayer.html)

**MultiplayerSpawner**
- Properties: `spawn_function: Callable` (called on all peers for a custom `spawn()`; receives `data`, must return a Node *not* in the tree, `add_child` happens automatically), `spawn_limit: int = 0` (0 = no limit; counts spawnable scenes and custom spawns), `spawn_path: NodePath = NodePath("")`. Methods: `add_spawnable_scene(path: String)`, `clear_spawnable_scenes()` (does not despawn remote instances), `get_spawnable_scene(index) -> String`, `get_spawnable_scene_count() -> int`, `spawn(data: Variant = null) -> Node`. Signals `spawned(node)`, `despawned(node)` — "Only emitted on remote peers." Internally it uses `MultiplayerAPI.object_configuration_add()` passing the spawned node as `object` and itself as `configuration`. — [MultiplayerSpawner class reference](https://docs.godotengine.org/en/stable/classes/class_multiplayerspawner.html)

**MultiplayerSynchronizer / SceneReplicationConfig**
- Properties: `delta_interval: float = 0.0` (applies to `REPLICATION_MODE_ON_CHANGE`; 0 = every network process frame), `public_visibility: bool = true`, `replication_config: SceneReplicationConfig`, `replication_interval: float = 0.0` (applies to `REPLICATION_MODE_ALWAYS`), `root_path: NodePath = NodePath("..")`, `visibility_update_mode: VisibilityUpdateMode = 0` (`VISIBILITY_PROCESS_IDLE = 0`, `VISIBILITY_PROCESS_PHYSICS = 1`, `VISIBILITY_PROCESS_NONE = 2` = only on manual `update_visibility()`). Methods: `add_visibility_filter(filter: Callable)`, `remove_visibility_filter(filter)`, `get_visibility_for(peer: int) -> bool`, `set_visibility_for(peer: int, visible: bool)`, `update_visibility(for_peer: int = 0)`. Signals: `delta_synchronized()`, `synchronized()`, `visibility_changed(for_peer)`. "Synchronization is not supported for Object type properties, like Resource." If the node at `root_path` was spawned by a MultiplayerSpawner, it is spawned/despawned per the synchronizer's visibility. — [MultiplayerSynchronizer class reference](https://docs.godotengine.org/en/stable/classes/class_multiplayersynchronizer.html)
- `SceneReplicationConfig`: `add_property(path: NodePath, index: int = -1)`, `remove_property(path)`, `has_property(path) -> bool`, `get_properties() -> Array[NodePath]`, `property_get_index(path) -> int`, `property_get_spawn(path) -> bool` / `property_set_spawn(path, enabled)`, `property_get_replication_mode(path) -> ReplicationMode` / `property_set_replication_mode(path, mode)`; `property_get_sync/set_sync` and `property_get_watch/set_watch` are **deprecated** in favour of the replication mode. Enum: `REPLICATION_MODE_NEVER = 0`, `REPLICATION_MODE_ALWAYS = 1` ("sent on every process frame using unreliable transfer"), `REPLICATION_MODE_ON_CHANGE = 2` ("sent on process using reliable transfer, but only when its value changes"). — [SceneReplicationConfig class reference](https://docs.godotengine.org/en/stable/classes/class_scenereplicationconfig.html)
- Godot 4.2 (older): GH-79479 made the synchronizer sync "sub-resource properties, transform components, and indexed data without syncing entire objects"; GH-81136 streamlined replication options and the editor UI; the same release fixed an ENet DoS flaw (backported to 4.0.4/4.1.2). — [Godot 4.2 release article](https://godotengine.org/article/godot-4-2-arrives-in-style/)

**Peers**
- `ENetMultiplayerPeer`: `peer.create_server(PORT, MAX_CLIENTS)`, `peer.create_client(IP_ADDRESS, PORT)`; assign to `multiplayer.multiplayer_peer`; use `OfflineMultiplayerPeer.new()` to terminate. The high-level API is UDP-only (port forwarding needed) and uses a modified ENet with IPv6 support. — [High-level multiplayer tutorial](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)
- `WebRTCMultiplayerPeer`: `create_server(channels_config: Array = []) -> Error` (ID 1), `create_client(peer_id: int, channels_config: Array = []) -> Error` (peer_id 2..2147483647, then `add_peer()` once with peer_id 1), `create_mesh(peer_id, channels_config)` (full mesh), `add_peer(peer: WebRTCPeerConnection, peer_id: int, unreliable_lifetime: int = 1) -> Error` (creates three channels: reliable, unreliable, ordered; extra channels from `channels_config` as TransferMode values, "WebRTC supports only one transfer mode per channel"; peers must be added in `STATE_NEW`), `remove_peer`, `has_peer`, `get_peer -> Dictionary`, `get_peers -> Dictionary`. Server/client modes enable `is_server_relay_supported()`. The class "will not create offers nor set descriptions, it will only poll them" (signalling is external). — [WebRTCMultiplayerPeer class reference](https://docs.godotengine.org/en/stable/classes/class_webrtcmultiplayerpeer.html)

**Extension points**
- `MultiplayerPeerExtension` virtuals (23): required `_close()`, `_disconnect_peer(peer: int, force: bool)`, `_get_available_packet_count() -> int`, `_get_connection_status() -> ConnectionStatus`, `_get_max_packet_size() -> int`, `_get_packet_channel() -> int`, `_get_packet_mode() -> TransferMode`, `_get_packet_peer() -> int`, `_get_transfer_channel() -> int`, `_get_transfer_mode() -> TransferMode`, `_get_unique_id() -> int` (1..2147483647), `_is_server() -> bool`, `_poll()`, `_set_target_peer(peer)`, `_set_transfer_channel(channel)`, `_set_transfer_mode(mode)`; optional `_get_packet(r_buffer: const uint8_t**, r_buffer_size: int32_t*) -> Error`, `_put_packet(buffer: const uint8_t*, buffer_size: int) -> Error`, `_get_packet_script() -> PackedByteArray` / `_put_packet_script(buffer: PackedByteArray) -> Error` ("Use this when extending this class via GDScript"; called only when the pointer versions are not implemented), `_is_refusing_new_connections()`, `_set_refuse_new_connections(enable)`, `_is_server_relay_supported()`. The intro says all methods "must be implemented" while the table marks seven optional — the page does not resolve this. — [MultiplayerPeerExtension class reference](https://docs.godotengine.org/en/stable/classes/class_multiplayerpeerextension.html)
- `MultiplayerAPIExtension` virtuals: `_poll() -> Error`, `_set_multiplayer_peer(multiplayer_peer: MultiplayerPeer)`, `_get_multiplayer_peer() -> MultiplayerPeer`, `_get_unique_id() -> int`, `_get_peer_ids() -> PackedInt32Array`, `_rpc(peer: int, object: Object, method: StringName, args: Array) -> Error`, `_get_remote_sender_id() -> int`, `_object_configuration_add(object: Object, configuration: Variant) -> Error`, `_object_configuration_remove(object, configuration) -> Error`. The doc example `LogMultiplayer` wraps a `SceneMultiplayer`, forwards its signals, logs each `_rpc`, and in `_object_configuration_add/remove` checks whether `configuration` is a `MultiplayerSynchronizer` or `MultiplayerSpawner` (or a root-path NodePath) before forwarding; it is installed with `get_tree().set_multiplayer(LogMultiplayer.new())` in an autoload's `_enter_tree()`, and "Native extensions can instead call `MultiplayerAPI.set_default_interface()` during initialization." — [MultiplayerAPIExtension class reference](https://docs.godotengine.org/en/stable/classes/class_multiplayerapiextension.html)
- `MultiplayerAPI.object_configuration_add()` is also used by SceneTree "internally to set the root path." — [MultiplayerAPI class reference](https://docs.godotengine.org/en/stable/classes/class_multiplayerapi.html)

**Process hooks and property interception (relevant to an extension that wants to observe arbitrary nodes)**
- Node notification constants: `NOTIFICATION_PHYSICS_PROCESS = 16`, `NOTIFICATION_PROCESS = 17`, `NOTIFICATION_INTERNAL_PROCESS = 25`, `NOTIFICATION_INTERNAL_PHYSICS_PROCESS = 26`; `process_priority` and `process_physics_priority` default 0 and "Nodes whose priority value is lower call their process callbacks first, regardless of tree order." — [Node class reference](https://docs.godotengine.org/en/stable/classes/class_node.html)
- `Object._set(property, value) -> bool` / `_get(property)` customise `set()`/`get()` only for the object's own script/extension class, and "This method is not called when setting built-in properties of an object"; there is no documented hook for intercepting sets on other objects. Related: `set(property, value)`, `get(property)`, `set_indexed(property_path, value)`, `get_indexed(property_path)`, `set_deferred`, `notify_property_list_changed()` and the `property_list_changed` signal, `_get_property_list() -> Array[Dictionary]`, `_validate_property(property: Dictionary)`, `_property_can_revert`, `_property_get_revert`. — [Object class reference](https://docs.godotengine.org/en/stable/classes/class_object.html)

**Weaknesses: documented and community-reported**
- Prediction is not built in: a Godot 4.4.1 forum thread answer (gertkeno) says "Prediction must still be implemented manually, though Synchronizer signals help"; synchronizers are C++-backed so per-frame RPCs are "much slower"; pennyloafers warns "RPCs are very easy to use/abuse", that RPCs and Spawners should not be mixed (RPCs don't share replication data), and flags the large-scene problem of synced data arriving for nodes a peer has not instantiated. No bandwidth numbers appear in the thread. — [Forum: MultiplayerSynchronizer vs RPC's](https://forum.godotengine.org/t/multiplayersynchronizer-vs-rpcs/115962)
- A Godot 4.6.2 thread (Aug 2026): a RigidBody2D synced with MultiplayerSynchronizer "is swapping between two values" on the client; diagnosis (Diego_Rodrigues) that the client's physics "fights with the network state arriving from the server"; the working fix (KyotoCrank, 17 Aug 2026) was `freeze = true` on non-authority instances and syncing only position/rotation; netfox recommended for competitive cases. — [Forum: Synchronizer glitches between two locations](https://forum.godotengine.org/t/muliplayer-syncronizer-on-client-glitches-between-two-locations/142803)
- A Godot 4.6 thread (Apr 2026): a synchronizer with `public_visibility` off still had the spawner spawn the player on every client; the poster found in the engine source that "a spawned node whose authority differs from its spawner's ignores synchronizer visibility"; advice was not to nest spawners with visibility, keep spawner and node authority consistent, or go fully server-authoritative with input RPCs (the poster's choice). — [Forum: Synchronizer visibility does not affect Spawner](https://forum.godotengine.org/t/multiplayersynchonizer-visibility-does-not-affect-spawner/137629)
- Other 4.3–4.6 forum threads: spawned player's authority stays 1 on clients (workaround: custom `spawn_function`, or name the node after the peer id); synchronizers don't carry `multiplayer_authority` itself so people sync a separate id field; in 4.5.1 spawned items did not sync until a `spawn_function` passing simple data was used. — [Forum: spawner auth id](https://forum.godotengine.org/t/multiplayer-spawner-not-spawning-with-correct-auth-id/103128); [Forum: late-joiner authority](https://forum.godotengine.org/t/how-to-set-correct-authority-on-object-spawned-in-scene-for-a-late-joining-player/100359); [Forum: 4.5.1 spawner sync](https://forum.godotengine.org/t/multiplayerspawner-peer-sync-issues-in-4-5-1/131944)
- (older, 2024) r/godot "Multiplayer makes me wanna quit Godot": authority management felt like "a pile of workarounds"; a senior community member said they rarely use the synchronizer or spawner beyond top-level objects. — [r/godot thread (mirror)](https://lr.eu.psf.lt/r/godot/comments/1fcn5uv/multiplayer_makes_me_wanna_quit_godot)
- Interpolation with the synchronizer alone is choppy when the server owns the character; the suggested workaround is a separate visual node that follows an interpolated copy of the synced position. — [Forum: network interpolation with MultiplayerSynchronizer](https://forum.godotengine.org/t/is-it-possible-to-achieve-network-interpolation-with-multiplayer-synchronizer/48514)
- Godot's own physics-interpolation docs say networked data "may not align with local ticks, so a custom interpolation approach may fit better." — [Physics interpolation introduction](https://docs.godotengine.org/en/stable/tutorials/physics/interpolation/physics_interpolation_introduction.html)

**Changes across 4.x**
- 4.1 (older): GDExtension "still in beta"; 4.0 extensions had to be recompiled; a backward-compat system introduced. The release article says nothing about networking. — [Godot 4.1 article](https://godotengine.org/article/godot-4-1-is-here/)
- 4.2 (older): in-editor GDExtension hot reloading (GH-80284), GDExtension on Web exports (GH-82633), custom Callables (GH-79005), indexed properties (GH-79763), `validate_property()` (GH-81261/GH-81515), synchronizer sub-resource/indexed sync (GH-79479). — [Godot 4.2 article](https://godotengine.org/article/godot-4-2-arrives-in-style/)
- 4.3: 2D physics interpolation; GDExtension runtime-only class registration, GDExtension classes can register their own virtual methods for scripts to override, GDExtension docs in the class reference. No networking items. — [Godot 4.3 release page](https://godotengine.org/releases/4.3/)
- 4.5: GDExtension main-loop callbacks (startup/shutdown/frame; PR 106030); 3D physics interpolation moved into SceneTree (PR 104269). No networking items. — [Godot 4.5 release page](https://godotengine.org/releases/4.5/)
- 4.6: Jolt is the default 3D physics engine for new projects (PR #105737; existing projects unaffected); unique Node IDs (PR #106837); GDExtension "required" parameters/returns (PR #86079); GDExtension interface defined in JSON instead of a C header (PR #107845); LibGodot (PR #110863). No high-level networking changes; pre-release coverage mentions only IP/IPv6 parsing fixes (GH-114827). — [Godot 4.6 release page](https://godotengine.org/releases/4.6/); [LinuxCompatible 4.6 RC1](https://www.linuxcompatible.org/story/godot-46-rc-1-released)
- Roadmap: the Godot Foundation's 2026 vision statement guides funding/contractors and stresses "a smaller, solid engine", but does not name multiplayer; it "is not intended to be used as a tool for evaluating specific changes." — [Godot vision statement 2026](https://godotengine.org/article/godot-vision-statement-2026/)

### Inferences
- For an extension that must interoperate, the two stable seams are (a) `rpc_config()` + `rpc()`/`rpc_id()` on Nodes and (b) `MultiplayerAPIExtension` wrapping a `SceneMultiplayer`, since the stock spawner/synchronizer announce themselves only through `object_configuration_add/remove` with the node as `configuration`. Replacing the default API (`set_default_interface`) is the only way to see every synchronizer/spawner in the tree without editing scenes.
- There is no engine hook to observe property writes on arbitrary nodes; the stock synchronizer itself polls values each network frame (hence `REPLICATION_MODE_ON_CHANGE` is "detected on process"). A Rust extension would have to poll or require users to route writes through its own node/accessor.
- The 4.6 unique Node IDs could become a more robust entity identifier than NodePath for custom replication, but no networking use of them is documented yet.

### Gaps
- No godot-proposals issue on built-in prediction/interpolation was reachable (GitHub search was blocked from this session and web search returned none); whether such a proposal exists in 2025–2026 is unverified.
- Which 4.x minor introduced `delta_interval`/`REPLICATION_MODE_ON_CHANGE` could not be pinned (4.2's GH-81136 "streamlined" the options, which is the closest evidence).
- No quantitative synchronizer bandwidth measurements were found in primary sources; only the 1350-byte `max_sync_packet_size` default.
- Godot 4.5's and 4.6's official release dates were not shown on the pages fetched (4.5.2 builds dated 19 Mar 2026; 4.6 described as "Almost 3 years after the 4.0 release", with third-party coverage dated Jan–Feb 2026).

## Key question 2 — Community addons and services

### Takeaway
netfox (GDScript, MIT, ~1.1k stars) is the de-facto rollback/prediction layer for Godot 4 and the most actively documented; SnopekGames' GGPO-style addon has only a 1.0.0-alpha for Godot 4.2 (2024) and leans on fixed-point physics; Andrea Catania's NetworkSynchronizer is a C++ engine module last targeting Godot 4.0; Steam transport is available as `SteamMultiplayerPeer` GDExtensions (the GodotSteam one moved to Codeberg after its GitHub repo was archived in Nov 2025); Nakama's GDScript client bridges to the built-in MultiplayerAPI; W4 Cloud (AGPLv3 backend, 2024) is W4 Games' hosted/matchmaking stack.

### Cited Findings

**netfox (foxssake)**
- "A set of addons for responsive online games with the Godot engine"; MIT; addons `netfox` (core: timing, rollback), `netfox.noray` (connect via noray), `netfox.extras` (input/weapon base classes), `netfox.internals` (auto-installed dependency); "Godot 4.x is supported", examples written against 4.1; GitHub page showed 1.1k stars, 92 forks on 2026-11-08; author @elementbound; a free noray prototyping instance at `tomfol.io:8890` with no uptime guarantees. — [foxssake/netfox](https://github.com/foxssake/netfox)
- Nodes: `TickInterpolator`, `RollbackSynchronizer`, `PredictiveSynchronizer`, `StateSynchronizer`, `RewindableAction`; singletons/guides: `NetworkTime`, `NetworkTimeSynchronizer`, `NetworkEvents`, `NetworkRollback`, `NetworkPerformance`, `NetworkCommandServer`, Network Schemas, Interpolators; extras: `NetworkWeapon` (2D/3D/Hitscan3D), `RewindableStateMachine`, `RewindableState`, `RewindableRandomNumberGenerator`, `BaseNetInput`. Feature list includes "Lag compensation with Client-side Prediction and Server-side Reconciliation". — [netfox docs home](https://foxssake.github.io/netfox/latest/)
- `NetworkTime`: a separate tick loop independent of render/physics frames; project settings Tickrate, `max_ticks_per_frame`, Sync to Physics (one tick per physics update), Tickrate Mismatch Action (Warn/Disconnect/Adjust/Signal); signals in order `before_tick_loop`, `before_tick`, `on_tick(delta, tick)`, `after_tick`, `after_tick_loop`; `NetworkTime.start()` is a coroutine (clients sync time first), `stop()`; `after_client_sync(peer_id)`, `after_sync`; `NetworkTime.time`/`tick` are the recommended time source, `local_*`/`remote_*` deprecated since v1.9.0; "Starting the tick loop before starting multiplayer is not supported"; pausing can desync peers. — [netfox NetworkTime guide](https://foxssake.github.io/netfox/latest/netfox/guides/network-time/)
- `NetworkRollback` loop per tick: `before_loop` (nodes call `notify_resimulation_start`), `on_prepare_tick(tick)` (rewind; `notify_simulated`), `after_prepare_tick(tick)`, `on_process_tick(tick)`, `on_record_tick(tick)`, `after_loop`; a node is rollback-aware if it implements `_rollback_tick`; `is_rollback_aware`, `process_rollback`, `is_simulated`, `get_latest_input_tick(root)`, `has_input_for_tick(root, tick)`, `get_input_submissions()`; settings: Enabled, History limit, Input redundancy (success = `1 - (1 - p)^redundancy`), Display offset, Input delay (ticks), Enable diff states. — [netfox NetworkRollback guide](https://foxssake.github.io/netfox/latest/netfox/guides/network-rollback/)
- `RollbackSynchronizer`: child of its target with `root`, `state_properties` (recorded each tick, restored on rollback; nodes holding them must be server-owned), `input_properties` (gathered per player, nodes owned by that player), `enable_input_broadcast` (default true for legacy; recommended off), `full_state_interval`, `diff_ack_interval`; callback `_rollback_tick(delta, tick, is_fresh)` (`is_fresh` true the first time a tick is processed, for one-shot effects); `process_settings()` after runtime config changes; `process_authority()` on all peers when authority changes; diff states send only changed properties, full states acked reliably, diffs acked unreliably; "Don't put state and input properties on the same node". — [netfox RollbackSynchronizer](https://foxssake.github.io/netfox/latest/netfox/nodes/rollback-synchronizer/)
- `StateSynchronizer`: "Similar to Godot's MultiplayerSynchronizer, but is tied to the network tick loop"; broadcasts configured properties every tick with no visibility management and no delta updates; "explicitly designed to work with" `TickInterpolator` (MultiplayerSynchronizer runs on its own timer so it does not work with TickInterpolator); use MultiplayerSynchronizer for non-interpolated values like HP when its delta/visibility features are wanted. — [netfox StateSynchronizer](https://foxssake.github.io/netfox/latest/netfox/nodes/state-synchronizer/)
- Rollback caveats: multiply velocity by `NetworkTime.physics_factor` around `move_and_slide()`; `is_on_floor()` is stale during rollback; Godot "doesn't support manually stepping or updating physics" (links Godot PR 76462); "Rollback and physics-based games ( RigidBodies ) don't work at the moment"; collision workarounds via `force_shapecast_update()` / `move_and_collide()`; state machines need rollback awareness (`RewindableStateMachine` in extras). — [netfox rollback caveats](https://foxssake.github.io/netfox/latest/netfox/tutorials/rollback-caveats/)

**Godot Rollback Netcode (SnopekGames / dsnopek)**

## Key question 3 — godot-rust (gdext): maturity, registration API, threading, extension traits, editor plugins, gotchas

### Takeaway
gdext is at `godot` 0.5.5 (crates.io, 2026-08-09; 0.5.0 on 2026-03-27 with roughly monthly patch releases), MPL-2.0, ~5.4k GitHub stars, "in a usable state" with hot reload supported since Godot 4.2 and CI-tested; classes/functions/properties/signals/RPCs register via `#[derive(GodotClass)]`, `#[godot_api]`, `#[func]`, `#[var]`/`#[export]`, `#[signal]`, `#[rpc]`; `IMultiplayerPeerExtension` and `IMultiplayerApiExtension` traits exist with full Rust signatures; threading remains `experimental-threads` with "a high risk of unsoundness"; web export works but is experimental and needs nightly Rust plus a dual threads/nothreads build.

### Cited Findings

**Version and maturity**
- crates.io `godot`: `max_version` 0.5.5; releases 0.5.5 (2026-08-09), 0.5.4 (2026-06-23), 0.5.3 (2026-05-19), 0.5.2 (2026-04-28), 0.5.1 (2026-04-12), 0.5.0 (2026-03-27); 632,761 downloads; repository godot-rust/gdext. — [crates.io API: godot](https://crates.io/api/v1/crates/godot)
- GitHub page (2026-11-08): 5.4k stars, 324 forks, 3,528 commits; MPL-2.0 ("Changes to godot-rust itself must be shared, but game code can stay closed-source"); "in a usable state" for games, editor plugins and tools; occasional minor breaking changes with migration guides; "Even hot-reload is tested!"; Wasm, Android and iOS "experimental". — [godot-rust/gdext](https://github.com/godot-rust/gdext)
- Cargo features: `api-4-{minor}` (one at a time; default = current Godot minor at patch 0), `api-custom`/`api-custom-json`, `double-precision`, `upcoming-editor-placeholders`, `experimental-godot-api`, `experimental-threads` ("adds synchronization to access the user instance in Gd<T>"; "there is a high risk of unsoundness at the moment"), `experimental-wasm`, `experimental-wasm-nothreads`, `lazy-function-tables` (not thread-safe, cannot combine with experimental-threads), `codegen-rustfmt`, `register-docs` (Godot 4.3+), `safeguards-dev-balanced`/`safeguards-release-disengaged`, `serde`. — [docs.rs godot 0.5.5](https://docs.rs/godot/latest/godot/)

- Book migration guides exist for 0.2 through 0.5. — [godot-rust book SUMMARY](https://raw.githubusercontent.com/godot-rust/book/master/src/SUMMARY.md)

**Entry point and .gdextension**
- `[lib] crate-type = ["cdylib"]`; `#[gdextension] unsafe impl ExtensionLibrary for MyExtension {}`; `.gdextension` has `entry_symbol = "gdext_rust_init"` ("no other symbol works"), `compatibility_minimum = 4.1`, `reloadable = true` (reload when the editor regains focus; "If Godot crashes, try turning this off"), and a `[libraries]` map such as `linux.debug.x86_64 = "res://../rust/target/debug/lib{YourCrate}.so"`. Hot reload "is supported since Godot 4.2". — [godot-rust book: Hello World](https://godot-rust.github.io/book/intro/hello-world.html)

**Classes, constructors, properties, functions, signals, RPCs**
- `#[derive(GodotClass)] #[class(base=Node3D)] struct Monster { name: String, hitpoints: i32, base: Base<Node3D> }`; default base is `RefCounted`; registration is automatic; before Godot 4.2 a new class needed an editor restart. — [godot-rust book: Classes](https://godot-rust.github.io/book/register/classes.html)
- Constructors: `fn init(base: Base<Node3D>) -> Self` in `impl INode3D`, or `#[class(init, base=Node3D)]` (fields `Default::default()`), `#[init(val = 100)]`, `#[class(no_init, base=Node3D)]`; omitting both is a compile error. — [godot-rust book: Constructors](https://godot-rust.github.io/book/register/constructors.html)
- README example also shows `#[init(node = "Ui/HealthBar")] health_bar: OnReady<Gd<ProgressBar>>` and typed signals `signals().value_changed().connect(...)`. — [godot-rust/gdext](https://github.com/godot-rust/gdext)
- `#[var]` exposes a field (no `pub` needed); `#[export]` exposes it to the editor and "always implies #[var]"; enums derive `GodotConvert, Var, Export` with `#[godot(via = GString)]` or an int; C-style only; custom `Var`/`Export` impls run a conversion every engine access, which for `#[export]` fields adds "significant traffic" from editor/scene serialisation — prefer `Array`, `Dictionary`, `Gd`; `Packed*Array` is copy-on-write so GDScript mutations of a registered packed-array property are not seen on the Rust side. — [godot-rust book: Properties](https://godot-rust.github.io/book/register/properties.html)
- `#[godot_api]` (no arguments) is required on `I<Base>` impls and on inherent impls with `#[func]`; `#[func] fn damage(&mut self, amount: i32)`; associated fns without receiver become static. — [godot-rust book: Functions](https://godot-rust.github.io/book/register/functions.html)
- `#[func(rename = ...)]`, `#[func(virtual)]` (scripts override as `_name`; needs `Base<T>`), `#[func(gd_self)]` (explicit `Gd<T>` first arg instead of implicit `bind()`/`bind_mut()`), `#[opt(default = "...")]`; `#[signal] fn some_signal(my_parameter: Gd<Node>);` generates `WithSignals` and `self.signals().some_signal()` returning a `TypedSignal` with emit/connect; `#[signal(internal)]` hides it. `#[rpc]` "Equivalent to GDScript's @rpc", implies `#[func]`, only on `Node`-derived classes with `Base<T>`: options `authority` (default) | `any_peer`; `call_remote` (default) | `call_local`; `unreliable` (default) | `unreliable_ordered` | `reliable`; `channel = N` (u32); or `config = <RpcConfig expr>` with fields `rpc_mode`, `transfer_mode`, `call_local`, `channel`; example `#[rpc(unreliable_ordered, channel = 2)]`; not supported in secondary impl blocks. **Note the default transfer mode differs from GDScript's `@rpc` (reliable).** — [docs.rs: godot_api attribute](https://docs.rs/godot/latest/godot/register/attr.godot_api.html); GDScript default from [High-level multiplayer tutorial](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)

- `Gd<T>` tracks ref-counting for RefCounted types (`new_gd()`); `new_alloc()` types need `Gd::free()` or `queue_free()`; `cast::<U>()` panics on failure, `try_cast` returns `Result`; "If you try to access a destroyed object, the Rust code will panic." — [godot-rust book: Objects](https://godot-rust.github.io/book/godot-api/objects.html)

- `experimental-threads` "adds Send and Sync implementations for Gd<T>" and makes guards multi-thread aware; "the safety aspects are not ironed out yet"; `experimental-godot-api` cannot be combined with it; docs recommend Rust threads over Godot threads and note Godot's own thread-safety rules still apply and "the Rust compiler can't verify what happens to an object through C++ or GDScript." — [gdext docs (pr-671)](https://godot-rust.github.io/docs/gdext/pr-671/godot); [gdext docs (pr-910)](https://godot-rust.github.io/docs/gdext/pr-910/godot); [gdext __docs source](https://godot-rust.github.io/docs/gdext/master/src/godot/__docs.rs.html)

**godot-cpp vs gdext / performance**
- A community evaluation (gdext vs GDScript, not vs godot-cpp) found "GDScript might be more performant when it comes to frequent calls to the engine, while Rust might be more performant when it comes to actual calculations" and that "actual numbers are rare." — [franziskusz/gdext-evaluation](https://github.com/franziskusz/gdext-evaluation)

### Inferences
- Everything the built-in multiplayer exposes to GDScript is reachable from Rust: `rpc_config()`/`rpc_id()` via `Gd<Node>`, `#[rpc]` for the extension's own nodes, and both `Extension` traits with safe signatures (only the raw-pointer packet functions are `unsafe`). A Rust `MultiplayerAPIExtension` that owns a `SceneMultiplayer` can be installed with `SceneTree.set_multiplayer()` or `MultiplayerAPI.set_default_interface()`.
- Property interception from Rust is limited to the extension's own classes (`on_set`/`on_get`), mirroring the engine's rules; observing arbitrary GDScript nodes means polling `Object.get()`/`get_indexed()` per tick, with a Variant conversion per property read.
- The mismatch between `#[rpc]`'s default `unreliable` and GDScript's default `reliable` is a documentation/ergonomics trap for a mixed Rust/GDScript codebase (RPC checksums must match on both ends).
- A background networking thread should hand data to the main thread through channels and apply it in `process`/`physics_process`, since `experimental-threads` is explicitly unsound-risky and no safe cross-thread `Gd<T>` story exists.

### Gaps
- No primary measurement of gdext's cross-boundary call or Variant conversion overhead was found; the book pages fetched contained no performance statements.
- The "Currently supported features" status of gdext is tracked in GitHub issue #24, which could not be fetched.

## Key question 5 — Godot's determinism story: floats, physics engines (Godot Physics, Jolt, Rapier), fixed point, tick rate, physics interpolation, and what rollback addons do

### Takeaway
Neither Godot Physics nor Godot's Jolt integration promises determinism ("Godot Jolt is not able to make such guarantees"; Godot itself makes none), physics cannot be stepped manually (netfox cites Godot PR 76462), and rollback addons therefore either avoid the physics engine (netfox: kinematic bodies with workarounds, RigidBodies unsupported) or replace it with fixed-point physics (SG Physics 2D, Klotho's 32.32 fixed point). Physics ticks default to 60/s; physics interpolation (2D in 4.3, 3D moved into SceneTree in 4.5) renders 1–2 ticks behind and is documented as a poor fit for networked data.

### Cited Findings
- Physics Tick per Second defaults to 60 (Project Settings > Physics > Common); physics interpolation is "optional and disabled by default", blends previous and current transforms by `Engine.get_physics_interpolation_fraction`, shows objects "between one and two ticks in the past", and for multiplayer "networked data may not align with local ticks, so a custom interpolation approach may fit better." — [Physics interpolation introduction](https://docs.godotengine.org/en/stable/tutorials/physics/interpolation/physics_interpolation_introduction.html)
- `Node.physics_interpolation_mode` defaults to `PHYSICS_INTERPOLATION_MODE_INHERIT`; `reset_physics_interpolation()` "should be called **after** moving the node" to avoid a glitch on teleports. — [Node class reference](https://docs.godotengine.org/en/stable/classes/class_node.html)
- 2D physics interpolation shipped in 4.3 (3D "already in the making", PR #92391); 3D interpolation moved from RenderingServer to SceneTree in 4.5 (PR 104269) keeping the user API. — [Godot 4.3 release page](https://godotengine.org/releases/4.3/); [Godot 4.5 release page](https://godotengine.org/releases/4.5/)
- Jolt became the default 3D physics engine for new projects in 4.6 (PR #105737); existing projects keep their settings. — [Godot 4.6 release page](https://godotengine.org/releases/4.6/)
- Godot Jolt README (the extension that became the 4.4 engine module): "While Jolt itself offers deterministic simulations, Godot Jolt is not able to make such guarantees"; simulations "may even happen to be deterministic, but this should not be relied upon"; GitHub discussion #794: the extension makes "no guarantees about perfect determinism, nor does Godot itself for that matter"; the extension is in maintenance mode since Jolt was merged into Godot 4.4 as a module. — [godot-jolt discussion #794](https://www.github.com/godot-jolt/godot-jolt/discussions/794); [godot-jolt repo](https://github.com/godot-jolt/godot-jolt); [godot-jolt wiki](https://github.com/godot-jolt/godot-jolt/wiki)
- A Digital Production write-up of 4.6 says the engine "does not claim bit-exact determinism across platforms" (secondary source). — [Digital Production on Godot 4.6](https://digitalproduction.com/2026/01/28/godot-4-6-arrives-with-major-cg-friendly-updates/)
- netfox: Godot "doesn't support manually stepping or updating physics" (links Godot PR 76462); "Rollback and physics-based games ( RigidBodies ) don't work at the moment"; kinematic bodies work with `physics_factor`, `force_shapecast_update()`, `move_and_collide()` test mode, and a static→kinematic transform flush before each rollback tick; netfox.extras offers "optional rollback-compatible physics simulation". — [netfox rollback caveats](https://foxssake.github.io/netfox/latest/netfox/tutorials/rollback-caveats/)
- SG Physics 2D: a deterministic fixed-point 2D physics plugin by dsnopek because the built-in engine "isn't deterministic"; floating point "implementations vary significantly across even chips by the same manufacturer"; a Godot 4 port via GDExtension and Vector2i was planned in 2022 (shipping status unconfirmed). (older) — [SG Physics 2D forum tutorial](https://godotforums.org/d/28338-getting-started-with-sg-physics-2d-and-deterministic-physics-in-godot-good-for-rollback-netcode); [GDQuest glossary](https://www.gdquest.com/library/glossary/deterministic_simulation)
- Klotho (Godot .NET) uses 32.32 fixed-point (FP64) and a seeded RNG with deterministic physics and rollback. — [Godot Asset Library #5234](https://godotengine.org/asset-library/asset/5234)
- A forum thread argues Jolt "can be deterministic, but you may have to build your own library with specific flags." — [Forum: Delta Rollback in 3D](https://forum.godotengine.org/t/can-i-use-delta-rollback-in-3d/97665)
- Forum consensus (pennyloafers, 4.4.1 thread): deterministic lockstep "needs hardware determinism, hard across different platforms"; the alternatives are snapshot interpolation and state synchronization. — [Forum: MultiplayerSynchronizer vs RPC's](https://forum.godotengine.org/t/multiplayersynchronizer-vs-rpcs/115962)

### Inferences
- A Rust extension aiming at rollback should treat Godot physics as non-rewindable and non-steppable: either server-authoritative state sync with client prediction of kinematic movement only (netfox's model), or its own deterministic simulation in Rust (fixed point or carefully controlled f32) that drives Godot nodes as views.
- Because the engine has no public "step physics once" API (PR 76462 unmerged per netfox), running the simulation inside `_physics_process` at `physics_ticks_per_second` and using `reset_physics_interpolation()` on corrections is the only engine-blessed path.

### Gaps
- Rapier for Godot (the GDExtension `godot-rapier`) was not surveyed; its determinism claims are unverified here.
- Whether Godot's built-in Jolt module (4.4+) exposes Jolt's deterministic mode or any related project setting was not confirmed from primary docs.
- The status of Godot PR 76462 (manual physics stepping) in 2026 was not checked directly (netfox cites it as unavailable "at the time of writing").
- Cross-platform float determinism of GDScript/Godot math (e.g. FMA, trig implementations) has no primary-source statement found; community claims only.
