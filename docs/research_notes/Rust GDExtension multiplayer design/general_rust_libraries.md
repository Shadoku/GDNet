# General-purpose (engine-agnostic) multiplayer and netcode libraries, with depth on the Rust ecosystem

Research notes compiled 2026-11-08. Version numbers and release dates come from the crates.io API unless stated; star counts and "last commit" values were read from the shields.io GitHub badges on 2026-11-08 (the GitHub API itself was blocked in this session), so they are approximate ("1.2k"). Dates are given where a source gave them; anything older than 2025 is marked.

A note on the two wasm targets, because it governs the whole "compiles for Godot web exports" question: godot-rust (gdext) web export builds for `wasm32-unknown-emscripten` with a nightly toolchain and `-Zbuild-std`, not for `wasm32-unknown-unknown` ([godot-rust book](https://godot-rust.github.io/book/toolchain/export-web.html)). Every Rust networking crate below that "supports wasm" does so through `wasm-bindgen`/`web-sys` on `wasm32-unknown-unknown` (matchbox, naia, renet2, web-transport-wasm, aeronet_webtransport, ggrs's `wasm-bindgen` feature). Whether those JS-glue paths work inside an Emscripten side module loaded by Godot is **not documented anywhere I found**; treat "wasm support" in this document as "wasm32-unknown-unknown support" unless Emscripten is named explicitly (Jolt is the one library that explicitly verifies Emscripten).

## Key question 1: Rust replication frameworks (lightyear, bevy_replicon, naia, ggrs/bevy_ggrs, backroll, matchbox, bevy_quinnet, aeronet, bevy_nest)

### Takeaway
As of late 2026 the Rust replication layer has consolidated around Bevy: lightyear (0.31, Oct 2026) rebuilt itself on bevy_replicon (0.45.5, Oct 2026) in June 2026 and even its transport crate depends on `bevy_ecs`/`bevy_app`, so neither is usable from a Godot GDExtension without Bevy. The engine-independent options are naia (0.25, May 2026; ECS-agnostic core with diff-mask replication, tick-buffered inputs, rooms/scopes, browser WebRTC), GGRS (0.13, June 2026; GGPO-style rollback with no Bevy dependency and a pluggable socket) and matchbox_socket (0.15, Oct 2026; WebRTC full mesh, native + browser) — and backroll (2022) is dead.

**naia (naia-lib)**
- `naia-server`/`naia-client`/`naia-shared` 0.25.0, 2026-05-12, MIT OR Apache-2.0; recent downloads only 426–787 — [crates.io](https://crates.io/crates/naia-shared). ~1.2k stars, last commit May 2026, release v0.25.0 — [GitHub](https://github.com/naia-lib/naia).

### Inferences
- lightyear's 2025–2026 redesign is two steps: the July 2025 rewrite into `lightyear_*` crates with entity-based links (0.21), then the June 2026 delegation of replication to bevy_replicon (0.27) which removed `ReplicationGroup`. What lightyear still owns is prediction/rollback, interpolation, visibility/rooms, inputs, bandwidth priority and the deterministic/P2P pipeline. Everything it owns is expressed as Bevy components/resources, and its transport crate depends on `bevy_ecs`, so there is no Bevy-free slice to lift into a GDExtension; its *designs* (RollbackPolicy, history buffers per component, priority accumulation, retaining visibility variants) are the copy-worthy part.
- bevy_replicon's "send every unacknowledged mutation every tick, client applies if newer" is a resend-until-acked model, not Quake-3 delta compression; lightyear 0.28's `Diffable` diff-compressed components add per-component deltas on top.
- naia is the only maintained Rust framework that is explicitly engine-independent and still ships entity replication with diff masks, scopes and tick-buffered inputs; its recent-download count (~400–800) and May 2026 last commit suggest a small user base compared with replicon/lightyear (recent downloads ~50–80k).
- GGRS and matchbox_socket are the cleanest Bevy-free building blocks: GGRS for rollback (request-based API, pluggable `NonBlockingSocket`), matchbox_socket for browser-capable P2P transport. Their wasm paths are `wasm-bindgen`-based (see the note at the top).

## Key question 2: Rust transports and reliability layers (renet/renetcode/renet2, quinn, WebTransport crates, laminar, turbulence, naia-socket, str0m/webrtc-rs, netcode-rs, steamworks, GNS bindings, ENet, NAT traversal)

### Takeaway
renet (2.0.1, Oct 2026) remains the standard Bevy-independent channel/reliability layer with netcode.io-style connect tokens via renetcode (Netcode 1.02), and its fork renet2 (1.0.0, Oct 2026) adds browser-capable WebTransport/WebSocket transports and multi-transport servers; QUIC is served by quinn (0.11.12) with wtransport (native, "not completely production-ready") and web-transport (native + wasm) on top; laminar and turbulence have had no release since 2021/2022; WebRTC is available as webrtc-rs (5.2k stars) or sans-IO str0m (0.25, Nov 2026); Steam Networking Sockets is reachable through the `steamworks` crate (0.13.1) and GNS through gns-rs; ENet exists as a safe transpiled port (rusty_enet 0.4.1) that its author calls not ready for serious use; iroh (1.4.1, 13k stars) is the serious QUIC-by-public-key hole-punching option.

### Cited Findings

**renet / renetcode / renet2**
- `renet` 2.0.1 (2026-10-30), `renetcode` 2.0.0 (2026-01-20), `bevy_renet` 6.0.0 (2026-10-30), `renet_steam` 4.0.0 (2026-10-30), all MIT OR Apache-2.0; renet 206,326 downloads / 42,729 recent — [crates.io renet](https://crates.io/crates/renet); [renetcode](https://crates.io/crates/renetcode). 961 stars, 534 commits, 15 open issues; "aimed at fast-paced titles like FPS games" — [GitHub](https://github.com/lucaspoffo/renet).

**netcode.io design (the model renet/renetcode/yojimbo follow)**
- Web backend authenticates the player and returns a connect token over HTTPS; the private portion is encrypted/signed with a key shared by backend and dedicated servers using a libsodium AEAD; public portion holds client keys, a server address list and authenticated-but-unencrypted data; tokens expire; handshake: request (server rejects seen tokens, checks expiry and its own address), small challenge encrypted with a per-server-start random key (anti-amplification), response (proves the source address), slot assignment or denial; payloads unreliable-unordered; ~5 s timeout; redundant disconnect packets; up to 256 clients in the reference implementation; ICE/STUN/TURN dropped because only dedicated servers are targeted; libsodium instead of DTLS — [Gaffer On Games](https://gafferongames.com/post/why_cant_i_send_udp_packets_from_a_browser/). The C reference `netcode` is at v1.4.9, 2.6k stars — [GitHub](https://github.com/mas-bandwidth/netcode). The old `netcode` Rust wrapper crate is 0.3.1 from 2017-04-23 (BSD-3) — [crates.io](https://crates.io/crates/netcode) (pre-2025, dead).

### Inferences
- For a Godot GDExtension that must not depend on Bevy, the realistic native transport stack is renet (or renet2 for browser clients and mixed UDP+WebTransport servers) over renetcode's connect tokens, with quinn/web-transport for QUIC where encryption and congestion control should come from the protocol, and the `steamworks` crate for Steam P2P/relay. None of renet, renet2, quinn, wtransport, web-transport, webrtc-rs, str0m, steamworks, rusty_enet or iroh depends on Bevy.
- laminar and turbulence should be treated as historical designs (both 2021–2023), not dependencies.
- The strongest free relay story for a Steam-shipped game is SDR via GNS lanes; for non-Steam P2P the Rust-native option is iroh's relay fallback (self-hostable) or a TURN server behind matchbox/webrtc-rs.

### Gaps
- No throughput/latency benchmarks of renet vs quinn vs GNS were found.
- The renetcode constant values (token size, user-data bytes, max payload) were not on the docs index page; they follow the Netcode 1.02 standard but I did not verify the numbers.
- I did not find documentation of how renet2's WebTransport client behaves under Emscripten (only `wasm32-unknown-unknown` is stated).
- str0m's and webrtc-rs's wasm status was not checked (both are primarily server-side; browser peers use the browser's own WebRTC).

## Key question 3: C/C++ and other general-purpose libraries, backends and relay services (ENet, yojimbo, GNS, libjuice, KCP, GGPO, Snapnet, Quilkin, Agones, Hathora, Edgegap, Nakama, Colyseus, SpacetimeDB, Rivet, PlayFab, SDR, EOS P2P)

### Takeaway
The C/C++ classics are stable and mostly unchanging (ENet 1.3.18, yojimbo 1.15.2 "production ready" but single-threaded and sized for ≤100 players, KCP 2.1.1 with its 30–40 % latency claim, GGPO untouched since 2019 and Windows-only); the design-worthy commercial middleware is Snapnet (server-authoritative predict/rollback that explicitly does not require determinism); the backend layer saw a shake-up in 2026 (Hathora shut down May 5 2026, PlayFab cut its free tier, Rivet pivoted to generic Actors) while the open-source constants remain Nakama 3.42, Colyseus 0.18 (MIT, schema with @type decorators and 63-field limit), Agones 1.62 and Quilkin (calendar-versioned 2026.10.4); SpacetimeDB 2.x (26k stars, BSL 1.1) is the "database is the server" model that runs BitCraft as a single module.

### Cited Findings

**C/C++ libraries**
- yojimbo (Glenn Fiedler): client/server over UDP with encrypted, signed packets; netcode-style connect tokens; connection management and timeouts; fragmentation; unreliable-unordered and reliable-ordered channels; data blocks on reliable messages; bitpacker/serialization; per-connection latency/jitter/loss/bandwidth estimates; "Designed for client/server games with 100 players or less"; single-threaded; "stable and production ready"; BSD-3; built on netcode, reliable and serialize — [README](https://raw.githubusercontent.com/mas-bandwidth/yojimbo/main/README.md); v1.15.2, 2.8k stars — [GitHub](https://github.com/mas-bandwidth/yojimbo).
- KCP: "Average latency is 30–40% lower than TCP, with up to 3x lower maximum delay, at a cost of 10–20% more bandwidth"; pure algorithm with no sockets or clock; fast-mode RTO ×1.5 instead of TCP's ×2; selective retransmit; fast retransmit on out-of-order ACKs; immediate ACK option; UNA + explicit ACK hybrid; TCP-fair flow control by default, `nc` disables congestion control/slow start; MIT; users kcptun, v2ray, frp, shadowsocks-android; Rust ports kcp-rs and kcp-rust-native — [README.en](https://raw.githubusercontent.com/skywind3000/kcp/master/README.en.md); v2.1.1, 17k stars — [GitHub](https://github.com/skywind3000/kcp).
- GGPO: MIT; Windows-only build (VS2019 + CMake, "efforts are underway to port it"); sample Vector War — [README](https://raw.githubusercontent.com/pond3r/ggpo/master/README.md); 3.6k stars, last commit November 2019 — [GitHub](https://github.com/pond3r/ggpo). ### Inferences
- The copy-worthy designs here are: yojimbo/netcode's token + challenge handshake (already in renetcode), GNS's lanes (priority + weight per lane, independently sequenced), KCP's aggressive ARQ tuning for low-latency reliable channels, GGPO/GGRS's request-based rollback with SyncTest, Snapnet's claim that server-authoritative predict/rollback can work without determinism, Colyseus's declarative schema (field-level sync declarations, `@view` per-client visibility, patch-only vs join-only fields), and SpacetimeDB's "subscribe to a table, call a reducer" API surface.
- The hosting layer is volatile; a library should target Agones-compatible dedicated servers plus Steam/EOS-style relays rather than any single vendor.

### Gaps
- Quilkin's filter list and deployment modes could not be fetched (the book URL guessed returned 404); the README itself does not enumerate them.
- EOS P2P official docs did not render (empty/404), so relay-control modes, packet size limits and pricing are unverified.
- No pricing for Snapnet; no official PlayFab statement on the free-tier change (vendor blogs only).
- SpacetimeDB's single-threaded-per-database execution claim appears only in a third-party article; the official README does not state threading.

## Key question 4: Serialization and compression (bitcode, bincode, speedy, rkyv, postcard; bit packing; quantization; delta compression)

### Takeaway
postcard (1.1.3) has become the default wire format for both bevy_replicon and lightyear (0.29+), bitcode (0.6.9) is the smallest and most compressible but explicitly does not promise a stable format, rkyv (0.8.18) wins on zero-copy deserialize speed, and bincode 3.0.0 shipped in Dec 2025; quantization is done at the component-rule level (replicon `replicate_as`/`replicate_with`, naia `SignedVariableFloat<BITS,FRAC>`), and delta compression against acknowledged baselines exists as naia's per-user diff masks and lightyear's `Diffable` diff-compressed components, while replicon resends unacked changes rather than deltas.

### Cited Findings
- `bitcode` 0.6.9, 2025-12-18, MIT OR Apache-2.0, 11.9 M downloads — [crates.io](https://crates.io/crates/bitcode); 677 stars — [GitHub](https://github.com/SoftbearStudios/bitcode). README: "Uses smaller integers where possible all the way down to 1 bit"; "All instances of each field are grouped together making compression easier"; "Highly compressible by Deflate/LZ4/Zstd"; validation up front on typed vectors; auto-vectorisable; `#[derive(Encode, Decode)]` plus a `serde` feature; `no_std` with `alloc`; non-goals: "Stable format across major versions", self-describing format, non-Rust compatibility; inspired by tree-buf — [README](https://raw.githubusercontent.com/SoftbearStudios/bitcode/main/README.md).
- rust_serialization_benchmark (updated 2026-11-05, Xeon 6975P-C VM, rustc 1.101 nightly): **log** dataset — bitcode 0.6.9 serialize 174.69 µs / deserialize 1.4353 ms / 703,710 B / zstd 227,322 B; postcard 1.1.3 256.27 µs / 1.9480 ms / 724,953 B / 252,968 B; rkyv 0.8.18 222.22 µs / 1.4616 ms (unvalidated) / 1,011,488 B / 325,965 B; borsh 1.8.1 322.62 µs / 1.9068 ms / 885,780 B / 286,248 B. **mesh** dataset — bitcode 1.0012 ms / 533.75 µs / 6,000,006 B / zstd 4,921,841 B; postcard 411.56 µs / 1.0549 ms / 6,000,003 B / 5,346,897 B; rkyv 447.97 µs / 405.36 µs / 6,000,008 B / 5,346,872 B; borsh 3.1917 ms / 3.5318 ms. bincode and speedy were not in these two tables — [benchmark README](https://raw.githubusercontent.com/djkoloski/rust_serialization_benchmark/master/README.md).
- `bincode` 3.0.0, 2025-12-16, MIT, 370 M downloads — [crates.io](https://crates.io/crates/bincode); 3.1k stars. `speedy` 0.8.7, 2024-01-14 (pre-2025) — [crates.io](https://crates.io/crates/speedy). `rkyv` 0.8.18, 2026-08-05, 182.7 M downloads — [crates.io](https://crates.io/crates/rkyv); 4.4k stars. `postcard` 1.1.3, 2025-07-24, 89.5 M downloads, "no_std + serde compatible message library" — [crates.io](https://crates.io/crates/postcard); 1.6k stars.
- Defaults in the frameworks: bevy_replicon "Components use `postcard` by default" with `replicate_as`/`replicate_with` "such as quantization or skipping fields" and a `compact_entity` module that "packs `Entity` more efficiently for networking" — [docs.rs](https://docs.rs/bevy_replicon/latest/bevy_replicon/); lightyear "Uses `postcard` by default" (switched in 0.29) and supports optional LZ4 packet compression (0.27) — [README](https://raw.githubusercontent.com/cBournhonesque/lightyear/main/README.md), [releases](https://github.com/cBournhonesque/lightyear/releases).
- Quantization in naia: `Property<T>` with bandwidth types `SignedVariableFloat<BITS, FRAC>` and `UnsignedInteger<N>` — [CONCEPTS.md](https://raw.githubusercontent.com/naia-lib/naia/main/docs/CONCEPTS.md).
- Delta/diff models: naia "tracks changed fields per in-scope user, so only changed fields are sent" (diff masks) — [CONCEPTS.md](https://raw.githubusercontent.com/naia-lib/naia/main/docs/CONCEPTS.md); lightyear 0.25 `Diffable` with a `Delta` generic, registered after prediction/interpolation, and 0.28 "diff-compressed components, which send only deltas" — [releases](https://github.com/cBournhonesque/lightyear/releases); lightyear gathers updates "since the last ACK from the receiver" — [book](https://raw.githubusercontent.com/cBournhonesque/lightyear/main/book/src/concepts/advanced_replication/replication_logic.md); bevy_replicon "By default, all unacknowledged mutations are sent every tick" and the page "does not say whether mutations use delta compression" — [docs.rs](https://docs.rs/bevy_replicon/latest/bevy_replicon/). GNS and yojimbo explicitly leave delta encoding to the game (GNS: "Does not handle entity serialization, delta encoding, or compression"; yojimbo ships only a bitpacker) — [GNS README](https://github.com/ValveSoftware/GameNetworkingSockets), [yojimbo README](https://raw.githubusercontent.com/mas-bandwidth/yojimbo/main/README.md).
- Colyseus's state sync is "delta-compressed and binary-encoded" at the schema level with `.patchOnly()`/`.fullStateOnly()` per field — [README](https://raw.githubusercontent.com/colyseus/colyseus/master/README.md), [schema docs](https://docs.colyseus.io/state/schema).

### Inferences
- For a wire format that must stay stable across versions of a GDExtension, postcard (serde, stable, `no_std`, the ecosystem default) is the safe pick; bitcode is the right choice only if the library owns both ends and re-encodes on upgrade, since the authors disclaim format stability. rkyv's advantage (zero-copy reads) matters little for small per-tick packets.
- A Quake-3-style "delta against last acked snapshot" is not provided ready-made by any maintained Rust crate; naia's diff masks are the closest built-in, and lightyear's `Diffable` trait is the component-level analogue. A GDExtension would implement acked-baseline deltas itself on top of a bit-packer (bitcode's packing or a hand-rolled one).

### Gaps
- The benchmark page I read did not include bincode or speedy rows, so I have no like-for-like numbers for them.
- I found no documentation of lightyear's `Diffable` API beyond release notes, and no measurement of its bandwidth savings.
- No source quantified bevy_replicon's or renet's per-packet overhead.

## Key question 5: Determinism in Rust (fixed-point crates, Rapier/Avian/Jolt determinism, float determinism and glam/libm, state hashing for desync detection)

### Takeaway
Cross-platform determinism in Rust rests on IEEE-754 basic ops (+, −, ×, ÷, sqrt) being bit-exact while transcendental functions are not: Rapier requires its `enhanced-determinism` feature and nalgebra's `ComplexField::sin` instead of `f32::sin`, Avian 0.8 ships an `enhanced-determinism` feature ("cross-platform deterministic math… at a small performance cost") after listing determinism as a future feature in early 2025, Jolt (C++, Godot's physics) guarantees determinism per binary and offers `CROSS_PLATFORM_DETERMINISTIC` at ~8 % cost with Emscripten explicitly verified, and the `fixed` crate (1.31, Mar 2026) gives integer-exact arithmetic but deliberately no transcendental functions (the companion `cordic` crate is from 2021); desync detection is done by hashing state and comparing checksums at an interval (GGRS `DesyncDetection::On`, GGPO's checksum out-param, SyncTest sessions).

### Cited Findings
- `fixed` 1.31.0, 2026-03-20, MIT/Apache-2.0, 16.6 M downloads — [crates.io](https://crates.io/crates/fixed). Types `FixedI8`…`FixedI128`, `FixedU8`…`FixedU128` with typenum fractional bits (`FixedI32<U24>`), aliases like `I20F12`; arithmetic, comparisons, lossless/lossy/checked conversions, string parsing/formatting in several bases, `Saturating`/`Wrapping`/`Strict` wrappers, `sqrt`, bytemuck casting; "No algebraic, trigonometric, or other transcendental functions… this is deliberate"; "The `cordic` crate provides CORDIC-based functions"; features `serde`, `std`, `borsh`, `arbitrary`, experimental `num-traits`; `no_std` except `serde-str`; MSRV rustc 1.93 — [docs.rs](https://docs.rs/fixed/latest/fixed/). `cordic` 0.1.5, 2021-05-16, BSD-3-Clause (pre-2025) — [crates.io](https://crates.io/crates/cordic). `fixed-trigonometry` 0.4.4, 2024-09-30 — [crates.io](https://crates.io/crates/fixed-trigonometry).
- Rapier (`rapier3d` 0.36.1, 2026-10-10, Apache-2.0; 6k stars — [crates.io](https://crates.io/crates/rapier3d), [GitHub](https://github.com/dimforge/rapier)): "locally deterministic" by default (same machine, version, compiler); cross-platform determinism requires the `enhanced-determinism` feature, which cannot be combined with `simd8` (a separate determinism domain) but can with `parallel` (parallel results match sequential regardless of thread count); requires identical initial conditions and insertion order, "target platforms that comply with IEEE 754-2008… includes most modern mainstream processors and WASM targets", and trig/other functions computed via nalgebra's `ComplexField`/`RealField` instead of std (`ComplexField::sin(2.0)` not `2.0f32.sin()`) — [Rapier docs](https://rapier.rs/docs/user_guides/rust/determinism).
- Avian (`avian3d` 0.8.0, 2026-10-20, Bevy 0.20; 3.3k stars — [crates.io](https://crates.io/crates/avian3d), [GitHub](https://github.com/avianphysics/avian)): feature `enhanced-determinism` (off by default) "Enables cross-platform deterministic math, improving determinism across architectures at a small performance cost"; `parallel` on by default; `f64` feature; `libm ^0.2` optional dependency; "Avian is still young, so stability issues and bugs are to be expected" — [docs.rs](https://docs.rs/avian3d/latest/avian3d/). A March 2025 Bevy forum thread said Avian then listed "Proper cross-platform determinism" as a future feature — [redlib mirror of r/bevy](https://redlib.hbubli.cc/r/bevy/comments/1j5trxc/any_2d_platformers_with_avian) (pre-0.8). Avian's 2D determinism test hashes a chaotic falling-hinges scene's transforms against an expected value that must be updated whenever simulation behaviour changes — [avian3d 0.6.0 source](https://docs.rs/crate/avian3d/0.6.0/source/src/tests/determinism_2d.rs). lightyear's Avian integration defaults to position-based replication (0.29) — [releases](https://github.com/cBournhonesque/lightyear/releases).
- Jolt (C++; v5.6.0, 12k stars, MIT — [GitHub](https://github.com/jrouwe/JoltPhysics)): deterministic when "The APIs that modify the simulation are called in exactly the same order" and "The same binary code is used" (Windows build gives the same result on AMD or Intel); `CROSS_PLATFORM_DETERMINISTIC` CMake option targets identical results across MSVC2022/clang/gcc/emscripten, Debug/Release, Windows/macOS/Linux, x86/ARM/RISC-V/PowerPC/LoongArch, 32/64-bit, verified on "WASM32/WASM64 under emscripten in Node.js"; same source and same defines required (`JPH_DOUBLE_PRECISION` everywhere or nowhere); breakers: std trig ("different implementations on different platforms" — use Jolt's Sin/Cos), `std::sort`/heap/hash (use Jolt's QuickSort/BinaryHeap/Hash), inconsistent FP mode (recommends `-ffp-model=precise`/`/fp:precise`, `-ffp-contract=off`, consistent DAZ/FTZ), `BroadPhaseQuery` results "NOT deterministic", listener callback order non-deterministic, `GetActiveBodies` order non-deterministic; cost "approximately 8% slower"; Samples app has "Check Determinism" (save state, rewind, re-step, compare) — [Jolt docs](https://jrouwe.github.io/JoltPhysics/index.html). README: WebAssembly handled by the separate JoltPhysics.js project; integrations listed for Godot, Source (VPhysics-Jolt), Unreal; shipped in Horizon Forbidden West and Death Stranding 2 — [README](https://raw.githubusercontent.com/jrouwe/JoltPhysics/master/README.md).
- Float determinism: "IEEE 754 guarantees that +, -, *, / and sqrt produce the same bits on every platform Rust targets (SSE2+, aarch64, wasm32). It does not cover sin, exp, ln, powf, cbrt, hypot, … — those come from the platform libm"; the `alice-det-math` crate implements them from basic ops with fixed-order polynomials and no FMA, CI on macOS/Linux/Windows/wasm32, recommends clippy `disallowed-methods` for `f64::sin`/`cos`; excludes x87-only i586 and fast-math builds — [alice-det-math docs](https://docs.rs/alice-det-math) (crate author's claims).
- glam (`glam` 0.34.3, 2026-11-08, 182 M downloads — [crates.io](https://crates.io/crates/glam)): feature `libm` uses the `libm` crate's math functions instead of `std` (needed for `no_std`), `nostd-libm`, `scalar-math` disables SIMD, `core-simd` nightly; README makes "no statements about determinism or numerical precision differences between SIMD and scalar paths"; 0.35.0 to be the final breaking pre-1.0 release; MSRV 1.85 — [README](https://raw.githubusercontent.com/bitshifter/glam-rs/main/README.md). `libm` crate 0.2.16, 2026-03-17, "libm in pure Rust" (part of rust-lang/compiler-builtins) — [crates.io](https://crates.io/crates/libm).
- Desync detection: GGRS `DesyncDetection` "compares checksums between peers", `with_desync_detection_mode` (`On` needs interval > 0), `SyncTestSession` with `with_check_distance` (default 2, "2 or higher to catch non-determinism") — [docs.rs](https://docs.rs/ggrs/latest/ggrs/struct.SessionBuilder.html); GGPO `save_game_state` has a checksum out-parameter and synctest rolls back one frame every frame — [DeveloperGuide](https://raw.githubusercontent.com/pond3r/ggpo/master/doc/DeveloperGuide.md); bevy_ggrs links `docs/debugging-desyncs.md` — [README](https://raw.githubusercontent.com/gschup/bevy_ggrs/main/README.md); lightyear 0.27 added "late-join catch-up for deterministic games" and 0.22/0.29 deterministic input-only modes — [releases](https://github.com/cBournhonesque/lightyear/releases).

### Inferences
- A Godot GDExtension using Godot's own Jolt-based 3D physics inherits Jolt's per-binary determinism only if Godot ships identical binaries to all peers and the game calls the API in the same order — and Godot's build does not necessarily set `CROSS_PLATFORM_DETERMINISTIC`, so cross-platform lockstep over Godot physics is not something the library can promise (see the Godot-ecosystem notes for Godot's side). For library-owned simulation, the Rust recipe is: `fixed` or f32/f64 with basic ops only, transcendentals from `libm`/a software implementation (glam's `libm` feature routes glam's math there), no `fast-math`, and a per-tick state hash compared across peers GGRS-style.
- Avian's `enhanced-determinism` exists in 0.8, but neither Avian nor Rapier publishes a cross-platform verification matrix comparable to Jolt's; treat Rust physics determinism as "designed for" rather than "verified across platforms".

### Gaps
- No official Rust-lang statement on float determinism was found (only the `alice-det-math` author's summary); the IEEE basic-ops claim is standard but I could not cite rust-lang documentation for it.
- Avian's 2026 changelog entry introducing `enhanced-determinism` was not located, so when it moved from "future feature" to shipped is unknown (between March 2025 and 0.8).
- glam's own position on determinism across SIMD vs scalar paths is absent from its README.

## Key question 6 (the constraint): what is usable from a non-Bevy Godot GDExtension, and what compiles to wasm32 for Godot web exports

### Takeaway
Usable without Bevy: naia (core), GGRS, matchbox_socket (+ matchbox_server), renet/renetcode/renet2, quinn, wtransport, web-transport, webrtc-rs, str0m, steamworks, gns-rs, rusty_enet, iroh, rust-p2p-core, bitcode/postcard/bincode/rkyv, fixed, glam, Rapier. Not usable without Bevy: lightyear (all crates, including `lightyear_transport`), bevy_replicon and every `bevy_replicon_*` backend, bevy_ggrs, bevy_matchbox, bevy_quinnet, aeronet (all IO crates, Bevy-native), bevy_rewind, Avian. For Godot web exports the target is `wasm32-unknown-emscripten`, and every crate's "wasm support" I found is for `wasm32-unknown-unknown` with wasm-bindgen glue, so browser networking from a GDExtension is unverified territory.

### Cited Findings
- Godot web export of a gdext extension: nightly rustc, `wasm32-unknown-emscripten` target, `rust-src`, `cargo +nightly build -Zbuild-std --target wasm32-unknown-emscripten`; emsdk 3.1.74 for Godot 4.3+ (≤3.1.39 for 4.2); gdext features `api-custom`, `experimental-wasm`, `lazy-function-tables`, `experimental-wasm-nothreads` for single-threaded builds; link flags `-sSIDE_MODULE=2`, `emscripten-wasm-eh=false` (Rust 1.93+ enables wasm EH by default, "which breaks Godot"); recommended to ship both a `.threads.wasm` and a nothreads `.wasm`; threaded exports need Cross-Origin Isolation; panics abort; Firefox support needs 4.3+ and is more limited; web support is "experimental" — [godot-rust book](https://godot-rust.github.io/book/toolchain/export-web.html).
- Crates whose wasm path is wasm-bindgen/web-sys on `wasm32-unknown-unknown`: matchbox_socket (wasm deps `wasm-bindgen`, `web-sys`, `js-sys`, `ws_stream_wasm`) — [docs.rs](https://docs.rs/matchbox_socket/latest/matchbox_socket/); naia (`wbindgen` feature, wasm-pack/trunk, `wasm32-unknown-unknown`) — [README](https://raw.githubusercontent.com/naia-lib/naia/main/README.md); renet2_netcode (`wasm32-unknown-unknown` with `wt_client_transport`/`ws_client_transport`) — [README](https://raw.githubusercontent.com/UkoeHB/renet2/main/README.md); web-transport (`web-transport-wasm`) — [crates.io](https://crates.io/crates/web-transport); ggrs (`wasm-bindgen` feature) — [docs.rs](https://docs.rs/ggrs/latest/ggrs/); rusty_enet works in wasm only "if you supply your own WebRTC interface or similar" — [README](https://raw.githubusercontent.com/jabuwu/rusty_enet/main/README.md).
- Bevy dependence evidence: `lightyear_transport` depends on `bevy_app`, `bevy_ecs`, `bevy_reflect`, `bevy_time`, `bevy_utils` — [Cargo.toml](https://docs.rs/crate/lightyear_transport/latest/source/Cargo.toml.orig); aeronet is "Bevy-native… network state as entities, observers, and component mutation" — [README](https://github.com/aecsocket/aeronet); GGRS "does not depend on Bevy" — [README](https://github.com/gschup/ggrs); naia core is ECS-agnostic with separate Bevy adapters — [README](https://raw.githubusercontent.com/naia-lib/naia/main/README.md); renet's Bevy integration is the separate `bevy_renet` crate — [README](https://github.com/lucaspoffo/renet).
- Jolt is the only physics/netcode-adjacent library in this survey that explicitly verifies Emscripten determinism (WASM32/64 in Node.js) — [Jolt docs](https://jrouwe.github.io/JoltPhysics/index.html); Rapier states WASM targets are IEEE-754-2008 compliant for its guarantee — [Rapier docs](https://rapier.rs/docs/user_guides/rust/determinism).

### Inferences
- A GDExtension that wants browser play has two paths neither of which is proven: (a) make the Rust side transport-agnostic (GGRS's `NonBlockingSocket`, rusty_enet's socket trait, naia's `Socket` trait are precedents) and let the Godot web build supply the socket via Godot's own `WebRTCPeerConnection`/`WebSocketPeer` through gdext, or (b) try to compile a wasm-bindgen-based crate under Emscripten, which is undocumented. Path (a) is the only one with documented pieces on both sides.
- lightyear's design (one entity, per-component histories, RollbackPolicy, retaining visibility, priority accumulation) and naia's design (Property<T> diff masks, TickBuffered channel, rooms + user scope, delegated authority) are the two most complete reference architectures to copy; naia is additionally a dependency candidate because it is engine-agnostic, but its small active user base (≈400–800 recent downloads per crate) is a risk.

### Gaps
- No source documents any Rust networking crate being built or run under `wasm32-unknown-emscripten`; this is the largest unknown for a Godot web export and would need a build experiment.
- Mobile: naia states native iOS/Android are unsupported pending QUIC; the other Rust transports (renet, quinn) do not call out mobile explicitly and I did not find mobile-specific statements for them. Consoles: only GNS/SDR and Jolt mention console shipping; no Rust crate in this survey documents console support.
