# Multiplayer game networking: academic and industry literature survey (canonical, 2018-2026, and underused work)

Research date: 2026-11-08. "Today" in the dating below is late 2026. Each technique carries a status tag:
**[A] standard practice** (shipped in several engines/libraries), **[B] known but rarely implemented in libraries**,
**[C] new / under-explored**. "Measured" means the source reports an experiment or production measurement; "claim"
means a design statement or marketing without data. Items marked "(recalled, not re-fetched this session)" are
canonical facts whose primary source I know but did not re-open in this session; the report writer should treat
exact numbers there with care and prefer the fetched items.

## Key question 1: The canonical body of work (1985-2017) — what each solves, costs, numbers, and library adoption

### Takeaway
The canonical stack (Bernier/Source prediction + lag compensation, Quake 3 delta snapshots, Tribes 2 priority/most-recent-state ghosting, AoE deterministic lockstep, GGPO rollback, Fiedler's three models) is still the vocabulary every 2018-2026 engine uses; Unreal, Unity Netcode for Entities, Photon Fusion/Quantum, SnapNet and GGRS are each a direct descendant of one or two of these papers, and almost every measured number in the field (Valorant's 141 ms peeker's advantage, AoE's 200 ms turns, Fiedler's 256 kbit/s budgets) traces back to one of them.

### Cited Findings

**Prediction, reconciliation and lag compensation (Valve / Source lineage) [A]**
- Bernier (Valve, GDC 2001), "Latency Compensating Methods in Client/Server In-game Protocol Design and Optimization": client-side prediction of the local player, server-side rewind of other players to the client's view time for hit tests ("lag compensation"), interpolation of remote entities. The canonical text is hosted on the Valve Developer Community wiki — [Valve Developer Community](https://developer.valvesoftware.com/wiki/Latency_Compensating_Methods_in_Client/Server_In-game_Protocol_Design_and_Optimization) (recalled, not re-fetched this session; the companion "Source Multiplayer Networking" page returned HTTP 403 in this session, so its defaults — cl_interp 100 ms, lag-compensation rewind formula, sv_maxunlag — could not be re-verified).
- Gambetta's four-part "Fast-Paced Multiplayer" series (2014-2015) is the most-cited tutorial restatement of Bernier: authoritative server, prediction, server reconciliation via input sequence numbers, entity interpolation, and lag compensation — [gabrielgambetta.com](https://www.gabrielgambetta.com/client-server-game-architecture.html) (recalled, not re-fetched this session).
- Riot's VALORANT netcode post (deWet & Straily, 2020-07-28) is the most detailed shipped-game account of the Source model with numbers: 128 Hz server tick and a fixed 128 Hz movement timestep on client and server; server buffering 2 frames (0.5 queue insertion + 0.5 smoothing target + 1 apply/output); client buffering ~3 frames; baseline peeker's advantage ≈141 ms; Riot Direct + 128-tick at 35 ms RTT and 60 FPS cut it ~40 ms (28 %); at 144 FPS total ≈71 ms (49 % reduction); goal of 35 ms ping for 70 % of players; playtests found top players detect ~10 ms changes and a 10 ms shift in peeker's advantage swung evenly matched duels between a 90 % holder win rate and a 90 % peeker win rate (measured in internal playtests) — [Riot Games](https://www.riotgames.com/en/news/peeking-valorants-netcode).
- Riot lists the shipped technique set: server authority, client prediction, input/movement buffering on both ends, fixed timestep decoupled from render with interpolation, move queue/timeline mapping, server-side prediction of missing input (repeat last input), server-committed corrections that snap only the mispredicted client, bounded rewind lag compensation, a private backbone, player-adjustable client buffering, and design mitigations (shoulder-first peeks, moving inaccuracy, hit-tag slowdown) — [Riot Games](https://www.riotgames.com/en/news/peeking-valorants-netcode).

**Quake 3 snapshot-delta model [A]**
- Quake 3 (id, 1999) sends per-client snapshots delta-encoded against the last snapshot the client acknowledged, over unreliable UDP, so a lost packet costs nothing but a bigger next delta; the server keeps a ring of past snapshots per client for this. Primary descriptions: Brian Hook's 2004 note "The Quake3 Networking Model" and Fabien Sanglard's source review — [bookofhook](http://trac.bookofhook.com/bookofhook/trac.cgi/wiki/Quake3Networking); [fabiensanglard.net](https://fabiensanglard.net/quake3/network.php) (recalled, not re-fetched this session).
- Fiedler's "State Synchronization" (2015-01-05) implements the same "delta against acked baseline" idea per object: a 5-bit base-sequence offset covers ~half a second at 60 packets/s, and he estimates delta compression gives "about another order of magnitude" over quantization alone (claim/estimate) — [gafferongames.com](https://gafferongames.com/post/state_synchronization/).

**Tribes 2 networking model (Frohnmayer & Gift, GDC 1999/2000) [B for most-recent-state; A for the layered idea]**
- Four data classes: non-guaranteed, guaranteed (retransmit if lost), **Most Recent State** ("volatile data of which only the most recent version is of interest"), and Guaranteed Quickest. A Connection layer with a sliding window and packet-delivery **notification** (dropped packets are never retransmitted by the connection layer; the stream managers decide what to resend) with ~3 bytes/packet overhead, over a bit-packing stream — [gamedevs.org PDF](https://www.gamedevs.org/uploads/tribes-networking-model.pdf).
- Ghost manager: one ghost per object per remote host; **scope** decides what is ghosted; each object carries a State Mask ("TRIBES simulation objects typically have upwards of 20 state flags") so partial state is re-sent per flag; packets are filled "first by status change, then by object priority", priority assigned by the simulation; the server's per-client packet rate/size is set by the remote host (e.g. 10 packets/s for a 28.8 modem). Move manager gives "soonest possible" delivery of inputs; Event manager gives guaranteed and guaranteed-ordered events — [gamedevs.org PDF](https://www.gamedevs.org/uploads/tribes-networking-model.pdf).
- Halo: Reach's networking (Aldridge, GDC 2011, "I Shot You First") explicitly traces its foundation to the Tribes paper and uses "intentionally unreliable replication" to enable prioritisation for 16 players — [Wolfire GDC summary](https://wolfire-blog.appspot.com/2011/03/GDC-Session-Summary-Halo-networking); [Edgegap deep dive (secondary)](https://edgegap.com/blog/game-backend-deep-dive-halo-reach-netcode-host-migration). A UCL reading-group page lists "minimum total upstream of 250 kbit/s for the host of a solid 16 player game" and "maximum total upstream bandwidth of 675 kbit/s from a single peer" but the page is garbled and misdated, so treat as unverified — [ng.cs.ucl.ac.uk](https://ng.cs.ucl.ac.uk/?p=115). A secondary source claims >80 % bandwidth reduction from Halo 3 to Reach and that four of five major bandwidth wins were design changes rather than netcode — [Edgegap (secondary)](https://edgegap.com/blog/game-backend-deep-dive-halo-reach-netcode-host-migration).

**Deterministic lockstep (Age of Empires, Bettner & Terrano, 2001) [A for RTS; B elsewhere]**
- "1500 Archers on a 28.8" (Game Developer, 2001-03-22): target 16 MB Pentium 90 at 15 fps on a 28.8 modem; sending unit state would cap moving units at ~250, so only commands are sent; commands issued on turn N execute on turn N+2; typical turn length 200 ms; "communications turn" ≈ round-trip ping split into the frames the slowest machine can run; speed control carried in 2 bytes per "Turn Done" message, turn length rises quickly on latency spikes and decays slowly; 250 ms command latency unnoticed, 250-500 ms playable, >500 ms noticeable; users issue ~1 command per 1.5-2 s with spikes of 3-4/s; desync detection by checksumming world/objects/pathfinding/targeting and halting; sync traces reached ~50 MB; lessons: players prefer consistent latency over fast-but-variable, filter command spam, keep metering on, test on modems continuously — [Game Developer](https://www.gamedeveloper.com/programming/1500-archers-on-a-28-8-network-programming-in-age-of-empires-and-beyond).
- Factorio uses lockstep with "latency hiding" rather than rollback: a separate "latency state" duplicates the relevant part of game state and is re-initialised from the real state every tick; the team did not plan latency hiding for most entity interactions or combat (FFF-83, 2015); the original design was always peer-to-peer (FFF-147, 2016); combat latency hiding was reworked (FFF-302, 2019); latency-hidden car driving arrived in FFF-412 (2024) — [FFF-83](https://factorio.com/blog/post/fff-83); [FFF-76](https://factorio.com/blog/post/fff-76); [FFF-147](https://cf-www.factorio.com/blog/post/fff-147); [FFF-302](https://direct.factorio.com/blog/post/fff-302); [FFF-412](https://factorio.com/blog/post/fff-412).

**Rollback / GGPO [A for fighting games; B for 3D]**
- GGPO (Tony Cannon, created 2009, MIT on GitHub): the game advances on local input, predicts remote inputs from the last seen, and re-simulates from the divergence point when real inputs arrive; it requires a fully deterministic engine that can save/load state and step a frame without rendering; used in Skullgirls (Mike Z) and FinalBurn Alpha; described in Game Developer Magazine (Sept 2012) and an Evo 2017 talk — [ggpo.net](https://www.ggpo.net/).
- NetherRealm's move of Mortal Kombat X and Injustice 2 to rollback was presented at GDC 2017 by Michael Stallone (secondary summary only) — [Edgegap (secondary)](https://edgegap.com/blog/game-backend-deep-dive-mortal-kombat-x-injustice-2-rollback).
- Rollback implementations expose a fixed input-delay knob; delay can be set to zero "at the cost of extra rollbacks", and delay only hides latency up to the delay value — [Wikipedia: Netcode](https://en.wikipedia.org/wiki/Netcode); [Wikipedia: GGPO](https://en.wikipedia.org/wiki/GGPO).

**Fiedler's three models (snapshot interpolation, deterministic lockstep, state synchronization) [A]**
- State Synchronization (2015-01-05): 901 cubes; up to 32 inputs and 64 state updates per packet; a 256 kbit/s target versus the snapshot-interpolation demo's 18 Mbit/s; position quantised to 4096 values/m (from 512), smallest-three quaternion at 15 bits/component (from 9); jitter buffer of 4-5 frames at 60 Hz; **priority accumulator** (per-object priority added each frame, top objects within budget sent, sent ones reset to zero; player cube 1,000,000, interacting cubes 100, at-rest 1); render-side error offsets decaying by 0.95/frame (≤25 cm) blending to 0.85 (≥1 m). Stated trade-offs: no determinism needed and no stalls versus lockstep, but "approximate and lossy" with divergence and pops; vs snapshot interpolation it sends a prioritised subset at the cost of quantisation/priority/smoothing complexity — [gafferongames.com](https://gafferongames.com/post/state_synchronization/).
- Networked Physics in VR (2018-02-22, Oculus-sponsored, BSD sample for Unity/PhysX): two sequence numbers per cube (authority sequence, ownership sequence; ownership outranks authority), host as arbiter, guest authority persists until the host confirms; <256 kbit/s per player so 4 players fit in 1 Mbit/s; positions quantised to 1/1000 cm on both sides to kill stack jitter; ballistic prediction matched PhysX within quantisation ~90 % of the time, encoded as a single "perfect prediction" bit; 100 ms jitter buffer for avatars. Limits: cooperative only (no server authority), PhysX non-deterministic so state sync not lockstep, rotation prediction never achieved, high-energy collisions were the main divergence source — [gafferongames.com](https://gafferongames.com/post/networked_physics_in_virtual_reality/).

**Overwatch (GDC 2017) [A for the pattern; the "rollback gameplay not physics" idea is B in generic libraries]**
- Timothy Ford, "'Overwatch' Gameplay Architecture and Netcode" (GDC 2017): ECS architecture and a deterministic networked simulation used "to keep features responsive and precise" (the vault page gives no numbers) — [GDC Vault](https://gdcvault.com/play/1024001). Secondary coverage: Overwatch predicts all abilities and projectiles by default and opts out only when necessary, and reconciliation works because the dedicated server holds ground truth — [Edgegap (secondary)](https://edgegap.com/blog/game-backend-deep-dive-overwatch-2016-netcode-architecture-rollback). Server tick was ~20.8 Hz at launch (60 Hz only in custom games) and was raised worldwide to 63 Hz in 2016, with "favor the shooter" retained — [Kotaku](https://kotaku.com/overwatchs-low-tick-rate-can-be-a-problem-1778708854); [mein-mmo](https://mein-mmo.de/en/overwatch-tickrate-weltweit-63,104523/).

**Rocket League (GDC 2018) [B: client physics prediction with server reconciliation of a full rigid-body scene]**
- Jared Cone (Psyonix), "It IS Rocket Science! The Physics of 'Rocket League' Detailed", 2018-03-21; the talk is free on GDC's YouTube channel — [GDC Vault](https://www.gdcvault.com/play/1024972/); [Game Developer](https://gamedeveloper.com/design/video-the-rocket-science-behind-i-rocket-league-s-i-physics). A Psyonix dev post notes "because we used a fixed tick rate for physics/gameplay, the client and server communicate using frames instead of time" — [devtrackers.gg](https://devtrackers.gg/rocket-league/p/bb42f194-rocket-league-netcode-question-is-your-local-client-constantly-extrapolating-the-ball-other-players). The oft-quoted 120 Hz physics tick could not be verified from a primary source this session.

**Destiny's hybrid host model (GDC 2015) [B]**
- Justin Truman, "Shared World Shooter: Destiny's Networked Mission Architecture" (GDC 2015): low-latency action + drop-in co-op + strangers in-world — [GDC Vault](https://gdcvault.com/play/1022246/contactUs). Fan analysis of the talk: each console computes physics for its "bubble" (physics host), a cloud "activity host" keeps authoritative mission state and scripting so physics-host migration is invisible; it quotes Bungie as saying a public-bubble physics-host migration happens "on average every two minutes and forty seconds" (unverified transcription) — [nessus42 gist](https://gist.github.com/nessus42/42c112d1f9eb3de147ab6e01439683da); [destiny.bungie.org forum](https://destiny.bungie.org/forum/index.php?id=62716). Destiny 2 moved both hosts into Bungie's data centres and promised no more host migrations in raids/Trials — [nessus42 gist](https://gist.github.com/nessus42/3738647a2052c4758c6f46f0464c47a6); [PC Gamer](https://www.pcgamer.com/the-strange-science-of-destiny-2s-uniquely-complicated-netcode).

**Fortnite / Replication Graph [A in Unreal only]**
- Epic's Replication Graph exists because per-actor-per-connection relevancy checks bottleneck at Fortnite Battle Royale scale (100 players, ~50,000 replicated actors); persistent graph nodes (grid spatialisation, dormancy, always-relevant, owner-carried) build per-client lists; no performance numbers given — [Epic docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/replication-graph-in-unreal-engine).

**Academic canon: dead reckoning, Time Warp, TSS, local-lag, bucket sync, interest management**
- Dead reckoning per the IEEE DIS standard (IEEE 1278.1): extrapolate remote entities from last position/velocity/acceleration; send an update when the owner's own dead-reckoned replica exceeds a threshold — described as the state of the art the 2024 PDR paper improves on — [Walker et al., IEEE ToG 2024 PDF](https://ece.uwaterloo.ca/~sl2smith/papers/2023TOG-Predictive_Dead_Reckoning.pdf). [A]
- Jefferson 1985, "Virtual Time" (ACM TOPLAS 7(3)): optimistic Time Warp with rollback and anti-messages — the ancestor of all rollback netcode — [ACM DOI 10.1145/3916.3988](https://doi.org/10.1145/3916.3988) (recalled, not re-fetched). [A as ancestry]
- Cronin, Filstrup, Kurc & Jamin, "An efficient synchronization mechanism for mirrored game architectures" (NetGames 2002, pp. 67-73; extended in Multimedia Tools and Applications 23(1), 2004): **Trailing State Synchronization** keeps several copies of the simulation at increasing delays; when a trailing (more complete) state disagrees with a leading one, the leading state is rolled back to the trailing one; evaluated on Quake in a mirrored-server architecture — [cronin-netgames02 PDF](https://www.eecg.utoronto.ca/~ashvin/courses/ece1746/2003/reading/cronin-netgames02.pdf); [UBC summary](https://www.cs.ubc.ca/~krasic/cpsc538a/summaries/38). [B]
- Mauve, Vogel, Hilt & Effelsberg, "Local-lag and Timewarp: Providing Consistency for Replicated Continuous Applications" (IEEE Trans. Multimedia 6(1):47-57, 2004): formal definitions of consistency and correctness for continuous replicated applications; proves a responsiveness vs short-term-inconsistency trade-off; **local-lag** deliberately delays local execution (minimum ≈ network delay: ~1 ms LAN, 20 ms national, 40 ms continental, 150 ms worldwide, plus clock skew; cites psychology suggesting 80-100 ms is not noticeable; notes a 1990s game already delayed local updates by 100 ms); **timewarp** repairs residual inconsistencies; timewarp cost is O(n²) in participants vs O(n) for dead reckoning, "very limited computational resources if the number of participants is sufficiently small (e.g., below 50)" in an unoptimised Java implementation (measured); dead reckoning gives consistency but "cannot guarantee correctness"; choice is application-dependent — [HHU PDF](https://publications.cs.hhu.de/library/Mauve2004a.pdf). [B]
- Bucket synchronisation (Diot & Gautier, MiMaze, IEEE Network 1999) groups events into fixed time buckets executed after a fixed playout delay — the lockstep-without-waiting ancestor (recalled, not re-fetched; no URL verified this session). [B]
- Interest management: the aura/nimbus spatial model (Benford & Fahlén, MASSIVE, mid-1990s) lets an entity perceive another only when its nimbus overlaps the other's aura, not necessarily mutually; Boulanger et al. (2006) measured that obstacle-aware interest management on a real MMOG cut update messages by up to 6× — [Boulanger 2006 PDF](https://www.sable.mcgill.ca/~clump/papers/boulanger-06-comparing.pdf); [Newcastle IM paper](https://research.ncl.ac.uk/game/research/publications/F6F6Ad01.pdf). Morgan, Lu & Storey's interest-management work (Newcastle, 2004-2005) is the usual academic citation (recalled). [A for grid/radius AoI; B for aura/focus/nimbus]
- Time dilation (EVE Online): CCP Veritas' 2011 dev blog proposes slowing simulated time to keep the server's command queue short, with an automatic floor at 10 % of normal time; by Feb 2012 "12.87 hours of simulation time in total have been dilated out of existence" in 12 days (measured) and "Time dilation does not solve everything" — [EVE Online](https://www.eveonline.com/news/view/introducing-time-dilation-tidi); [Engadget 2012](https://www.engadget.com/2012-02-09-eve-onlines-time-dilation-keeping-game-in-sync.html); [PC Gamer](https://www.pcgamer.com/eve-onlines-mad-time-dilation-tech-beats-lag/). [B]

### Inferences
- Nearly every shipped FPS since 2001 is Bernier + Quake-3 deltas + a Tribes-style priority scheduler; the differences between engines are in budgets (tick rate, buffers, rewind caps), not in model. Riot's numbers are the best public calibration of what those budgets buy (≈40 ms per step).
- The two canonical ideas that **libraries** mostly dropped are Tribes' per-flag most-recent-state with notification-based resend (libraries ship reliable/unreliable channels instead) and Mauve's local-lag as a tunable (libraries ship fixed input delay only in rollback modes).
- Age of Empires' turn-length adaptation and Mauve's local-lag are the same lever (deliberately trading responsiveness for consistency) discovered independently in industry and academia; both are measured to be invisible under ~100-250 ms.

### Gaps
- Source engine defaults (cl_interp, sv_maxunlag, rewind formula) could not be re-verified: the Valve wiki page returned 403.
- Overwatch GDC 2017 slide-level numbers (client ahead-of-server offset, rewind window) are not on the vault page; only secondary summaries were found.
- Rocket League's physics tick rate (commonly quoted 120 Hz) was not confirmed by a primary source.
- Halo Reach bandwidth numbers come from a garbled secondary page.
- Destiny's "migration every 2 min 40 s" is a fan transcription of the talk.
- No primary source for Diot & Gautier (bucket synchronisation) or Benford & Fahlén (aura/nimbus) was fetched; both are cited from memory.
- Gears of War and Titanfall/Respawn networking talks were not researched this session.
- Croquet's original TeaTime two-phase protocol (Reed/Smith/Kay/Raab, 2001-2007) versus the current reflector design: only secondary notes found (see KQ3).

## Key question 2: Newer research and industry designs, 2018-2026

### Takeaway
The measurable progress since 2018 is in (i) user studies that quantify peeker's advantage and fairness interventions (Claypool/NVIDIA FDG 2024/2026, Michaelides & Bellalta ToG 2026), (ii) learned motion prediction that beats DIS dead reckoning by up to 45 % at 300-400 ms update intervals (Walker et al. ToG 2024, with Ubisoft La Forge), and (iii) infrastructure (QUIC/BBR in Hytale, Valve SDR, Quilkin, SpacetimeDB); rollback for 3D physics is advancing in products (SnapNet, Easel 2026) not in papers, and CRDT/local-first approaches to games remain prototypes.

### Cited Findings

**Peeker's advantage and lag-compensation measurements [measured]**
- Tokey, Chen, Mettler, Tang, Boudaoud, Kim, Spjut & Claypool (WPI/NVIDIA), "The Effects of Network Latency on the Peeker's Advantage in First-person Shooter Games" (FDG 2024, DOI 10.1145/3649921.3650002): 24 users, one-way latencies 0/30/60 ms, peeker distances 7/19/27 m, a custom two-player FPS with self-prediction, 240 Hz monitor, local system latency 26.2 ms (SD 3.2) measured with a 1000 fps camera. Win-percentage difference (peeker minus defender) by peeker latency (rows 0/30/60 ms) × defender latency (columns 0/30/60 ms): 0 ms: −5.4 / 3.4 / 30.8 %; 30 ms: −7.4 / 4.4 / 28.8 %; 60 ms: −13.0 / 16.5 / 27.9 % (±~2.8 %, 95 % CI) — i.e. the advantage is driven by the **defender's** latency ("nearly 30 % regardless of the peeker's latency" at 60 ms defender) and is lowest with the peeker nearest the corner; distance effect F(2,11176)=40.7, p<.001; no significant time-to-damage difference (t(3430)=1.10, p=.27); a follow-up tournament with 15 of the users (RTX 3090 prize) had ~20 % more encounters per unit time — [WPI PDF](https://web.cs.wpi.edu/~claypool/papers/peeker-fdg-24/paper.pdf); [NVIDIA Research](https://research.nvidia.com/index.php/publication/2024-05_effects-network-latency-peeker-s-advantage-first-person-shooter-games).
- Michaelides & Bellalta (UPF Barcelona), "Demystifying the Peeker's Advantage in Multiplayer First-Person Shooter Games", IEEE Transactions on Games 18(1):197-206, published 2026-01-20 (CC-BY): simulation over system delays, frame rate, network delay and reaction time; **frame rate is the most influential factor, server tick rate and network delay have minimal impact**; 120 fps client + 60 ticks/s server brings the advantage below 100 ms; consistent across LAN and Internet configurations (simulation, not user study) — [OpenAlex record](https://api.openalex.org/works/doi:10.1109/TG.2026.3656267); [IEEE ToG spotlight](https://transactions.games/spotlight/august-2026-spotlight-paper). Note the tension with Riot's model, which attributes ~40 ms to tick rate + backbone; both agree frame rate dominates.
- Liu & Claypool (MMSys 2023): 39-person target-selection study; time warp (server rewind) and self-prediction each improve performance and QoE and together nearly fully offset latency — [WPI PDF](https://web.cs.wpi.edu/~claypool/papers/3d-selection-23/paper.pdf).
- Tokey, Boudaoud, Spjut & Claypool, "Adaptive Time Delay for Improving Player Experience and Fairness in FPS Games with Network Latency" (FDG 2026, Copenhagen, Aug 10-13 2026): time delay (adding latency to the low-latency player) equalises fairness but hurts QoE; **adaptive** time delay only adds it during player interactions; three studies (Zombiefield single-player, Last Stand and Color Clash multiplayer) with nearly 100 users show adaptive delay improves QoE vs fixed delay at high latency, improves fairness vs no delay, and that adding latency **gradually** matters for QoE — [WPI PDF](https://web.cs.wpi.edu/~claypool/papers/adaptive-fdg-26/paper.pdf); [NVIDIA Research](https://research.nvidia.com/publication/2026-08_adaptive-time-delay-improving-player-experience-and-fairness-first-person.md). Its related-work section cites: CS:GO accuracy −3 % and score −17 % from 0 to 150 ms with QoE −25 % between 25 and 150 ms (Liu et al.); defenders at 120 ms losing noticeably (their earlier work); jitter having no significant effect; Mauve et al. showing 250 ms local lag in a teleoperation app reduced inconsistencies — same PDF.
- "Shot around a corner" (NetGames 2017): a 250 ms cap on lag-compensation rewind is reasonable for 4 m/s movement — [AMiner record](https://www.aminer.org/pub/59ae3c592bbe271c4c7212ab/on-shot-around-a-corner-in-first-person-shooter-games). PolyU CS:GO study (Lee & Chang): lag compensation and higher tick rate significantly raise accuracy — [PolyU](https://research.polyu.edu.hk/en/publications/evaluation-of-lag-related-configurations-in-first-person-shooter-/). A WPI tech report proposes a "consistency-responsiveness space" for evaluating compensation methods by simulation — [WPI TR 20-01](https://ftp.cs.wpi.edu/pub/techreports/pdf/20-01.pdf). Halbhuber, "To Lag or Not to Lag" (CHI PLAY 2022 / dissertation) — [WPI mirror](https://digital.wpi.edu/downloads/3x816n147?locale=en) (not read).
- I found no paper literally titled "A Quantitative Analysis of Lag Compensation" by Saldana; the closest quantitative works are the WPI/NVIDIA and PolyU studies above.

**Learned motion prediction / neural dead reckoning [C]**
- Walker, Gilhuly, Sadeghi, Delbosc (Ubisoft La Forge) & Smith, "Predictive Dead Reckoning for Online Peer-to-Peer Games", IEEE Transactions on Games 16(1):173-184, 2024 (DOI 10.1109/TG.2023.3237943; supported by Ubisoft Toronto): a fully-connected network (2 layers × 100) or LSTM (2 layers × 128) predicts an opponent vehicle's future position from a reduced state (controls incl. steering/brake, and for the LSTM the last three states), paired with a **path-tracking controller from mobile robotics** (unicycle model, heading error clamped to ±80°) to converge the replica smoothly; trained on driving data recorded in Unity, with GTA Online as the motivating example; message intervals T = 100-400 ms; "up to 45 % less error" in RMS displacement vs the DIS dead-reckoning state of the art, with all methods near-equal at ≤200 ms and the LSTM best at 300-400 ms; a linear-blend baseline used λ = 0.4; a collision network handles static obstacles (measured, simulation) — [Waterloo PDF](https://ece.uwaterloo.ca/~sl2smith/papers/2023TOG-Predictive_Dead_Reckoning.pdf); [UWaterloo thesis](https://uwspace.uwaterloo.ca/handle/10012/16960).
- Earlier: McCoy, Ward & McLoone (Maynooth), "neuro-reckoning" extends DIS dead reckoning with neural nets — [Maynooth PDF](https://mural.maynoothuniversity.ie/1446/1/TWUsing_Neural-Networks.pdf). A European patent EP 4042342 A1, "Latency compensation using machine-learned prediction of user input", exists (applicant not confirmed) — [EPO](https://data.epo.org/publication-server/rest/v1.2/patents/EP4042342NWA1/document.html). No EA SEED netcode publication was found.

**Rollback for 3D / physics [B in products; C in papers]**
- SnapNet (product page, archived 2025): automatic prediction, rollback and reconciliation for gameplay and rigid bodies "with strict determinism not required"; shooters can "rollback and resimulate the entire game state (like GGPO) without requiring strict determinism" (claim) — [snapnet.dev via archive](https://dr.molodetz.nl/_proxy/https/web.archive.org/web/20250730030337/https://www.snapnet.dev/).
- Easel, "A Physics Engine with Incremental Rollback" (2026-05-01): snapshots and rolls back only bodies that change ("perhaps less than 30 per frame" in a large world, a "30-50×" reduction in snapshot work), bodies sleep at ~zero velocity, BVH with lazy rebalancing, swept CCD incl. dynamic-vs-dynamic; says Photon Quantum has no CCD because its stateless physics would make it too expensive; built on Parry; no determinism or benchmark numbers — [easel.games](https://easel.games/blog/2026-rollback-physics).
- Photon Quantum 3: predict/rollback with input-only sync, a game-agnostic authoritative server that synchronises clocks and distributes inputs each tick ("clients never need to wait for a slower client" unlike lockstep), pure-C# deterministic simulation with deterministic math/2D-3D physics/navmesh/animation libraries, sparse-set ECS with a custom allocator and zero runtime GC, Qtn DSL codegen — [Photon docs](https://doc.photonengine.com/quantum/current/getting-started/quantum-intro).
- Rust/WASM determinism: Rapier's `enhanced-determinism` feature (incompatible with `simd8`) targets IEEE 754-2008 platforms incl. WASM; transcendental functions must go through nalgebra's `ComplexField`, not `f32::sin` or `Math.sin`; the JS build is "deterministic across machines" with matching snapshot hashes — [rapier.rs](https://rapier.rs/docs/user_guides/rust/determinism/); [rapier.rs JS](https://rapier.rs/docs/user_guides/javascript/determinism). GGRS is a Rust GGPO reimplementation (no NAT traversal/signalling; Matchbox for browsers) — [docs.rs ggrs](https://docs.rs/crate/ggrs/latest/source/docs/setup.md); a community Bevy+GGRS+Rapier demo lists "deterministic physics and rollbacks (allegedly)" — [GitHub](https://github.com/cscorley/bevy_ggrs_rapier_example). A Godot Rocket-League-style rollback prototype needed a pending PR for manual physics stepping (Godot physics and Jolt lack it) — [80.lv](https://80.lv/articles/rocket-league-inspired-physics-network-game-prototype-in-godot).
- Unity Netcode for Entities 1.4 prediction: the prediction loop "runs from the oldest tick applied to any entity" and resimulates in `PredictedSimulationSystemGroup` (fixed step, several times per frame; physics inside it is resimulated too); partial ticks via `NetworkTime.IsPartialTick`; `IsFirstTimeFullyPredictingTick` guards one-shot effects; remote players can be predicted from serialised `IInputComponentData`; cost: a 300 ms connection can mean ~22 frames of resimulation in one frame; `GhostPredictionSmoothingSystem` reconciles errors over time; prediction switching by radius — [Unity docs](https://docs.unity3d.com/Packages/com.unity.netcode@1.4/manual/prediction-n4e.html); [Unity docs](https://docs.unity3d.com/Packages/com.unity.netcode@1.4/manual/prediction.html).
- Unreal Iris: push-based dirty tracking (game code notifies; "Iris does not expect the replication system to poll"), replication-state structs with per-member changemask bitfields and an init-state dirty bit, pipeline = copy+quantise dirty data → reset dirtiness → filtering → priority scheduling → sort by priority/dependencies → serialise — [Epic docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/components-of-iris-in-unreal-engine); [FReplicationStateHeader](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/IrisCore/FReplicationStateHeader).

**Transport: QUIC/WebTransport, reliable-UDP critiques, relays [A for custom UDP; B/C for QUIC]**
- Fiedler, "Why can't I send UDP packets from a browser?" (2017): web games on TCP suffer head-of-line blocking; QUIC removes it across streams but "it still exists within each stream" — [gafferongames.com](https://gafferongames.com/post/why_cant_i_send_udp_packets_from_a_browser/).
- Valve GameNetworkingSockets: ack-vector reliability "based on the 'ack vector' model from DCCP (RFC 4340 §11.4) and Google QUIC", AES-GCM-256 per packet, Curve25519 key exchange; the Steam Datagram Relay routes traffic over Valve's backbone to hide IPs and "in many cases improves ping"; the open-source build omits the relay — [GitHub README mirror](https://github.com/michicc/GameNetworkingSockets); [Steamworks docs](https://partner.steamgames.com/doc/api/ISteamnetworkingSockets); [Valve wiki SDR](https://developer.valvesoftware.com/wiki/Steam_Datagram_Relay).
- Quilkin (Embark Studios + Google Cloud, announced July 2021): non-transparent UDP proxy/sidecar for dedicated servers (Agones/Open Match ecosystem), hides server IPs; docs still describe it as alpha, "not to be used in production systems"; latest release seen v0.9.0 — [Google Cloud blog](https://cloud.google.com/blog/products/gaming/introducing-quilkin); [Embark on Medium](https://medium.com/embarkstudios/say-hi-to-quilkin-an-open-source-udp-proxy-88577c795204); [docs.rs](https://docs.rs/crate/quilkin/latest).
- Hytale (Hypixel Studios, 2026): secondary guides report QUIC over UDP with BBR congestion control added in Update 1 to reduce rubber-banding, UPnP exposure, and an August 2026 hotfix migrating P2P connectivity to ICE/STUN/TURN with fallback to a "direct connection race"; decompiled-server docs describe a Netty layer supporting QUIC and TCP — [Hone guide (secondary)](https://hone.gg/blog/?p=3631); [VeryGames (secondary)](https://www.verygames.com/en/novosti/pg-39-hytale-ice-stun-turn-multiplayer-svyazi); [community protocol docs](https://hytale-docs.pages.dev/modding/networking). No official Hypixel netcode post was found.
- Fraunhofer FOKUS (ISICT 2024, DOI 10.1007/978-981-96-4288-5_23): WebTransport/HTTP3 can reach latencies "comparable to WebRTC" for live streaming; motivated by cloud gaming but not a game-traffic evaluation — [Fraunhofer Publica](https://publica.fraunhofer.de/handle/publica/487765).
- Nakama relayed multiplayer: the server forwards messages "without inspection", holds only match ID and presences, no cheat detection; clients elect a host (lowest session ID) to reconcile; keep messages under the 1500-byte MTU and prefer one 1000-byte/s message over five 200-byte ones; broadcast order may differ from send order — [Heroic Labs docs](https://heroiclabs.com/docs/nakama/concepts/multiplayer/relayed/).

**"Database as the server" and replicated computation [C]**
- SpacetimeDB (BSL 1.1, v2.0): logic runs as a module inside the database; clients call transactional **reducers** (all-or-nothing) and **subscribe** to typed queries with incremental pushes into a client-side cache; commit-log persistence with hot-swap module updates; recommended pattern is one database per match/room; claims sub-microsecond hot-data access and "100-1000×" over traditional DBs (no benchmark given); no mention of client prediction, reconciliation or physics; BitCraft Online runs entirely on it as a single module — [SpacetimeDB FAQ](https://spacetimedb.com/docs/intro/faq); [BitCraft blog (Aug 2023)](https://bitcraftonline.com/news/spacetimedb-and-bitcraft).
- Croquet/Multisynq: Model code must be deterministic ("Croquet guarantees that the same sequence of random numbers is generated within the model on each device"; view-side `Math.random()` is unconstrained) — [Croquet tutorial](https://croquet.io/docs/croquet/tutorial-2_8_random.html); the reflector timestamps external messages from views and replicates them to all peers, with no application logic on the server; the "multiplayer code is executed on each client in a synchronized virtual machine, rather than on a server"; the reflector is published as a Node.js package — [GitHub croquet/croquet](https://github.com/croquet/croquet); [Krestianstvo write-up (secondary)](https://dev.to/nikolaysuslov/krestianstvo-electric-lazy-reflector-for-croquet-vm-4k93); DLS 2020 keynote "Croquet: A Unique Collaboration Architecture" — [conf.researchr.org](https://conf.researchr.org/details/dls-2020/dls-2020-papers/10/Croquet-A-Unique-Collaboration-Architecture-Keynote-).
- CRDTs in games: Netskip (Bertolotti et al.) — a formally analysed multiplayer architecture on CRDTs + skip lists — [UniMi PDF](https://air.unimi.it/bitstream/2434/1206402/2/da162ce9-8218-4b8e-9685-d50897f47a69.pdf); Dantas & Baquero, "CRDT-Based Game State Synchronization in Peer-to-Peer VR" (BrickSync, arXiv 2503.17826, March 2025), self-described first exploration of CRDTs in VR — [arXiv](https://arxiv.org/abs/2503.17826v1). Practitioner caveat: "it is rare for apps to use true CRDTs to power multiplayer collaboration" — [Jamsocket](https://jamsocket.xyz/blog/you-might-not-need-a-crdt).

**Cloud/edge placement [measured, 2024-2025]**
- "Gaming on the Edge" (IFIP Networking 2024): analytical model validated in the wild; edge deployment can beat cloud gaming under several parameter combinations, but the manager must weigh player-to-edge latency, edge capacity/load, and inter-edge latency between interacting players — [IFIP DL PDF](https://dl.ifip.org/db/conf/networking/networking2024/1570995709.pdf). Song et al., Computer Networks 2025: average 5G latency 37-150 ms depending on server location and operator — [UniPa PDF](https://iris.unipa.it/retrieve/60f478c1-7471-456e-9047-db7562447f84/1-s2.0-S0140366425003354-main.pdf).

### Inferences
- The measured literature now contradicts a common industry framing: Michaelides & Bellalta (simulation) and Tokey et al. (users) both find peeker's advantage is dominated by frame rate/defender latency, not server tick rate; Riot's own breakdown attributes only ~40 ms of 141 to tick+backbone. A design can therefore prioritise client frame pacing and defender-side buffering over chasing 128 Hz servers.
- Learned prediction pays off only at low update rates (≥300 ms): for a 20-60 Hz replicated game it is a bandwidth lever, not a latency lever.
- Rollback-for-physics progress (SnapNet, Easel, Quantum, Unity N4E) lives in products with limited public numbers; the academic record for 2023-2025 is empty, so claims like "no determinism required" are vendor claims.
- QUIC is being adopted at the edges (Hytale, Valve's QUIC-inspired ack vectors) but the dominant shipped transport remains custom UDP with reliability channels; Fiedler's per-stream HoL critique still stands for stream-based use, while RFC 9221 datagrams make QUIC viable as a secure UDP substrate.

### Gaps
- Michaelides & Bellalta full text was not accessible (verification interstitial); numbers are from the abstract.
- No academic paper on rollback netcode for 3D physics (2023-2025) was found; NetGames/MMSys 2025 proceedings were not indexed by the searches.
- No game-specific QUIC/WebTransport latency evaluation was found; only streaming evaluations.
- No official Hytale or DOOM Eternal netcode post was found; Hytale details come from community/hosting guides.
- No EA SEED netcode publication was found; the Ubisoft La Forge contribution is the Waterloo PDR paper.
- SpacetimeDB scaling (single node vs multi-node) is not stated in its FAQ.
- Croquet's official reflector/snapshot documentation page returned 404/403; the reflector description relies on the GitHub README and a secondary write-up.

## Key question 3: Underused or forgotten techniques worth reviving

### Takeaway
Most "forgotten" techniques are actually documented in detail in primary sources (Tribes' state-mask most-recent-state, Mauve's local-lag, Fiedler's authority sequence numbers, AoE's turn-length adaptation, EVE's time dilation, Croquet's reflector), each with at least one shipped or measured deployment; what is missing is library support, since engines settled on channel-based reliability, fixed input delay, single-owner authority and static tick rates.

### Cited Findings
- **Priority-scheduled most-recent-state with per-flag state masks and delivery notification (Tribes 2, 1999) [B]**: ghosting by scope, >20 state flags per object tracked independently, packets filled "first by status change, then by object priority", nothing retransmitted at the connection layer — [gamedevs.org PDF](https://www.gamedevs.org/uploads/tribes-networking-model.pdf). Fiedler's priority accumulator (2015) is the same idea for state sync — [gafferongames.com](https://gafferongames.com/post/state_synchronization/). Unreal Iris's dirty changemasks + priority scheduling are the closest modern engine implementation — [Epic docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/components-of-iris-in-unreal-engine); Halo: Reach built on it for 16 players — [Wolfire summary](https://wolfire-blog.appspot.com/2011/03/GDC-Session-Summary-Halo-networking).
- **Local-lag as a continuous tunable (Mauve et al. 2004) [B]**: delay local execution by roughly the network delay (20-150 ms) to remove short-term inconsistencies; 80-100 ms cited as unnoticeable; combine with timewarp for correctness; O(n²) timewarp fine below ~50 participants — [HHU PDF](https://publications.cs.hhu.de/library/Mauve2004a.pdf). The 2026 adaptive-time-delay studies show the modern payoff: adding delay only during interactions and **gradually** preserves fairness with better QoE — [WPI PDF](https://web.cs.wpi.edu/~claypool/papers/adaptive-fdg-26/paper.pdf). Rollback libraries expose only a fixed input-delay frame count — [Wikipedia: Netcode](https://en.wikipedia.org/wiki/Netcode).
- **Trailing State Synchronization (Cronin et al. 2002) [B]**: multiple simulation copies at staggered delays, roll the leading copy back to a trailing copy on disagreement, built for mirrored (multi-server) FPS architectures — [cronin-netgames02 PDF](https://www.eecg.utoronto.ca/~ashvin/courses/ece1746/2003/reading/cronin-netgames02.pdf). No current mainstream library implements TSS (inference from the library docs surveyed).
- **Replicated computation with a logic-less reflector (Croquet, 2001-present) [B/C]**: deterministic Model VMs on every client, reflector only timestamps and fans out messages, views unconstrained; end-to-end encryption possible because the server never inspects state — [Croquet tutorial](https://croquet.io/docs/croquet/tutorial-2_8_random.html); [GitHub croquet/croquet](https://github.com/croquet/croquet); [DLS 2020 keynote](https://conf.researchr.org/details/dls-2020/dls-2020-papers/10/Croquet-A-Unique-Collaboration-Architecture-Keynote-). Photon Quantum's input-relay server is the same topology with a commercial deterministic runtime — [Photon docs](https://doc.photonengine.com/quantum/current/getting-started/quantum-intro). Factorio's lockstep is the same topology with latency hiding — [FFF-83](https://factorio.com/blog/post/fff-83).
- **Aura/focus/nimbus interest management (MASSIVE, 1990s) [B]**: asymmetric perception (nimbus overlapping aura), vs the radius/grid AoI every engine ships; obstacle-aware IM measured at up to 6× fewer updates — [Boulanger 2006 PDF](https://www.sable.mcgill.ca/~clump/papers/boulanger-06-comparing.pdf); [Newcastle IM paper](https://research.ncl.ac.uk/game/research/publications/F6F6Ad01.pdf).
- **Delta encoding against an acked baseline with a short baseline window [A in Quake-lineage engines, B as a library primitive]**: Fiedler's 5-bit baseline offset (~0.5 s at 60 pps) and "order of magnitude" gain — [gafferongames.com](https://gafferongames.com/post/state_synchronization/).
- **Authority hand-off for interacting physics objects (Fiedler/Oculus 2018) [B]**: per-object authority and ownership sequence numbers, ownership outranks authority, host arbitrates, guest authority persists until confirmed; ~90 % perfect-prediction bit for ballistic objects; co-op only — [gafferongames.com](https://gafferongames.com/post/networked_physics_in_virtual_reality/). Photon Fusion's Shared mode offers single-owner-per-object with Transaction/Dynamic transfer policies (Dynamic has a cooldown) and warns cheating is possible — [Photon Fusion docs](https://doc.photonengine.com/fusion-core/v3/manual/ownership); [Fusion topologies](https://doc.photonengine.com/fusion-core/v3/getting-started/modes-and-topologies). Nakama relayed mode delegates arbitration to an elected client host — [Heroic Labs docs](https://heroiclabs.com/docs/nakama/concepts/multiplayer/relayed/).
- **Mission/physics host migration (Destiny, 2015) [B]**: separate cloud activity host so console physics-host migration is invisible — [GDC Vault](https://gdcvault.com/play/1022246/contactUs); [nessus42 gist](https://gist.github.com/nessus42/42c112d1f9eb3de147ab6e01439683da).
- **Turn-length adaptation (AoE, 2001) [B]**: communications turn ≈ RTT split into frames the slowest machine can run; 2-byte speed-control field; fast rise, slow decay — [Game Developer](https://www.gamedeveloper.com/programming/1500-archers-on-a-28-8-network-programming-in-age-of-empires-and-beyond). Photon Quantum's server "manages input latency" dynamically (claim) — [Photon docs](https://doc.photonengine.com/quantum/current/getting-started/quantum-intro).
- **Hash-based desync detection [A in lockstep engines; partial repair is B/C]**: AoE checksummed world/objects/pathfinding/targeting and halted the game on divergence — [Game Developer](https://www.gamedeveloper.com/programming/1500-archers-on-a-28-8-network-programming-in-age-of-empires-and-beyond); Rapier publishes snapshot hashes for cross-machine comparison — [rapier.rs JS](https://rapier.rs/docs/user_guides/javascript/determinism); the Bevy GGRS+Rapier demo has desync detection "(1v1 only)" — [GitHub](https://github.com/cscorley/bevy_ggrs_rapier_example). I found no source describing partial state repair after a detected desync (gap).
- **Smooth convergence via decaying error offsets (Source / Fiedler) [A]**: render-side position/orientation offsets decaying 0.95→0.85 per frame by error magnitude; Fiedler notes this is cheaper than smoothing the simulation — [gafferongames.com](https://gafferongames.com/post/state_synchronization/); Unity N4E ships `GhostPredictionSmoothingSystem` for the same purpose — [Unity docs](https://docs.unity3d.com/Packages/com.unity.netcode@1.4/manual/prediction.html).
- **Lockstep with speculative local execution ("latency hiding", Factorio) [B]**: a separate latency-state layer re-derived from the real state every tick; scoped to the player's own actions and a subset of interactions — [FFF-83](https://factorio.com/blog/post/fff-83); [FFF-302](https://direct.factorio.com/blog/post/fff-302).
- **Time dilation (EVE, 2011) [B]**: slow simulated time to bound server load, floor 10 %; 12.87 hours dilated in 12 days — [EVE Online](https://www.eveonline.com/news/view/introducing-time-dilation-tidi); [PC Gamer](https://www.pcgamer.com/eve-onlines-mad-time-dilation-tech-beats-lag/).
- **Learned extrapolation + robotics path tracking for remote entities [C]**: 45 % error reduction at 300-400 ms intervals — [Waterloo PDF](https://ece.uwaterloo.ca/~sl2smith/papers/2023TOG-Predictive_Dead_Reckoning.pdf).

### Inferences
- For a new library, the highest-leverage "revivals" are: (1) Tribes-style notification-based most-recent-state with per-field masks and a priority accumulator (replaces reliable channels for state), (2) a tunable local-lag/adaptive delay in the prediction layer, (3) Fiedler's authority/ownership sequence numbers for co-op physics, (4) hash checkpoints for rollback modes. Each has a primary source with a worked design and at least one shipped deployment.
- Croquet/Quantum/Factorio show the "relay + deterministic replicated simulation" topology is production-proven for 2-16 players; its cost is determinism discipline (random numbers, transcendental functions, physics stepping), which the Rapier docs and the Tentacle Tango postmortem (KQ4) both identify as the hidden cost.

### Gaps
- No source found for Hermite/Bezier entity interpolation beyond general knowledge (Fiedler's snapshot-interpolation article discusses Hermite interpolation; not re-fetched this session).
- No source found on "delta-encoding against multiple baselines" as a named technique beyond Fiedler's single-baseline window.
- No source found describing hashing-based desync detection **with partial state repair** in a shipped game.
- Normcore's ownership model was not found in search results; only Photon Fusion's docs were retrieved.
- Croquet's original TeaTime protocol (two-phase commit per a Future of Coding commenter) vs the current reflector could not be verified from primary docs.

## Key question 4: Developer ergonomics — how hard is netcode, rewrites, "what we'd do differently"

### Takeaway
There is no peer-reviewed study of netcode developer difficulty; the evidence is vendor research (Unity's 2020 survey of 200+ developers and 20 interviews) and postmortems, which consistently name determinism auditing, late retrofits of multiplayer, and underestimated scope as the main costs, while the one measured developer lesson set (AoE 2001) stresses metering and early modem testing.

### Cited Findings
- Unity's netcode research drew on "a survey of over 200 Unity users" about specific netcode frameworks and "over 20 in-depth interviews" with teams shipping multiplayer games; the data is from 2020 and Unity is a netcode vendor — [Unity blog](https://unity.com/blog/games/how-to-choose-the-right-netcode-for-your-game); [Unity report form](https://create.unity.com/form-netcode-report).
- Industry commentary: developers "often underestimate the scope of the networking problem" and prioritise core gameplay over multiplayer — [MCV/Develop](https://mcvuk.com/development-news/networking-opportunities/); an arena-shooter developer's post argues fast-paced networked games are hard to make fun (anecdotal) — [Game Developer](https://www.gamedeveloper.com/programming/making-fast-paced-multiplayer-networked-games-is-hard).
- Tentacle Tango: built rollback by hand, then moved to a GGPO-based approach; the hard part was auditing every system for determinism to produce identical results on two machines, which "took longer than we thought" (vendor blog, coherence.io) — [coherence.io](https://coherence.io/blog/tradecraft/tentacle-tango).
- Dino Party (Photon blog): going from local to online "meant rewriting large parts of the game"; chose dedicated servers on Fusion 2 — [Photon blog](https://blog.photonengine.com/dino-party-multiplayer-development/).
- KungFu Kickball: many iterations, started with a Photon plugin, researched lockstep (only deterministic games qualify) — [Game Developer](https://www.gamedeveloper.com/game-platforms/online-multiplayer-the-hard-way).
- Node Control (.io game) rejected rollback for discrete tile movement and reduced latency instead (Reddit snapshot, anecdotal) — [Reddit snapshot](https://reddit.sentinel-team.org/posts/1t2tmxb/snapshots/2026-05-09T03%3A16%3A32.277266Z).
- NetherRealm's MK X / Injustice 2 rollback migration (GDC 2017, Michael Stallone) is the best-known AAA netcode rewrite talk (secondary summary) — [Edgegap (secondary)](https://edgegap.com/blog/game-backend-deep-dive-mortal-kombat-x-injustice-2-rollback).
- AoE lessons (2001): consistent latency beats fast variable latency; filter command spam; "metering is king" and removing it early hid problems; educate single-player programmers that commands can be delayed or rejected; verify third-party "guaranteed delivery" claims; test on modems as a first-class activity — [Game Developer](https://www.gamedeveloper.com/programming/1500-archers-on-a-28-8-network-programming-in-age-of-empires-and-beyond).
- Godot-specific friction: rollback physics required a pending PR for manual physics stepping because neither Godot Physics nor Jolt exposes it — [80.lv](https://80.lv/articles/rocket-league-inspired-physics-network-game-prototype-in-godot). Rapier documents that `simd8` and `enhanced-determinism` are mutually exclusive and that math must route through `ComplexField` — [rapier.rs](https://rapier.rs/docs/user_guides/rust/determinism/).
- Unity N4E documents the runtime cost of prediction (≈22 resimulated frames per frame at 300 ms) and marks `PredictedGhost.ShouldPredict` as legacy, a sign of API churn in prediction APIs — [Unity docs](https://docs.unity3d.com/Packages/com.unity.netcode@1.4/manual/prediction-n4e.html).
- A general game-bug study notes large studios' complex systems "may tend to suffer more from issues due to networking", citing the "What Went Wrong" bug taxonomy — [core.ac.uk PDF](https://core.ac.uk/download/161455971.pdf).

### Inferences
- The recurring ergonomic failure is choosing a model late: rollback demands determinism (random, float math, physics stepping) that cannot be retrofitted cheaply, while state-sync demands quantisation/priority/smoothing plumbing that is tedious but incremental. A library that makes the model choice explicit at project start, and that ships determinism linting/hash checkpoints, addresses the most-cited pain.
- Metering (AoE) and desync hashing (AoE, Rapier) are the two tools every postmortem implicitly wishes it had earlier.

### Gaps
- No peer-reviewed empirical study of netcode bugs or developer difficulty was found (searches of "empirical study multiplayer game networking bugs" returned only a general game-bug paper).
- No "It Takes Two"/Hazelight networking talk was found; only design interviews.
- No single postmortem explicitly titled "what we'd do differently" about netcode was found; lessons are assembled from several blogs, two of them on vendor sites (coherence.io, Photon) with commercial interest.
