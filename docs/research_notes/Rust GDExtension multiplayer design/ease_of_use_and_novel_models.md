# Developer experience of multiplayer: transparent programming models, developer pain, testing ergonomics and novel ideas

Research notes written 2026-11-08. Every web source was read on that date unless a different date is given in the finding. "Accessed" dates refer to the fetch; publication dates are given where the page states one. Where a page did not say something, that is recorded as a gap rather than filled in from memory.

Scope note: this researcher covered the ease-of-use side (programming models, pain evidence, testing/debugging tooling, ideas for a new library). Adjacent researchers cover the Rust/GDExtension toolchain and the protocol-level comparison of libraries; those are only touched where they bear on ergonomics.

## Key question 1: Which "transparent multiplayer" programming models exist, how do they make networking feel like single-player development, and where does the illusion break?

### Takeaway
Four families of "transparent" model recur in the primary docs: (a) deterministic replicated computation with input-only networking (Croquet/Multisynq, Photon Quantum, Factorio lockstep, GGRS/netfox rollback), where the developer writes one simulation and the system never serialises state; (b) declared-state replication with authority rules (Unreal `Replicated`, Fusion `[Networked]`, Colyseus Schema, Godot MultiplayerSynchronizer, Normcore datastore), where the developer marks what replicates and the system diffs it; (c) distributed/automatic ownership of physics or objects (Roblox network ownership, Fusion Shared Mode, Normcore ownership); and (d) "the server is a database" (SpacetimeDB reducers over tables with client subscriptions). Each primary source states its own breaking points: determinism rules and "any code change = new session" (Croquet), fixed-point/no-float and 128-player caps (Quantum), unverifiable client physics (Roblox), 63-field and silent-drop rules (Colyseus), auto-property-only weaving and lost boolean changes (Fusion), same-NodePath and "declare every RPC on both sides" (Godot), and "rollback, physics, collisions are not helped" (SpacetimeDB critics).

### Cited Findings

**Croquet / Multisynq (deterministic replicated computation, reflector orders messages, no server code)**
- Croquet "lets you build real-time multiuser apps without writing server-side code"; the shared logic runs on each device inside a synchronized virtual machine. Reflectors are "simple, stateless message-passing servers that handle event ordering, synchronized time ticks, and no application logic". Every event that passes through the reflector is timestamped; model events are handled locally by each replica, whose only clock is simulation time set by the reflector — [Multisynq Core API Reference](https://docs.multisynq.io/api-reference); [croquet/croquet GitHub: "Client-side (!) Multiplayer for JavaScript"](https://github.com/croquet/croquet); [@croquet/croquet on npm](https://www.npmjs.com/package/@croquet/croquet)
- Model rules: "The model must be self-contained and deterministic. The view may read model state but must not write to it; external changes arrive as published events. The model must be serializable, and you cannot use async code in the model." The reflector is available as a Node.js package for self-hosting — [Multisynq Core API Reference](https://docs.multisynq.io/api-reference); [croquet/croquet GitHub](https://github.com/croquet/croquet)
- The Multiblaster tutorial shows the developer-facing shape: `Croquet.Model` subclasses hold shared state ("The 'model' is the part that is synchronized by Croquet for all users"); the view publishes `this.publish(this.viewId, "left-thruster", true)` and the model subscribes `this.subscribe(viewId, "left-thruster", this.leftThruster)`; the game loop is `this.future(50).mainLoop()` ("Future messages are how you define an object's behavior over time in Croquet"); "All communication is only between the local view and the shared model." Positions "do not need to be transmitted via the network"; "No special data structures need to be used." The networked version "has only 20 lines more than the non-Croquet one from step 0" (about 80 lines). "Croquet automatically snapshots the model data and keeps that session state even when everyone leaves the session." — [Croquet Multiblaster Tutorial](https://croquet.github.io/multiblaster-tutorial/)
- Stated gotchas of the model: "whenever we change the model code, a new session is created, even it has the same name" (old state becomes inaccessible unless kept via `persistSession()`); the view must smooth, because relying on the reflector's tick timing "would make the timing depend very much on the steadiness of ticks from the reflector"; view-only data (smoothed render positions) must live in the view (the tutorial uses a `WeakMap`); pub/sub is not a way to sync values across devices, only the model state is synchronized — [Croquet Multiblaster Tutorial](https://croquet.github.io/multiblaster-tutorial/)
- Multisynq also ships a React binding (`react-together`, e.g. a `useIsSynchronized` hook that signals when the local session has caught up to the reflector, "useful for hiding loading screens") — [Multisynq Docs: useIsSynchronized](https://docs.multisynq.io/react-together/hooks/use-is-synchronized)
- A third-party integration for Rogue Engine describes Croquet as providing "serverless networking" — [BeardScript/RogueCroquet](https://github.com/BeardScript/RogueCroquet)

**Photon Quantum (write the deterministic simulation once; the engine does prediction/rollback)**
- Quantum 3 is "a high-performance deterministic ECS (Entity Component System) framework" for Unity, for up to 128 players; game code is "an isolated, pure C# simulation" decoupled from Unity; game state lives in blittable, memory-aligned structs on a custom heap; gameplay logic runs in stateless Systems operating on a `Frame` — [Photon Quantum 3 Intro](https://doc.photonengine.com/quantum/current/quantum-intro)
- "In deterministic systems, game clients only exchange player input with the simulation running locally on all clients." Clients predict locally and a rollback system restores and re-simulates mispredictions; a game-agnostic authoritative server on Photon's cloud synchronizes clocks and manages input latency. "The developer defines the player inputs which will be distributed to all clients"; developers write no other networking code; "Clients never need to wait for a slower client or a client with a worse network connection." — [Photon Quantum 3 Intro](https://doc.photonengine.com/quantum/current/quantum-intro)
- Communication is defined in both directions: Input (every tick), Commands (occasional actions), Events (simulation → Unity view); Unity can observe the full simulation state. The simulation "allocates no C# heap memory at runtime and creates no garbage"; the stated goal is to "leave most of the CPU budget for the view/rendering code" — [Photon Quantum 3 Intro](https://doc.photonengine.com/quantum/current/quantum-intro)
- Trade-off made visible in the examples: only fixed-point types (`FP`, `FPVector3`) appear; the intro page does not state a rule against floats, but a third-party debugging guide attributes checksum mismatches to floating-point math varying across hardware and RNG not drawn from the frame's deterministic source, and recommends Quantum's fixed-point types — [Photon Quantum 3 Intro](https://doc.photonengine.com/quantum/current/quantum-intro); [bugnet.io: how to fix Quantum simulation desync](https://bugnet.io/blog/how-to-fix-quantum-simulation-desync-from-nondeterministic-code)

**Photon Fusion (declared `[Networked]` state; Shared vs Host/Server authority)**
- Networked Properties are declared by adding `[Networked]` to an auto-property of a `NetworkBehaviour`; Fusion generates IL that links the getter/setter to the Network Object's state buffer. "DO NOT implement these properties yourself - leave them as auto-properties." Example: `[Networked] public float Health { get; set; }`. Writes should happen in `FixedUpdateNetwork()`, which "ensures they will behave correctly with client prediction". Supported: blittable primitives and Unity structs, enums, user structs/`INetworkStruct`, `NetworkString<_N>`, `NetworkBool`, `TickTimer`, `PlayerRef`, `NetworkArray/Dictionary/LinkedList` with `[Capacity]`, fixed unsafe buffers, `NetworkObject`/`NetworkBehaviour` references (converted to ids; "References are not valid in `INetworkStruct`"). Gotchas: booleans can lose changes ("often recommended to use an int instead of bool"); generic networked properties are invalid; hand-written accessors break weaving — [Fusion 2: Networked Properties](https://doc.photonengine.com/fusion/current/manual/data-transfer/networked-properties)
- Topologies: Dedicated Server (`GameMode.Server`) has "full and exclusive State Authority over all objects", clients change state only via input or RPC requests, no NAT punching needed, cost is "spinning up complete Unity instances for every game session" (Photon does not host server builds). Client Host: built-in UDP NAT punch-through with relay fallback, which "happens to roughly 1 in 10 players"; "A rogue host can cheat." `GameMode.Single` runs the same code locally with no connection. Shared Authority (`GameMode.Shared`): each client "initially has State Authority over objects they spawn" and can release it; "The Photon Room controls changes of state authority and holds a complete copy of the networked state"; described as PUN-like but "more feature-rich, faster, and has no run-time allocation overhead" — [Fusion 2: Network Topologies](https://doc.photonengine.com/fusion/current/manual/network-topologies)

**Normcore (datastore + ownership, no custom server)**
- "Normcore uses a datastore to track all state in a room." It "provides an API that makes the most common server-authoritative operations possible without deploying a custom server or server plugin." Models start with `ownerID = -1` (no owner, anyone may write); "when a model is owned by a client, the server only lets the owning client make changes to it or to any of its child models"; "the ownership settings of a parent are enforced on all children". `RequestOwnership()`/`ClearOwnership()` "take effect immediately", but if the server blocks the request "then ownership and all changes that required ownership will be rolled back". `preventOwnershipTakeover` makes the server deny ownership changes unless the object has no owner. Lifetime flags (`destroyWhenOwnerOrLastClientLeaves`) are enforced by the server, "the server will always ensure lifetime flags are honored", and client-side cleanup is discouraged because "there's no guarantee they will run successfully" — [Normcore: Ownership and Lifetime Flags](https://docs.normcore.io/room/ownership-and-lifetime-flags)
- Transport is WebRTC (which enables web builds/spectating); rooms typically hold 4–100 players; "VR apps use roughly 5 to 10 times the bandwidth of a typical FPS or racing game"; data is encrypted — [Normcore: Common Questions](https://docs.normcore.io/essentials/common-questions)

**Roblox (everything physics-owned is replicated; automatic network ownership)**
- Physics is distributed: by default "the server retains ownership of any BasePart", but the engine assigns simulation to clients based on hardware and proximity ("parts close to a player's character are more likely to become player-owned"); anchored parts always stay with the server. Developers can override with the server-side `BasePart:SetNetworkOwner()` and return to automatic with `SetNetworkOwnershipAuto()` (the doc's vehicle example gives the driver ownership). `SetNetworkOwner(nil)` to keep an object on the server "may result in jittery physics interactions for clients" — [Roblox: Network Ownership](https://create.roblox.com/docs/physics/network-ownership)
- Where the illusion breaks: Roblox "cannot verify physics calculations when a client has ownership over a BasePart", so a client can teleport parts or move them through walls; a client can "fire Touched events on a BasePart it owns and send it to the server" even if nothing was touched, so Touched-driven damage must be validated server-side. Studio visualises ownership by outline colour (green = your client owns it, red = buffer zone that may be rejected, white/grey = server or another client, black = no owner, physics not applied) — [Roblox: Network Ownership](https://create.roblox.com/docs/physics/network-ownership)

**Colyseus (server-defined Schema with automatic patches)**
- "A field is synchronized when it is declared: with a `t.*` builder, or with a `@type()` decorator"; plain class properties are not serialized. Clients receive "tick patches" and late joiners a "full state sync". Delivery tuning: `.noSync()`, `.unreliable()`, `.patchOnly()`, `.fullStateOnly()`; `.quantized()`/`.angle()` encode floats in 8/16/32 bits; `.view(tag?)` makes a field visible only through a client's StateView (interest management) — [Colyseus: Schema](https://docs.colyseus.io/state/schema)
- Limits/gotchas: "A `Schema` type may hold up to 63 synchronizable properties" (inherited and deprecated fields count; nest a child schema to exceed it); `.unreliable()` works only on experimental WebTransport (on WebSocket the field is sent once then freezes, with a warning); writes to `.fullStateOnly()` fields after a client joins "are silently dropped"; quantization is lossy and the wrong mode is "a real bug"; in C#, mutating a MapSchema during enumeration throws; Schema is for room state and client input, not one-off messages — [Colyseus: Schema](https://docs.colyseus.io/state/schema)

**Godot high-level multiplayer (`@rpc`, authority, MultiplayerSynchronizer)**
- Each node has a `multiplayer` property referencing a `MultiplayerAPI`; networking starts by creating a peer (`ENetMultiplayerPeer`), `create_server()`/`create_client()`, and assigning `multiplayer.multiplayer_peer`; setting `OfflineMultiplayerPeer` terminates networking. "The server's ID is always 1, and clients are assigned a random positive integer." Authority "is the server by default, but can be changed per-node using" `Node.set_multiplayer_authority`. The default annotation is `@rpc("authority", "call_remote", "reliable", 0)`; `"any_peer"` is suggested for "transferring user input"; `"call_local"` is "useful when the server is also a player"; reliable mode has "a significant performance penalty" — [Godot docs: High-level multiplayer](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)
- Breaking points stated by the docs: "the sending and receiving node need to have the same `NodePath`" (use `force_readable_name = true` with `add_child()`); "all RPCs must be declared on both the client scripts and the server scripts", even unused ones, because signatures are checksummed (annotation, function, return type, NodePath; "Function arguments are not checked for matching"); mismatches "may print an error or cause unwanted behavior" and the error may not point to the RPC being edited; "RPC methods must be defined on Node-derived classes"; "RPCs will not serialize Objects or Callables"; the API "only uses UDP"; the HTML5 platform lacks some high-level features; the sample code is not designed for a dedicated server; gameplay is not secured automatically (treat "all client input as untrusted") — [Godot docs: High-level multiplayer](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)
- The high-level-multiplayer page does not itself document MultiplayerSpawner/MultiplayerSynchronizer's inspector "pick properties" replication config; the GitHub tracker holds the user-facing friction with it (see Key question 2) — [Godot docs: High-level multiplayer](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)

**netfox (Godot add-on: "prediction as a node", rollback with state/input properties)**
- netfox's core "implements timing, rollback and other multiplayer features", with "Lag compensation with Client-side Prediction and Server-side Reconciliation" and "Smooth motion with easy-to-use interpolation"; `netfox.noray` handles connectivity (the free hosted noray is "not recommended for shipping games"); Godot 4.x supported, C# "experimental"; a "Godot Rocket League" example "Demonstrates netfox's physics rollback capabilities" — [foxssake/netfox GitHub](https://github.com/foxssake/netfox); [netfox docs index](https://foxssake.github.io/netfox/latest/)
- RollbackSynchronizer is added as a child of the node it manages ("Root will most often be the RollbackSynchronizer's parent node"); "State properties are recorded for each tick and restored during rollback" ("For state, the server is the ultimate authority"); "Input properties are gathered for each player and sent to the server to use for simulation" (input nodes owned by their players); "Enable input broadcast" defaults on for legacy reasons, turning it off "lowers bandwidth and reduces the cheating surface". The developer implements `_rollback_tick(delta, tick, is_fresh)`; `is_fresh` is true the first time a tick is processed, to avoid replaying sounds/animations. Diff states vs full states are configurable (full-state interval, diff-ack interval; diffs computed only against ticks the receiver acknowledged; full-state acks on a reliable channel, diff acks unreliable). Limits: "It is not recommended to have both state and input properties on the same node"; changing configuration after instantiation is not recommended and needs `process_settings()`; authority changes need `process_authority()` "on all peers at the same time" — [netfox docs: RollbackSynchronizer](https://foxssake.github.io/netfox/latest/netfox/nodes/rollback-synchronizer/)
- Short netfox snippet from the docs (the single-player movement body, wrapped by the rollback machinery):
  ```gdscript
  func _rollback_tick(delta, tick, is_fresh):
      velocity = input.movement.normalized() * speed
      velocity *= NetworkTime.physics_factor
      move_and_slide()
      velocity /= NetworkTime.physics_factor
  ```
  (the `physics_factor` multiply/divide is the physics caveat the docs defer to a "Rollback caveats" tutorial) — [netfox docs: RollbackSynchronizer](https://foxssake.github.io/netfox/latest/netfox/nodes/rollback-synchronizer/)

**GGRS (Rust rollback, request-based API)**
- GGRS is "a reimagination of the GGPO network SDK written in 100% safe Rust"; "Instead of registering callback functions, GGRS returns a list of requests for the user to fulfill"; examples include sync-test and spectator demos; WASM via matchbox (WebRTC) sockets behind a feature flag; "fairly stable"; a Godot wrapper "is being developed by a third party"; the hosted matchmaking server for the demos is offline — [gschup/ggrs README](https://raw.githubusercontent.com/gschup/ggrs/main/README.md)

**SpacetimeDB (server = reducers over tables; clients subscribe)**
- Server logic is split across "reducers, procedures, and views"; data is defined with "tables, columns, and indexes"; subscriptions "Enable real-time data synchronization with clients"; quickstarts exist for Rust, C#, C++ and TypeScript modules; modules can be mounted as submodules; local standalone mode runs on port 3000 ("SSL is not supported in standalone mode"). The page maps its concepts for Convex users (mutations → reducers, actions → procedures, queries → views/subscriptions) — [SpacetimeDB: Getting Started](https://spacetimedb.com/docs/)
- Reducers are deterministic and isolated; failed work is rolled back; they "cannot perform arbitrary I/O during execution"; "Because reducers are deterministic (no I/O, no clock reads, no randomness), aborting them is practically free". "Replication does not increase the rate at which one database can execute contending write transactions because those transactions still pass through one ordered execution stream." Clockwork Labs scheduled two scaling features for 31 Oct (2026) — [RuntimeWire: SpacetimeDB scaling plan](https://runtimewire.com/article/spacetimedb-october-31-scaling-plan-single-thread); [ecosistemastartup analysis](https://ecosistemastartup.com/spacetimedb-por-que-escalar-oltp-no-es-solo-sumar-servidores/)
- Critic's view (Hacker News, mirrored thread): "the actual hard parts about building a multiplayer game, such as roll back, physics, collisions, all of that sort of stuff, well this actually doesn't really help with any of that. If anything it makes all of those things even more difficult"; "The database itself also doesn't horizontally scale beyond a single node." A SpacetimeDB developer replied: "Reliability, provable correctness, and ease of integration are higher priority than performance." — [HN thread 49378933 (mirror)](https://hn.nuxt.dev/item/49378933)
- Issue-tracker signal: 2,173 issues total; the most-commented are about language support and tooling (Golang support 19 comments, "C# intellisense not working" 18, QUIC transport request 16, "Where is ReducerContext?" 14, "CSharp quickstart does not compile" 14, Windows install error 13) rather than gameplay networking — GitHub REST search `repo:clockworklabs/SpacetimeDB is:issue`, sorted by comments, run 2026-11-08 via `gh api` (data not at a single URL; tracker at https://github.com/clockworklabs/SpacetimeDB/issues)

**Ambient (Rust/WASM, server-authoritative ECS with automatic networking)**
- The main repo now carries a warning that work on the Ambient runtime "is paused indefinitely" and the team is working on a separate project (Braindump); the repo describes Ambient as "an open-source cross-platform runtime and platform for building, deploying and sharing high-performance multiplayer games"; Rust was the only supported guest language and the project was alpha. A 2025 r/rust comment attributed to the developer says the company is shut down (single comment, unconfirmed by an official announcement) — [AmbientRun/Ambient](https://github.com/AmbientRun/Ambient); [r/rust thread, Oct 2023 (mirror)](https://redlib.hbubli.cc/r/rust/comments/16znx7x/ambient_ship_multiplayer_games_in_rust_in_minutes)

**Factorio (deterministic lockstep; what breaks it)**
- "all of the players need to simulate every single tick of the game identically"; "If any computer does something ever-so-slightly different, a desynchronization (desync) occurs"; the affected player must reconnect and re-download the map. "Unfortunately making a fully deterministic game is not easy" — [Factorio FFF-188 "Bug, Bug, Desync" (2017)](https://factorio.com/blog/post/fff-188)
- In FFF-415 (June 2024) a desync reproducible only on some machines turned out to depend on CPU core count; the developer recreated it by pretending the machine had fewer cores; four interacting factors exposed a threading-determinism bug present since 2017 — [Factorio FFF-415](https://direct.factorio.com/blog/post/fff-415)

**Valheim (ZDO object sync, 10-player cap)**
- Iron Gate's 1.0 FAQ: "Just like it is now, Valheim 1.0 will be a game for 1-10 players". Community analysis (James A. Chambers) found hard-coded send and receive rate limits in the ZDO manager that mods can raise, and "noticeable performance degradation approaching 5-6 simultaneous players". The article author (Edgegap, partly promotional; its own interpretation, not Iron Gate's) claims every entity is a ZDO and that a changed object is re-sent whole rather than by field, so bandwidth grows with active ZDOs; crossplay routes through Azure PlayFab Party relays and Iron Gate's docs warn crossplay players are more likely to see lag/timeouts; BepInEx mods hook the Steam networking layer and so do not load under crossplay — [Edgegap: Valheim multiplayer backend deep dive](https://edgegap.com/blog/valheim-multiplayer-game-backend-deep-dive)

### Inferences
- The two models that get closest to "write single-player code" are deterministic replication (Croquet, Quantum, netfox rollback) and declared-state replication with sensible default authority (Fusion Shared Mode, Normcore, Roblox). The former hides *all* state serialisation but imposes determinism discipline and a model/view split; the latter hides authority bookkeeping but leaks through "who may write" rules (Normcore rollbacks of rejected writes; Fusion's `FixedUpdateNetwork()` requirement; Roblox's unverifiable client physics).
- Every "transparent" system still needs the developer to understand one concept pair: Croquet model/view, Quantum simulation/view, netfox state/input, Fusion state authority/input authority, Godot authority/any_peer. A new library can pick one pair and name it consistently rather than exposing several.
- Croquet's "20 lines more than single-player" claim and netfox's `_rollback_tick` body being the ordinary movement code are the two concrete existence proofs that single-player-shaped gameplay code can be networked by a framework; both achieve it by owning the game loop (future messages / tick callbacks) rather than by intercepting arbitrary writes.
- SpacetimeDB and Colyseus are the "server-is-the-schema" branch: excellent for persistence/lobby/inventory-style state (transactions, subscriptions, delta patches) and, per their own critics and limits, not for tick-rate physics or rollback.
- Ambient's indefinite pause is a caution that a full engine+runtime bundling of automatic networking is a large bet; a library that attaches to an existing engine (Godot) avoids that risk.

## Key question 2: What do developers actually struggle with (forums, issue trackers, postmortems, surveys)?

### Takeaway
Quantified evidence from issue trackers (counted 2026-11-08) shows the same themes everywhere: spawn/parenting ordering and "node/object not found" races, transform syncing/teleport/interpolation jitter, host-vs-client asymmetries (SyncVar hooks on host, "call_local" surprises), late-join state, and prediction/physics double-application. Godot's most-commented open multiplayer proposal asks for exactly "property prediction and interpolation" (27 comments) and returning values from RPCs (25). I found no academic or industry survey quantifying which parts of multiplayer are hardest; the one survey found says ~7 in 10 studios (of ~300 respondents, 2023) develop multiplayer, which is prevalence, not difficulty.

### Inferences
- Across five trackers the single most common high-engagement theme is *object lifecycle ordering*: spawn with a parent, re-parent, teleport, pooled objects missing callbacks, scene changes mid-replication, late join. A library whose spawn/parent/visibility model is atomic and ordered (one message that creates, parents and initialises before any RPC can target the object) would remove the largest class of reported pain.
- The second theme is *transform/physics sync quality*: jitter at non-60 Hz refresh, forces applied twice under client-side prediction, RigidBody rollback. These are the areas where "prediction as a flag" must be paired with a tick-decoupled interpolation layer and clear physics guidance (netfox's `physics_factor` caveat shows the leak even in a dedicated rollback add-on).
- The third theme is *host/client asymmetry*: SyncVar hooks firing differently on host, `call_local` surprises, `is_server` semantics. "Offline mode is just a loopback peer" and "the host is just a client of itself" address this at the model level.
- Godot users explicitly ask the engine for prediction/interpolation (#7280), RPC return values (#2032), struct RPC arguments (#6216), manual property sync (#9406), a `@sync` annotation without inspector exposure (#8662), and an entity/authority node (#12217). These are a ready-made feature list for a GDExtension aiming at ease of use.
- Netcode postmortems of the named indie hits are not where the evidence is; the trackers and forums are far richer and quantifiable.

### Gaps
- No academic or industry survey with percentages on multiplayer difficulty was found (searches returned only prevalence data and anecdotes).
- No GDC talk or developer interview on a netcode rewrite was found for Among Us, Fall Guys, Valheim, Lethal Company, Content Warning, Deep Rock Galactic, Risk of Rain 2, Palworld or Enshrouded in this research; Deep Rock Galactic and Valheim results were player forum threads only. The claim that Lethal Company uses NGO is supported only indirectly (the modding weaver's stated purpose).
- Reddit thread counts for r/gamedev / r/godot multiplayer questions were not measured (Reddit was reachable only via mirrors in search results).
- Mirror's LatencySimulation and Discord discussions were not examined.

## Key question 3: What testing and debugging ergonomics exist (multi-instance launch, network-condition simulation, replay/desync diagnostics, profilers, automated tests)?

### Takeaway
Engines now ship multi-instance launch (Godot "Customize Run Instances" with per-instance args and feature tags; Unity Multiplayer Play Mode with up to 4 players in Unity 6; Unreal PIE with Network Emulation presets and per-direction lag/loss/jitter/reorder/duplication). Desync diagnostics are the mature part of the deterministic world: Factorio's per-tick CRCs and server/client state diffs, Quantum's checksum-bearing replays and system-bisection recipe, GGRS sync-test sessions. No source fetched describes a general-purpose time-travel debugger for networked state; netfox has a "Rollback Debugger" example.

### Cited Findings
- Godot: "Customize Run Instances" runs several copies at once, "especially useful when building and debugging multiplayer games"; "Enable Multiple Instances" with an instance count; Main Run Args and Main Feature Tags passed to every instance unless overridden; per-instance Launch Arguments and Feature Tags; user args read with `get_cmdline_user_args` must start with `--` (and combining fields "can produce unexpected results") — [Godot docs: Overview of debugging tools](https://docs.godotengine.org/en/stable/tutorials/scripting/debug/overview_of_debugging_tools.html)
- Unity: "Multiplayer Play Mode (MPPM) enables you to test multiplayer functionality without leaving the Unity Editor"; "You can simulate up to four Players (the Main Editor Player plus three Virtual Players) simultaneously"; requires "Unity 6 and later", Windows and Mac — [Unity MPPM 1.4 manual](https://docs.unity3d.com/Packages/com.unity.multiplayer.playmode@1.4/manual/index.html). NGO's testing-locally guide lists MPPM and third-party ParrelSync ("run two instances of the same Unity project simultaneously"); on macOS multiple app instances need `open -n YourAppName.app` — [NGO: Testing locally](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.8/manual/tutorials/testing/testing_locally.html); coherence's guide notes MPPM "can be more resource demanding than other solutions" — [coherence docs: Multiplayer Play Mode](https://docs.coherence.io/1.3/getting-started/setup-a-project/local-development/multiplayer-play-mode)
- Unreal Network Emulation: "simulates lag and packet loss for servers and clients"; settings `PktLag`, `PktLagVariance`, `PktLagMin/Max`, `PktJitter`, `PktLoss`, `PktIncomingLoss`, `PktOrder`, `PktDup`; per-direction incoming/outgoing min/max latency and loss; presets "Custom, Average, and Bad"; enabled under Editor Preferences > Play > Multiplayer Options, or via command line, console (`NetEmulation.<SETTING>`) or `[PacketSimulationSettings]` in ini; recommends testing at "500 round trip ping" and "10% packet loss or higher"; constraints: `PktLag` cannot be used with `PktOrder` — [Unreal: Using Network Emulation](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-network-emulation-in-unreal-engine)
- Normcore has its own "testing multiplayer locally" guide — [Normcore: Testing multiplayer locally](https://docs.normcore.io/guides/testing-multiplayer-locally) (not fetched; listed in search results)
- Factorio: desync report = server and client game state, diffed by developers; fast heuristic CRC per tick in normal play, full-state CRC per tick when hunting; a debug branch tagging saves with human-readable markers; reproduction steps valued above reports — [FFF-188](https://factorio.com/blog/post/fff-188); [FFF-55](https://factorio.com/blog/post/fff-55); the 2024 bug was reproduced by faking a lower core count — [FFF-415](https://direct.factorio.com/blog/post/fff-415)
- Photon Quantum: replays can store checksums alongside inputs (`includeChecksums` on export in Quantum 3; `RecordingFlags` in Quantum 2); running a replay needs the application build, game assets and the replay file; the Quantum 3 replay guide shows starting checksum verification in code so mismatches are logged; the Quantum 1 wiki recommends saving per-step checksums and diffing logs from two clients; the FPS Template guide describes bisecting the system list by comparing checksums at the midpoint to find the first diverging system, and recommends finding a desync that reproduces quickly; Photon advises against using checksums to catch cheaters in live games; a `ChecksumErrorFrameDump` class exists in the Quantum 3 API — [Quantum 3: Replay](https://doc.photonengine.com/quantum/current/manual/replay); [Quantum FPS Template: Miscellaneous](https://doc.photonengine.com/quantum/current/fps-template/miscellaneous); [Quantum 1 wiki: debugging desyncs](https://doc.photonengine.com/quantum/v1/community-wiki/knowledge-base/debugging_desyncs); [Quantum 2: Cheat protection](https://doc.photonengine.com/quantum/v2/manual/cheat-protection); [Quantum 3 API: ChecksumErrorFrameDump](https://doc-api.photonengine.com/en/quantum/current/class_photon_1_1_deterministic_1_1_checksum_error_frame_dump.html)
- GGRS ships "sync-test demos" and spectator demos alongside its P2P sessions — [gschup/ggrs README](https://raw.githubusercontent.com/gschup/ggrs/main/README.md)
- netfox's examples include a "Rollback Debugger" and a "Comparison sample" (a naive port vs a netfox port of a single-player demo) — [foxssake/netfox GitHub](https://github.com/foxssake/netfox)
- Roblox Studio visualises network ownership with coloured outlines (green/red/white-grey/black) — [Roblox: Network Ownership](https://create.roblox.com/docs/physics/network-ownership)

### Inferences
- The baseline for "ease of use" testing in 2026 is: one-click N instances with per-instance roles, and in-editor latency/loss/jitter presets. A Godot library can rely on the engine's run-instances dialog for the former and should supply the latter itself (Godot's docs page shows no network emulation feature).
- Desync tooling has a well-trodden recipe worth copying even for non-lockstep libraries: per-tick cheap hash + optional full hash, recorded inputs + checksums = replay, bisection by system/node to find the first diverging piece, and a fake-environment switch (core count, refresh rate) to reproduce machine-dependent bugs.
- FishNet #293 ("jitter when refresh rate isn't 60 Hz") suggests a test matrix should include non-60 Hz frame rates and host-vs-client roles, not only network conditions.

### Gaps
- Unreal's PIE net modes (number of players, run under one process) were not on the fetched page; Unity's Network Profiler, Unreal Network Insights, Mirror/FishNet stats windows, Mirror LatencySimulation, lightyear's deterministic tests and the mechanics of GGRS `SyncTestSession` (checksum/resimulation) were not confirmed from primary sources in this research.
- No source describing a time-travel debugger for networked game state was found.

## Key question 4: Which concrete novel ideas are worth adopting in a library whose goal is "as close to single-player as possible, ease of use first, best of the popular libraries"?

### Takeaway
The primary sources above support a short list of mechanisms with evidence behind them: own the tick loop and make prediction a node/flag (netfox, Fusion), keep gameplay code deterministic-by-construction where possible and detect divergence with cheap per-tick hashes (Factorio, Quantum, GGRS), make spawn+parent+init atomic and ordered (the dominant issue theme), give the host no special code path (Fusion `GameMode.Single`, Godot `OfflineMultiplayerPeer`), use a datastore/schema model for non-realtime state (Colyseus, Normcore, SpacetimeDB), supply ownership visualisation (Roblox Studio), ship network-condition presets and multi-instance roles (Unreal, Godot), and expose a single authority concept with server-enforced writes and rollback of rejected writes (Normcore).

### Cited Findings (each idea with the evidence that motivates it)
- **Prediction as a node/flag with state/input property lists**: netfox RollbackSynchronizer records state per tick, gathers inputs per player, and calls `_rollback_tick(delta, tick, is_fresh)` on rollback-aware nodes; the developer's tick body is ordinary movement code — [netfox: RollbackSynchronizer](https://foxssake.github.io/netfox/latest/netfox/nodes/rollback-synchronizer/). Fusion's `[Networked]` auto-properties plus "write in `FixedUpdateNetwork()`" give correct prediction behaviour — [Fusion: Networked Properties](https://doc.photonengine.com/fusion/current/manual/data-transfer/networked-properties). Godot users asked the engine for exactly this (#7280, 27 comments) — [godot-proposals #7280](https://github.com/godotengine/godot-proposals/issues/7280)
- **"Offline mode is just a loopback peer"**: Fusion's `GameMode.Single` "runs the same code locally without an external connection" — [Fusion: Topologies](https://doc.photonengine.com/fusion/current/manual/network-topologies); Godot's `OfflineMultiplayerPeer` is the documented way to terminate networking while keeping the API — [Godot: High-level multiplayer](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)
- **Atomic, ordered spawn/parent/initialise before any message can target the object**: motivated by the most-commented issues in NGO (#3653, #46, #40), Mirror (#1853, #72), FishNet (#435, #273), Godot (#68407, #101847) and the "RPC before node exists" forum race — [NGO issues](https://github.com/Unity-Technologies/com.unity.netcode.gameobjects/issues); [Godot forum: ENet synchronization errors](https://forum.godotengine.org/t/enet-synchronization-errors/91231)
- **Declare once, with a `@sync`-style annotation rather than inspector lists**: Colyseus syncs a field "when it is declared" with a type builder/decorator — [Colyseus: Schema](https://docs.colyseus.io/state/schema); Godot users asked for "a @sync annotation to synchronize properties without exposing them in the inspector" (#8662) and for manual property syncing (#9406) — [godot-proposals, topic:multiplayer](https://github.com/godotengine/godot-proposals/issues?q=label%3Atopic%3Amultiplayer)
- **Server-enforced authority with automatic rollback of rejected writes, parent ownership inherited by children**: Normcore's server "only lets the owning client make changes" and rolls back blocked ownership requests "and all changes that required ownership"; parents' ownership "is enforced on all children"; lifetime flags enforced server-side — [Normcore: Ownership and Lifetime Flags](https://docs.normcore.io/room/ownership-and-lifetime-flags)
- **Automatic authority inference from proximity with a visual overlay**: Roblox assigns physics ownership by proximity/hardware and draws ownership outlines in Studio; the trade-off is unverifiable client physics, so gameplay-critical objects stay server-owned — [Roblox: Network Ownership](https://create.roblox.com/docs/physics/network-ownership)
- **Deterministic-by-construction gameplay plus cheap per-tick hashing and recorded replays**: Croquet's "20 lines more than single-player", Quantum's input-only networking, Factorio's heuristic/full CRC and state-diff reports, Quantum's checksum replays and system bisection — [Croquet Multiblaster](https://croquet.github.io/multiblaster-tutorial/); [Quantum intro](https://doc.photonengine.com/quantum/current/quantum-intro); [FFF-55](https://factorio.com/blog/post/fff-55); [Quantum FPS Template: Miscellaneous](https://doc.photonengine.com/quantum/current/fps-template/miscellaneous)
- **Datastore/event model for lobby, inventory, chat and persistence**: Normcore's room datastore and lifetime flags; Colyseus's patched Schema with `.view()` filters; SpacetimeDB's transactional reducers over tables with subscriptions, explicitly not aimed at rollback/physics — [Normcore: Ownership](https://docs.normcore.io/room/ownership-and-lifetime-flags); [Colyseus: Schema](https://docs.colyseus.io/state/schema); [SpacetimeDB docs](https://spacetimedb.com/docs/); [HN thread (mirror)](https://hn.nuxt.dev/item/49378933)
- **Bandwidth controls as declarative field options**: Colyseus `.unreliable()`, `.patchOnly()`, `.fullStateOnly()`, `.quantized()`/`.angle()` — [Colyseus: Schema](https://docs.colyseus.io/state/schema); netfox's diff-state vs full-state intervals with ack-based diffs — [netfox: RollbackSynchronizer](https://foxssake.github.io/netfox/latest/netfox/nodes/rollback-synchronizer/); Fusion `[Capacity]` bounds on collections/strings — [Fusion: Networked Properties](https://doc.photonengine.com/fusion/current/manual/data-transfer/networked-properties)
- **Input-only broadcast to the server by default**: netfox recommends turning input broadcast off because it "lowers bandwidth and reduces the cheating surface" — [netfox: RollbackSynchronizer](https://foxssake.github.io/netfox/latest/netfox/nodes/rollback-synchronizer/)
- **Zero-config transport with NAT fallback and realistic expectations**: Fusion's host mode uses UDP punch-through with relay fallback for "roughly 1 in 10 players"; Normcore uses WebRTC for web reach; Valheim's crossplay relay hop is associated with more lag/timeouts per Iron Gate's docs — [Fusion: Topologies](https://doc.photonengine.com/fusion/current/manual/network-topologies); [Normcore: Common Questions](https://docs.normcore.io/essentials/common-questions); [Edgegap: Valheim](https://edgegap.com/blog/valheim-multiplayer-game-backend-deep-dive)
- **RPC ergonomics the Godot community wants**: return values from `rpc_id()` (#2032, 25 comments), custom structs as RPC parameters (#6216), no requirement to declare RPC methods on both sides (#7065), `rpc_id` running locally without `call_local` (#98588) — [godot-proposals, topic:multiplayer](https://github.com/godotengine/godot-proposals/issues?q=label%3Atopic%3Amultiplayer); [godot #98588](https://github.com/godotengine/godot/issues/98588)
- **Testing built in**: per-instance roles via Godot's run-instances feature tags; Unreal-style latency/loss/jitter/reorder/duplicate presets and "500 ms RTT, 10 % loss" stress guidance; a non-60 Hz refresh test (FishNet #293) — [Godot: debugging tools](https://docs.godotengine.org/en/stable/tutorials/scripting/debug/overview_of_debugging_tools.html); [Unreal: Network Emulation](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-network-emulation-in-unreal-engine); [FishNet issues](https://github.com/FirstGearGames/FishNet/issues)
- **Code-change versioning of sessions**: Croquet starts a new session whenever model code changes (so hot-reload of networked code must either re-sync all peers or be scoped to view code) — [Croquet Multiblaster](https://croquet.github.io/multiblaster-tutorial/)

### Inferences
- A hybrid is well supported by the sources: deterministic rollback for the per-tick gameplay slice (netfox/Quantum/GGRS style, "prediction as a flag"), a server-enforced datastore with ownership and lifetime flags for everything else (Normcore/Colyseus style), and a single authority concept exposed as "owner" with proximity-based auto-assignment and a visual overlay (Roblox style). Each piece has a shipping precedent; the novelty would be in unifying them behind one node annotation model in Godot.
- The highest-leverage ease-of-use features, by frequency of pain in the trackers, are (1) atomic spawn/parent/init ordering with late-join replay, (2) interpolation/prediction that is correct at any refresh rate, (3) host == client semantics, (4) struct/return-value RPCs, (5) clear errors that point at the user's RPC rather than at engine internals.
- Scripting-language friendliness in Godot means `_rollback_tick`-style callbacks and property-path lists (what netfox already does in GDScript) rather than IL weaving (Fusion) or server-side TypeScript schemas (Colyseus); the GDScript side of a Rust GDExtension should expose annotations/exports, not code generation.
- Determinism cannot be assumed for user GDScript or Godot physics, so cheap per-tick hashing with an opt-in "strict determinism" mode (and a sync-test runner that resimulates ticks and compares hashes, à la GGRS/Quantum) is the realistic way to offer rollback without lockstep guarantees.

### Gaps
- No primary source was fetched for: automatic interest management from camera/viewport, Tribes 2-style bandwidth prioritisation, host migration implementations, CRDT-based game state, generated client stubs (SpacetimeDB's bindings were only named, not described), time-travel debuggers, or hot-reload of networked code beyond Croquet's "new session on code change" rule. These remain ideas without evidence in these notes.
- No quantitative comparison of ease of use between models (time-to-first-multiplayer, lines of code) exists in the sources beyond Croquet's own "20 lines" claim.
