# Own the tick, borrow Godot's peers

A new Rust GDExtension for Godot 4 should own a fixed network tick with split *state* and *input* properties, server-authoritative state synchronisation with client prediction and rollback of kinematic gameplay (no determinism required), and an atomic, id-based spawn protocol, while leaving the wire to Godot's existing `MultiplayerPeer`s by wrapping `SceneMultiplayer` through `MultiplayerAPIExtension`. The evidence for that shape converges from three directions. Every library developers migrate toward in 2026 (FishNet, Photon Fusion, Netcode for Entities, netfox) is tick-based with an explicit input struct, while the two without that core (Mirror, Unity NGO) are exactly the ones where prediction is "experimental" and transform sync draws the most complaints ([Edgegap](https://edgegap.com/blog/easiest-unity-netcode-for-game-developers); [Mirror docs](https://mirror-networking.gitbook.io/docs/manual/general/client-side-prediction)). Godot itself ships a pluggable RPC system and polling synchronizers but no tick loop, prediction, interpolation or lag compensation, and its physics can neither be stepped manually nor promise determinism ([netfox caveats](https://foxssake.github.io/netfox/latest/netfox/tutorials/rollback-caveats/); [godot-jolt #794](https://www.github.com/godot-jolt/godot-jolt/discussions/794)). The Rust ecosystem's replication frameworks (lightyear, bevy_replicon, aeronet) have fused with Bevy down to their transport crates, so the usable Rust pieces are transports (renet, quinn, steamworks), GGRS, serialization (postcard) and, above all, *designs* to copy: lightyear's per-component histories and `RollbackPolicy`, naia's diff masks and `TickBuffered` channel, Fiedler's priority accumulator and Tribes' most-recent-state ([lightyear_transport Cargo.toml](https://docs.rs/crate/lightyear_transport/latest/source/Cargo.toml.orig); [naia CONCEPTS](https://raw.githubusercontent.com/naia-lib/naia/main/docs/CONCEPTS.md)). Two constraints shape the architecture more than any feature: gdext's threading is `experimental-threads` with "a high risk of unsoundness", and Godot web export targets `wasm32-unknown-emscripten` while every Rust networking crate's "wasm support" is `wasm32-unknown-unknown` plus wasm-bindgen glue, so the Rust core must be a single-threaded, sans-IO engine that moves bytes through Godot's peers rather than opening sockets itself ([gdext docs](https://docs.rs/godot/latest/godot/); [godot-rust book](https://godot-rust.github.io/book/toolchain/export-web.html)). The research literature adds what libraries drop: frame pacing and defender-side buffering matter more than 128 Hz servers, adaptive and gradual input delay beats fixed delay, and per-tick state hashing is the one tool every determinism postmortem wished it had earlier ([Tokey et al. FDG 2024](https://web.cs.wpi.edu/~claypool/papers/peeker-fdg-24/paper.pdf); [Tokey et al. FDG 2026](https://web.cs.wpi.edu/~claypool/papers/adaptive-fdg-26/paper.pdf); [Factorio FFF-55](https://factorio.com/blog/post/fff-55)).

## Tick-owned prediction, not attribute syntax, is what developers migrate toward

Across Unity, Unreal, Roblox and the smaller engines, the way a developer *marks* replicated state has settled into three dialects, and none of them decides adoption. Attribute-on-member with IL post-processing (Mirror `[SyncVar]`, Fusion `[Networked]`, coherence `[Sync]`) is the tersest but hides codegen and carries hard limits: Mirror allows **64 SyncVars per script** and Fusion warns "DO NOT implement these properties yourself" because the weaver rewrites auto-properties and can lose boolean changes ([Mirror SyncVars](https://mirror-networking.gitbook.io/docs/manual/guides/synchronization/syncvars); [Fusion networked properties](https://doc.photonengine.com/fusion/current/manual/data-transfer/networked-properties)). Generic wrapper fields (NGO `NetworkVariable<T>`, FishNet `SyncVar<T>`, PurrNet) are explicit and carry permissions and send rate on the wrapper, at the cost of `.Value` verbosity and footguns such as NGO's `NetworkList<T>` leaking memory when initialised at declaration ([NGO NetworkVariable](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.4/manual/basics/networkvariable.html); [FishNet SyncVar](https://fish-networking.gitbook.io/docs/manual/guides/synchronizing/syncvar)). Schema or model compilation (Quantum's `.qtn` DSL, Normcore's `[RealtimeModel]` partial classes, coherence's bake step, Colyseus `@type()`) gives the best bandwidth control and the worst iteration loop: coherence's baked scripts break compilation on renames and Colyseus caps a Schema at **63 synchronised properties** ([coherence baking](https://docs.coherence.io/1.3/manual/baking-and-code-generation); [Colyseus Schema](https://docs.colyseus.io/state/schema)). Unreal has kept the same `UPROPERTY(Replicated)` + `DOREPLIFETIME` + `UFUNCTION(Server, Reliable)` shape since UE3 while swapping the engine beneath it: Iris moved to Beta in 5.7, is compiled in by default but still off, and Epic has "no plans to deprecate the legacy replication system or the Replication Graph" ([Epic forums](https://forums.unrealengine.com/t/5-7-iris-strategy/2699685)).

What does separate the libraries is the presence of a fixed-tick input→predict→reconcile loop. FishNet's `[Replicate]`/`[Reconcile]` pair runs on `TimeManager.OnTick`, builds a replicate struct per tick, forwards the owner's inputs through the server so other clients can replay them, and sends redundant replicates against loss ([FishNet prediction](https://fish-networking.gitbook.io/docs/manual/guides/prediction/creating-code/controlling-an-object)). Fusion writes networked state inside `FixedUpdateNetwork()` with `GetInput(out data)`, and its RPCs are "delivered in Forward ticks and are never re-delivered in Resimulation ticks" ([Fusion RPC](https://doc.photonengine.com/fusion/current/manual/rpc)). Netcode for Entities runs `PredictedSimulationSystemGroup` fixed-step on both sides, restarts from "the oldest tick applied to any entity" and warns that a 300 ms connection means "about 22 resimulated ticks in one frame" ([N4E prediction](https://docs.unity3d.com/Packages/com.unity.netcode@1.6/manual/prediction-n4e.html)). Quantum goes furthest: developers "define only the inputs", the deterministic simulation does the rest, and "clients never need to wait for a slower client" because an input-relay server distributes inputs each tick ([Quantum 3 intro](https://doc.photonengine.com/quantum/v3/quantum-intro)). The libraries that lack this loop pay for it in user-visible quality: Mirror's `PredictedRigidbody` is "experimental", does not use `Physics.Simulate()`, and stacked objects "don't yet come to rest properly" ([Mirror prediction](https://mirror-networking.gitbook.io/docs/manual/general/client-side-prediction)); NGO users call `NetworkTransform`/`NetworkAnimator` "terribly inefficient", with the animator unable to handle "100+ networked animated characters" ([Unity Discussions](https://discussions.unity.com/t/fishnet-vs-netcode-for-game-objects/928418)). The migration posts in the same thread give the motives in order: built-in tick prediction (Mirror→FishNet), performance at CCU (NGO→FishNet/Mirror), no CCU pricing or relay lock-in (Photon→FishNet/PurrNet), and PurrNet's praise for spawning with plain `Instantiate()`/`Destroy()` and "async RPCs with return values" ([PurrNet](https://github.com/PurrNet/PurrNet); [Edgegap](https://edgegap.com/blog/easiest-unity-netcode-for-game-developers)). An academic comparison found RTTs of **46–52 ms across Fusion, FishNet, Mirror and NGO** with bandwidth ordered Fusion < FishNet < Mirror < NGO, so latency does not differentiate them either; only bandwidth discipline and the prediction loop do ([ResearchGate](https://www.researchgate.net/publication/382960914_Comparison_of_Open-Source_Networking_Libraries_for_Unity_Engine_in_Higher_Education)).

Authority models are drifting in a direction the design must take a position on. NGO's Distributed Authority, Fusion Shared, coherence, Normcore and Roblox all let the client that spawns an object own it, and every vendor says the same thing about the cost: NGO's DA is "typically not suited to high-performance competitive games", Roblox "cannot verify physics calculations when a client has ownership", and Fusion's host mode admits "a rogue host can cheat" ([NGO DA](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.4/manual/terms-concepts/distributed-authority.html); [Roblox](https://create.roblox.com/docs/physics/network-ownership); [Fusion topologies](https://doc.photonengine.com/fusion/current/manual/network-topologies)). Roblox is nevertheless the clearest existence proof of "easy": the engine replicates the whole data model, assigns physics per part by proximity and hardware with one server override, and exposes exactly `RemoteEvent`, `UnreliableRemoteEvent` and `RemoteFunction`, whose server-side handler always receives the calling `Player` first ([Roblox remotes](https://create.roblox.com/docs/scripting/events/remote)). The smaller engines (Flax, Stride, Defold) copy the NGO/Mirror vocabulary of `NetworkManager`, `StartHost` and replication attributes, which confirms that vocabulary is now what developers expect to find ([Flax networking](https://docs.flaxengine.com/manual/networking/high-level/index.html)).

## Rust's replication layer fused with Bevy, leaving transports, GGRS and designs to borrow

The Rust frameworks that look most relevant on paper are the ones a GDExtension cannot use. lightyear 0.31 (Oct 2026, ~1.2k stars) rebuilt its replication on bevy_replicon in June 2026 and keeps prediction, interpolation, visibility, inputs and bandwidth priority for itself, but even `lightyear_transport` depends on `bevy_app`, `bevy_ecs`, `bevy_reflect` and `bevy_time`, so there is no Bevy-free slice to lift ([lightyear releases](https://github.com/cBournhonesque/lightyear/releases); [lightyear_transport Cargo.toml](https://docs.rs/crate/lightyear_transport/latest/source/Cargo.toml.orig)). bevy_replicon 0.45 (**~79k recent downloads**, the most-used Rust replication crate) and every `bevy_replicon_*` backend, aeronet ("Bevy-native", with replication, rollback and prediction as "explicit non-goals"), bevy_ggrs, bevy_quinnet and Avian physics are in the same position ([bevy_replicon](https://crates.io/crates/bevy_replicon); [aeronet](https://github.com/aecsocket/aeronet)). What these crates leave behind is a set of decisions worth copying wholesale. lightyear merges predicted, confirmed and interpolated into one entity, keeps a `ConfirmedHistory<C>` and `PredictionHistory<C>` per component, exposes `RollbackPolicy { state, input, max_rollback_ticks: 20 }` with `Check`/`Always`/`Disabled` modes, treats entity actions (spawn/despawn/insert/remove) as reliable-ordered and value updates ("90%+" of messages) as sequenced with stale ones dropped, and caps bandwidth with a priority accumulator in which "priority 10 is sent twice as often as 5" ([lightyear prediction](https://raw.githubusercontent.com/cBournhonesque/lightyear/main/book/src/concepts/advanced_replication/prediction.md); [replication logic](https://raw.githubusercontent.com/cBournhonesque/lightyear/main/book/src/concepts/advanced_replication/replication_logic.md); [bandwidth](https://raw.githubusercontent.com/cBournhonesque/lightyear/main/book/src/concepts/advanced_replication/bandwidth_management.md)). bevy_replicon's contrasting rule, "all unacknowledged mutations are sent every tick" and a client applies a mutation only if it is newer than the last applied tick, is a resend-until-acked model rather than delta compression, and its docs state plainly that "clients are eventually consistent, not tick-identical" ([bevy_replicon docs](https://docs.rs/bevy_replicon/latest/bevy_replicon/)).

naia 0.25 (May 2026) is the only maintained Rust framework that is explicitly engine-agnostic and still ships entity replication: `Property<T>` fields mark the entity dirty on write, per-user diff masks send only changed fields to in-scope clients, rooms give coarse scope and `user_scope_mut` fine scope, a `TickBuffered` channel delivers client input at the matching server tick, and `SignedVariableFloat<BITS, FRAC>` quantises on the wire ([naia CONCEPTS](https://raw.githubusercontent.com/naia-lib/naia/main/docs/CONCEPTS.md)). Its recent downloads are only **426–787 per crate** against replicon's tens of thousands, its browser path is wasm-bindgen on `wasm32-unknown-unknown`, and "native iOS and Android are not yet supported", so it is a reference architecture rather than a dependency ([naia README](https://raw.githubusercontent.com/naia-lib/naia/main/README.md); [crates.io](https://crates.io/crates/naia-shared)). GGRS 0.13 (June 2026) is the cleanest Bevy-free building block: a GGPO reimplementation in "no `unsafe` code" that, "instead of registering callback functions, returns a list of requests for the user to fulfill" (`SaveGameState`, `LoadGameState`, `AdvanceFrame`), with a pluggable `NonBlockingSocket`, `SyncTestSession` for determinism checks and `DesyncDetection` comparing checksums between peers ([GGRS](https://github.com/gschup/ggrs); [SessionBuilder](https://docs.rs/ggrs/latest/ggrs/struct.SessionBuilder.html)). backroll, its async sibling, has been dead since November 2022 ([crates.io](https://crates.io/crates/backroll)).

The transport layer is healthier. renet 2.0.1 (Oct 2026, 961 stars) provides `ReliableOrdered`, `ReliableUnordered` and `Unreliable` channels with fragmentation and per-channel memory caps, and renetcode implements the Netcode 1.02 connect-token handshake with ChaCha20-Poly1305 encryption; its fork renet2 adds WebTransport and WebSocket sockets, multi-transport servers (UDP plus WebTransport at once) and a reworked ack protocol ([renet](https://github.com/lucaspoffo/renet); [renetcode](https://docs.rs/renetcode/latest/renetcode/); [renet2](https://raw.githubusercontent.com/UkoeHB/renet2/main/README.md)). quinn 0.11 (405 M downloads) is the QUIC substrate; the one public Godot+Rust multiplayer account found, CaveVox, used a Quinn relay with QUIC datagrams at 60–120 Hz for state and streams for reliable events, bridged through gdext ([quinn](https://crates.io/crates/quinn); [Habr](https://habr.com/ru/post/988636)). The `steamworks` crate 0.13.1 exposes `NetworkingSockets` with P2P listen sockets, lanes with priorities and weights, and hosted dedicated-server tickets, while Valve's GameNetworkingSockets documents AES-GCM-256 per packet, DCCP/QUIC-style ack vectors and relay-only-with-Steam ([steamworks docs](https://docs.rs/steamworks/latest/steamworks/networking_sockets/struct.NetworkingSockets.html); [GNS](https://github.com/ValveSoftware/GameNetworkingSockets)). laminar (last release 2021) and turbulence (2022) are historical designs, not dependencies; rusty_enet's own author calls it "far from ready for serious use" ([laminar](https://crates.io/crates/laminar); [rusty_enet](https://raw.githubusercontent.com/jabuwu/rusty_enet/main/README.md)). iroh 1.4 (13k stars) is the serious hole-punching option, dialling QUIC by public key with self-hostable relay fallback ([iroh](https://raw.githubusercontent.com/n0-computer/iroh/main/README.md)).

Two cross-cutting facts constrain all of this. First, the wasm target: gdext builds for `wasm32-unknown-emscripten` with nightly rustc, `-Zbuild-std`, `-sSIDE_MODULE=2`, `emscripten-wasm-eh=false`, dual threads/nothreads artefacts and panics that abort; every crate above that "supports wasm" (matchbox, naia, renet2, web-transport, GGRS's `wasm-bindgen` feature) does so through wasm-bindgen on `wasm32-unknown-unknown`, and no source documents any of them running inside an Emscripten side module ([godot-rust book](https://godot-rust.github.io/book/toolchain/export-web.html); [matchbox docs](https://docs.rs/matchbox_socket/latest/matchbox_socket/)). Second, serialization: postcard 1.1.3 is the default wire format of both replicon and lightyear; bitcode 0.6.9 produces the smallest and most compressible output (**703,710 B vs postcard's 724,953 B on the log dataset, 227 KB vs 253 KB after zstd**) but its README lists "stable format across major versions" as a non-goal; rkyv's zero-copy advantage matters little for small per-tick packets ([benchmark](https://raw.githubusercontent.com/djkoloski/rust_serialization_benchmark/master/README.md); [bitcode](https://raw.githubusercontent.com/SoftbearStudios/bitcode/main/README.md)). No maintained crate ships Quake-3-style delta-against-acked-baseline; naia's diff masks and lightyear's `Diffable` are the nearest, so the extension will implement that itself over a bit-packer ([lightyear releases](https://github.com/cBournhonesque/lightyear/releases)).

## Godot ships pluggable RPCs and a polling synchronizer, but no tick loop, prediction or determinism

Godot 4's stack (the docs pages fetched identify as 4.7) is a server-authoritative, NodePath-addressed RPC system plus two replication nodes. `@rpc` defaults to `("authority", "call_remote", "reliable", 0)`; every RPC "must be declared on both the client scripts and the server scripts, even unused ones" because signatures are checksummed, arguments are not type-checked, Objects and Callables are not serialised, and the node must sit at the same NodePath on both sides ([High-level multiplayer](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)). `MultiplayerSynchronizer` replicates property paths in `REPLICATION_MODE_ALWAYS` (every frame, unreliable) or `ON_CHANGE` (reliable, detected on process) with a 1350-byte `max_sync_packet_size` and per-peer visibility filters; `MultiplayerSpawner` auto-spawns scenes and both announce themselves to the `MultiplayerAPI` only through `object_configuration_add/remove` ([MultiplayerSynchronizer](https://docs.godotengine.org/en/stable/classes/class_multiplayersynchronizer.html); [MultiplayerSpawner](https://docs.godotengine.org/en/stable/classes/class_multiplayerspawner.html)). The docs are candid about the two authority traps that generate most forum threads: `set_multiplayer_authority` "does not automatically replicate the new authority to other peers" and "the parent's authority does not propagate to newly added children" ([Node](https://docs.godotengine.org/en/stable/classes/class_node.html)). Reported failures through Godot 4.6.2 follow from exactly these: a RigidBody2D "swapping between two values" because client physics "fights with the network state", a spawned node whose authority differs from its spawner's ignoring synchronizer visibility, late joiners whose synchronizers log "Node not found" until a staging scene exists, and the general race in which a server-spawned node's RPC arrives before the spawn has replicated, with "no way to override that behavior" ([forum: RigidBody glitch](https://forum.godotengine.org/t/muliplayer-syncronizer-on-client-glitches-between-two-locations/142803); [forum: visibility vs spawner](https://forum.godotengine.org/t/multiplayersynchonizer-visibility-does-not-affect-spawner/137629); [forum: ENet sync errors](https://forum.godotengine.org/t/enet-synchronization-errors/91231)). The most-commented open multiplayer proposal asks for "property prediction and interpolation" (**27 comments**), the next for returning values from `rpc_id()` (**25**), then manual property syncing, struct RPC parameters, a `MultiplayerEntity` node for identity and authority, and a `@sync` annotation without inspector exposure ([godot-proposals](https://github.com/godotengine/godot-proposals/issues?q=label%3Atopic%3Amultiplayer)).

The engine's two seams are stable and sufficient. `MultiplayerPeerExtension` lets a Rust transport appear as a stock peer (16 required methods, raw-pointer packet functions optional), and `MultiplayerAPIExtension` lets an extension replace or wrap the whole RPC/replication protocol, installed with `SceneTree.set_multiplayer()` or, for native extensions, `MultiplayerAPI.set_default_interface()` during initialisation ([MultiplayerAPIExtension](https://docs.godotengine.org/en/stable/classes/class_multiplayerapiextension.html); [MultiplayerPeerExtension](https://docs.godotengine.org/en/stable/classes/class_multiplayerpeerextension.html)). `SceneMultiplayer.send_bytes(bytes, id, mode, channel)` and the `peer_packet(id, packet)` signal give a raw byte path over any configured peer, so the extension's own protocol can ride ENet, WebRTC, the GodotSteam `SteamMultiplayerPeer` (whose GitHub repo was archived in November 2025 and moved to Codeberg) or Nakama's `NakamaMultiplayerBridge` without binding any of their SDKs ([SceneMultiplayer](https://docs.godotengine.org/en/stable/classes/class_scenemultiplayer.html); [GodotSteam peer](https://github.com/GodotSteam/MultiplayerPeer); [nakama-godot](https://github.com/heroiclabs/nakama-godot)). Property observation is the one thing the engine does not offer: `_set`/`_get` hooks fire only for an object's own script or extension class and "not when setting built-in properties", so the stock synchronizer itself polls each network frame and a Rust extension must poll `Object.get()`/`get_indexed()` too, one Variant conversion per property per tick ([Object](https://docs.godotengine.org/en/stable/classes/class_object.html)). Godot 4.6's unique Node IDs are a candidate identifier more robust than NodePath, though nothing in networking uses them yet ([Godot 4.6](https://godotengine.org/releases/4.6/)).

netfox (GDScript, MIT, ~1.1k stars) is the de-facto answer and the design the extension will be measured against. It runs a `NetworkTime` tick loop independent of render and physics frames (with an option to tick once per physics update), orders a rollback loop `before_loop → on_prepare_tick → on_process_tick → on_record_tick → after_loop`, and gives `RollbackSynchronizer` separate `state_properties` (server-owned, recorded per tick, restored on rollback) and `input_properties` (owned by each player), with `_rollback_tick(delta, tick, is_fresh)` as the user's callback, `is_fresh` guarding one-shot effects, diff states against acknowledged ticks, and `enable_input_broadcast` recommended off because it "lowers bandwidth and reduces the cheating surface" ([NetworkTime](https://foxssake.github.io/netfox/latest/netfox/guides/network-time/); [NetworkRollback](https://foxssake.github.io/netfox/latest/netfox/guides/network-rollback/); [RollbackSynchronizer](https://foxssake.github.io/netfox/latest/netfox/nodes/rollback-synchronizer/)). Its `_rollback_tick` body is ordinary movement code wrapped in `velocity *= NetworkTime.physics_factor` around `move_and_slide()`, and that factor is the leak: Godot "doesn't support manually stepping or updating physics" (PR 76462), `is_on_floor()` is stale during rollback, and "rollback and physics-based games (RigidBodies) don't work at the moment" ([netfox caveats](https://foxssake.github.io/netfox/latest/netfox/tutorials/rollback-caveats/)). The determinism story closes the door on lockstep over engine physics: Godot Jolt "is not able to make such guarantees" and simulations "may even happen to be deterministic, but this should not be relied upon"; Godot's physics interpolation renders "between one and two ticks in the past" and its own docs say networked data "may not align with local ticks, so a custom interpolation approach may fit better" ([godot-jolt #794](https://www.github.com/godot-jolt/godot-jolt/discussions/794); [physics interpolation](https://docs.godotengine.org/en/stable/tutorials/physics/interpolation/physics_interpolation_introduction.html)). The rollback addons that do promise determinism replace physics: SG Physics 2D with fixed point because floating point "implementations vary significantly across even chips by the same manufacturer", and Klotho (C#) with 32.32 fixed point ([SG Physics 2D](https://godotforums.org/d/28338-getting-started-with-sg-physics-2d-and-deterministic-physics-in-godot-good-for-rollback-netcode); [Klotho](https://godotengine.org/asset-library/asset/5234)).

gdext (`godot` 0.5.5, Aug 2026, ~5.4k stars, MPL-2.0 with closed game code allowed) is "in a usable state" with hot reload tested since Godot 4.2, and everything the stack exposes is reachable: `#[rpc]` on Node classes, `rpc_config()`/`rpc_id()` on `Gd<Node>`, `IMultiplayerPeerExtension` and `IMultiplayerApiExtension` with safe signatures, `#[func(virtual)]` so scripts can override extension-defined virtuals (an engine feature since 4.3), and `on_set`/`on_get`/`on_get_property_list` (API 4.3+) for the extension's own classes ([gdext](https://github.com/godot-rust/gdext); [godot_api](https://docs.rs/godot/latest/godot/register/attr.godot_api.html); [INode](https://godot-rust.github.io/docs/gdext/master/godot/classes/trait.INode.html); [Godot 4.3](https://godotengine.org/releases/4.3/)). Three gotchas carry over into design. gdext's `#[rpc]` defaults to `unreliable` where GDScript's `@rpc` defaults to `reliable`, a checksum trap in a mixed codebase ([godot_api](https://docs.rs/godot/latest/godot/register/attr.godot_api.html)). `experimental-threads` "adds Send and Sync implementations for Gd<T>" but "there is a high risk of unsoundness at the moment", cannot be combined with `experimental-godot-api` or `lazy-function-tables`, and the Rust compiler "can't verify what happens to an object through C++ or GDScript" ([gdext docs](https://docs.rs/godot/latest/godot/); [gdext threading docs](https://godot-rust.github.io/docs/gdext/master/src/godot/__docs.rs.html)). And custom `Var`/`Export` conversions run on every engine access, so registered state should prefer `Array`, `Dictionary`, `Gd` and packed arrays, remembering that packed arrays are copy-on-write and GDScript mutations of one are invisible on the Rust side ([properties](https://godot-rust.github.io/book/register/properties.html)). Godot 4.5's GDExtension main-loop callbacks (startup/shutdown/frame) give a process-level hook independent of nodes, useful for a tick driver, at the cost of raising the minimum API level ([Godot 4.5](https://godotengine.org/releases/4.5/)).

## Research since 2018 shifts the lever from server tick rate to frame pacing, shaped delay and desync hashing

The canonical stack has not changed since 2001: Bernier's prediction and lag compensation, Quake 3's delta snapshots against the last acknowledged baseline, Tribes 2's scope-and-priority ghosting, Age of Empires' deterministic lockstep and GGPO's rollback. Riot's VALORANT post is the best public calibration of what budgets buy: a **128 Hz** server and fixed movement step, roughly two frames of server buffering and three of client buffering, a baseline peeker's advantage of **≈141 ms**, of which Riot Direct plus 128-tick removed about 40 ms and 144 FPS rendering a further ~30 ms for a total 49 % reduction, with playtests showing a 10 ms shift swings evenly matched duels from a 90 % holder win rate to a 90 % peeker win rate ([Riot Games](https://www.riotgames.com/en/news/peeking-valorants-netcode)). Fiedler's state-synchronisation demo fixes the bandwidth engineering: 901 cubes in **256 kbit/s** versus 18 Mbit/s for naive snapshot interpolation, position quantised to 4096 values/m, smallest-three quaternions, a 4–5 frame jitter buffer at 60 Hz, a priority accumulator (player cube 1,000,000, interacting 100, at rest 1; sent objects reset to zero) and render-side error offsets decaying by 0.95 per frame for small errors and 0.85 for large, which he notes is cheaper than smoothing the simulation ([gafferongames](https://gafferongames.com/post/state_synchronization/)). Tribes 2 supplied the layering every modern engine rediscovers: four data classes including **Most Recent State** ("volatile data of which only the most recent version is of interest"), a connection layer that notifies the stream managers about dropped packets instead of retransmitting, per-object state masks of "upwards of 20 state flags", and packets filled "first by status change, then by object priority" ([Tribes paper](https://www.gamedevs.org/uploads/tribes-networking-model.pdf)). Unreal Iris's changemask bitfields with priority scheduling are the closest modern engine implementation of that idea ([Iris components](https://dev.epicgames.com/documentation/en-us/unreal-engine/components-of-iris-in-unreal-engine)). Age of Empires' lockstep (commands on turn N execute on N+2, 200 ms turns, 250 ms command latency unnoticed, turn length rising quickly on spikes and decaying slowly, checksummed desync detection) carries the field's best developer lessons: "metering is king", consistent latency beats fast but variable latency, and test on bad links continuously ([Game Developer](https://www.gamedeveloper.com/programming/1500-archers-on-a-28-8-network-programming-in-age-of-empires-and-beyond)).

The measured literature since 2018 corrects an industry reflex. Tokey, Claypool and NVIDIA's 24-user FDG 2024 study found peeker's advantage is driven by the **defender's** latency ("nearly 30 % regardless of the peeker's latency" at 60 ms defender latency) and shrinks with peeker distance, with no significant time-to-damage difference ([Tokey et al. 2024](https://web.cs.wpi.edu/~claypool/papers/peeker-fdg-24/paper.pdf)); Michaelides and Bellalta's 2026 simulation in IEEE Transactions on Games concludes "frame rate is the most influential factor, server tick rate and network delay have minimal impact", with a 120 fps client on a 60 Hz server bringing the advantage under 100 ms ([OpenAlex](https://api.openalex.org/works/doi:10.1109/TG.2026.3656267)). Riot's own breakdown attributes only ~40 of 141 ms to tick rate plus backbone, so the three sources agree that a library should spend its effort on client frame pacing, tick-decoupled interpolation and defender-side buffering before chasing 128 Hz. The FDG 2026 adaptive time-delay study (nearly 100 users across three games) adds the ergonomic twist: adding delay to the low-latency player equalises fairness but hurts experience, adding it only during interactions and **gradually** keeps most of the fairness with better QoE ([Tokey et al. 2026](https://web.cs.wpi.edu/~claypool/papers/adaptive-fdg-26/paper.pdf)). That is Mauve's 2004 local-lag result rediscovered: delaying local execution by roughly the network delay (20–150 ms, with 80–100 ms cited as unnoticeable) removes short-term inconsistency, timewarp repairs the rest, and timewarp's O(n²) cost is fine below ~50 participants ([Mauve et al.](https://publications.cs.hhu.de/library/Mauve2004a.pdf)). Rollback libraries expose only a fixed input-delay count; a continuous, adaptive delay is a cheap novelty no library ships ([GGRS SessionBuilder](https://docs.rs/ggrs/latest/ggrs/struct.SessionBuilder.html)). Learned motion prediction (Ubisoft La Forge and Waterloo, IEEE ToG 2024) cuts dead-reckoning error by up to **45 %** but only at 300–400 ms update intervals, with all methods near-equal at ≤200 ms, so for a 20–60 Hz game it is a bandwidth lever rather than a latency one ([Walker et al.](https://ece.uwaterloo.ca/~sl2smith/papers/2023TOG-Predictive_Dead_Reckoning.pdf)).

Rollback for 3D gameplay without strict determinism is advancing in products, not papers. Snapnet performs "client-side prediction, rollback, and reconciliation automatically" for gameplay and rigid bodies with "strict determinism not required" ([snapnet.dev](https://www.snapnet.dev/)); Easel's 2026 physics engine snapshots and rolls back only bodies that change ("perhaps less than 30 per frame", a claimed 30–50× reduction in snapshot work) ([Easel](https://easel.games/blog/2026-rollback-physics)); Unity N4E resimulates physics inside its predicted group and documents the cost ([N4E physics](https://docs.unity3d.com/Packages/com.unity.netcode@1.6/manual/physics.html)); Unreal's Chaos resimulation still leaves modular vehicles "completely unplayable in multiplayer" across 5.5–5.8 according to a tutorial author ([Epic forums](https://forums.unrealengine.com/t/apply-resimulation-to-chaos-moudular-vehicle/2694754)). Where determinism is wanted, the Rust recipe is now documented: IEEE 754 basic operations are bit-exact across SSE2+, aarch64 and wasm32 while transcendentals come from the platform libm, so Rapier's `enhanced-determinism` requires nalgebra's `ComplexField::sin` instead of `f32::sin` and cannot combine with `simd8`; Avian 0.8 ships the same feature; Jolt verifies `CROSS_PLATFORM_DETERMINISTIC` on Emscripten at ~8 % cost but warns that std trig, `std::sort`, inconsistent FP modes and broad-phase query order all break it ([alice-det-math](https://docs.rs/alice-det-math); [Rapier](https://rapier.rs/docs/user_guides/rust/determinism); [Jolt](https://jrouwe.github.io/JoltPhysics/index.html)). The `fixed` crate 1.31 gives integer-exact arithmetic and deliberately no transcendental functions ([fixed](https://docs.rs/fixed/latest/fixed/)). The tooling that makes determinism survivable is equally well documented: Factorio ran a fast heuristic CRC every tick and a full-state CRC when hunting, diffs server and client states in desync reports, and reproduced a 2024 desync that depended on CPU core count by faking a lower count ([FFF-55](https://factorio.com/blog/post/fff-55); [FFF-415](https://direct.factorio.com/blog/post/fff-415)); Quantum stores checksums in replays and bisects the system list to find the first diverging system ([Quantum FPS template](https://doc.photonengine.com/quantum/current/fps-template/miscellaneous)); GGPO's synctest "runs a 1-frame rollback every frame and raises an error if the re-executed state differs" ([GGPO guide](https://raw.githubusercontent.com/pond3r/ggpo/master/doc/DeveloperGuide.md)).

Three older or underused designs deserve a place because each has a shipped deployment and no library support. Trailing State Synchronization (Cronin et al., NetGames 2002) keeps several simulation copies at staggered delays and rolls the leading copy back to a trailing one on disagreement, evaluated on Quake in a mirrored-server architecture ([Cronin et al.](https://www.eecg.utoronto.ca/~ashvin/courses/ece1746/2003/reading/cronin-netgames02.pdf)). Fiedler's 2018 Oculus networked-physics work gives per-object authority and ownership sequence numbers (ownership outranks authority, host arbitrates, guest authority persists until confirmed) that let cooperative players throw stacks of cubes at each other under 256 kbit/s per player, with a single "perfect prediction" bit covering ~90 % of ballistic updates ([gafferongames VR](https://gafferongames.com/post/networked_physics_in_virtual_reality/)). Croquet, Quantum and Factorio demonstrate that a logic-less relay plus deterministic replicated simulation is production-proven for 2–16 players: the reflector "handles event ordering, synchronized time ticks, and no application logic", the networked Multiblaster "has only 20 lines more than the non-Croquet one", and the cost is that "whenever we change the model code, a new session is created" ([Multisynq](https://docs.multisynq.io/api-reference); [Croquet tutorial](https://croquet.github.io/multiblaster-tutorial/)). Factorio's latency hiding, a separate "latency state" re-derived from the real state every tick for the player's own actions, shows how to put responsiveness back into lockstep without rollback ([FFF-83](https://factorio.com/blog/post/fff-83)). Obstacle-aware interest management cut update messages by up to 6× on a real MMOG, and EVE's time dilation bounded server load at the cost of 12.87 hours of simulated time in twelve days; both are MMO-scale levers a small library can skip ([Boulanger 2006](https://www.sable.mcgill.ca/~clump/papers/boulanger-06-comparing.pdf); [EVE](https://www.eveonline.com/news/view/introducing-time-dilation-tidi)).

## Issue trackers name the real pain: lifecycle ordering, transform quality, host asymmetry, RPC typing

Counting the most-commented issues across five trackers on 2026-11-08 gives a sharper picture of "ease of use" than any survey. In Unity NGO (1,298 issues) the top items are "Multiple re-parents and Teleport() calls on NetworkTransform corrupts In Local Space position" (**101 comments**), "Problem with Spawning at runtime and with NetworkedTransform" (87), two more NetworkTransform teleport and local-space issues, and "Spawning A Player and a Non-Player Object" (59) ([NGO issues](https://github.com/Unity-Technologies/com.unity.netcode.gameobjects/issues)). Mirror's are "No writer found" serialization errors, `NetworkServer.Spawn()` losing the parent on clients, and "Host SyncVar not set on server before client hook is called" ([Mirror issues](https://github.com/MirrorNetworking/Mirror/issues)). FishNet's are spawning with a parent (30), tick-smoother issues (30), "Predicted network transforms jitter when refresh rate isn't 60 Hz" (23), pooled objects missing `OnStartClient`, SyncVar hooks not firing for the host, and "Forces are applied twice or more on CSP objects" (20) ([FishNet issues](https://github.com/FirstGearGames/FishNet/issues)). Godot's `topic:multiplayer` issues lead with MultiplayerSpawner misbehaving after a scene change via RPC (22), the synchronizer unable to sync `velocity` from a `CharacterBody2D` (16), authority unsettable in `_enter_tree` (14), and `rpc_id()` requiring `call_local` to run locally ([Godot issues](https://github.com/godotengine/godot/issues?q=is%3Aissue+is%3Aopen+label%3Atopic%3Amultiplayer)). netfox's own tracker asks about properties outside the root node, RigidBody sync, server-authoritative mode without network-wide rollback and batching RPCs ([netfox issues](https://github.com/foxssake/netfox/issues)). The same five themes appear everywhere: object lifecycle ordering (spawn, parent, re-parent, teleport, pool, scene change, late join), transform and physics quality at non-60 Hz, host-versus-client asymmetry, RPC typing and routing, and errors that point at engine internals rather than the user's code. A library whose spawn message creates, parents and initialises before any message can target the object, whose host is literally a client of itself, and whose interpolation is tick-decoupled would remove the largest classes of reported pain.

The systems that get closest to "write single-player code" do it by owning the game loop, never by intercepting arbitrary writes. Croquet's `future(50).mainLoop()` and netfox's `_rollback_tick` are the two existence proofs; Fusion gets the same effect by requiring writes inside `FixedUpdateNetwork()`; Quantum by making the simulation a separate pure-C# program ([Croquet tutorial](https://croquet.github.io/multiblaster-tutorial/); [Fusion networked properties](https://doc.photonengine.com/fusion/current/manual/data-transfer/networked-properties)). Every transparent system still asks the developer to learn one concept pair (model/view, simulation/view, state/input, state authority/input authority, authority/any_peer), so a new library should pick one pair and name it consistently. Normcore shows the authority bookkeeping that can be hidden: a model's writes are accepted only from its owner, ownership "of a parent are enforced on all children", a rejected ownership request rolls back "all changes that required ownership", and lifetime flags are enforced by the server even on improper disconnects ([Normcore](https://docs.normcore.io/room/ownership-and-lifetime-flags)). Roblox shows the visualisation: Studio outlines parts green (yours), red (buffer zone that may be rejected), white/grey (server or another client) and black (no owner) ([Roblox](https://create.roblox.com/docs/physics/network-ownership)). The "server is a database" branch (SpacetimeDB reducers over tables with subscriptions, Colyseus patched schemas with `@view()` filters) is excellent for lobby, inventory and persistence and, by its own critics' account, "doesn't really help with" rollback, physics or collisions, with reliability explicitly prioritised over performance ([SpacetimeDB](https://raw.githubusercontent.com/clockworklabs/SpacetimeDB/master/README.md); [HN thread](https://hn.nuxt.dev/item/49378933)). Ambient, the Rust runtime that bundled automatic networking with its own engine, is "paused indefinitely", a caution against building an engine rather than attaching to one ([Ambient](https://github.com/AmbientRun/Ambient)).

Testing ergonomics have a clear 2026 baseline. Godot's "Customize Run Instances" launches several copies with per-instance arguments and feature tags ([Godot debugging tools](https://docs.godotengine.org/en/stable/tutorials/scripting/debug/overview_of_debugging_tools.html)); Unity's Multiplayer Play Mode simulates up to four players in the editor ([MPPM](https://docs.unity3d.com/Packages/com.unity.multiplayer.playmode@1.4/manual/index.html)); Unreal's Network Emulation offers per-direction lag, variance, jitter, loss, reorder and duplication with Custom/Average/Bad presets and recommends testing at "500 round trip ping" and "10% packet loss or higher" ([Unreal emulation](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-network-emulation-in-unreal-engine)). Godot has the first and lacks the second, so the extension should supply emulation itself. The determinism postmortems agree on the rest: the Tentacle Tango team found that auditing every system for determinism "took longer than we thought", Dino Party's move from local to online "meant rewriting large parts of the game", and Factorio's threading-determinism bug hid for seven years ([coherence blog](https://coherence.io/blog/tradecraft/tentacle-tango); [FFF-415](https://direct.factorio.com/blog/post/fff-415)). The recurring failure is choosing the model late: rollback demands determinism that cannot be retrofitted, state sync demands quantisation, priority and smoothing plumbing that is tedious but incremental. A library that makes the model choice explicit at project start and ships hash checkpoints, recorded inputs and a sync-test mode addresses the most-cited pain directly.

## Conclusion

The surprising result of the survey is how little of the problem is about wire format or API syntax and how much is about who owns time. Every framework that feels close to single-player, from Croquet's twenty extra lines to netfox's `_rollback_tick`, achieves it by owning the tick and the order of operations around it, and every framework that leaves the tick to the engine (Mirror, NGO, Godot's stock synchronizer) accumulates the same tracker of spawn races, jitter and double-applied forces. For Godot specifically this means the extension's first job is a tick loop that physics already dictates (60 Hz, inside `_physics_process`, since physics cannot be stepped manually), its second is an id-based lifecycle protocol that replaces NodePath addressing, and only its third is replication and prediction. The measured literature strengthens rather than complicates this: with peeker's advantage dominated by frame rate and defender latency, a library that pairs 60 Hz simulation with tick-decoupled interpolation, decaying correction offsets and an adaptive local-lag knob will serve a Godot indie game better than one chasing Riot's 128 Hz.

The ecosystem analysis also changes what "build on Rust crates" means. The crates worth depending on are small and boring (postcard, a bit-packer, GGRS for an opt-in deterministic mode, renet or quinn behind a native-only peer), while the valuable parts of lightyear, naia, Iris and Tribes are designs that cost nothing to adopt. Because gdext cannot safely share `Gd<T>` across threads and Godot's web export sits on Emscripten where no Rust transport has been shown to run, the core must be a sans-IO state machine fed bytes by Godot's own peers; that constraint, far from being a limitation, is what lets the extension compose with ENet, WebRTC, Steam and Nakama on day one and reach the browser without a single wasm-bindgen dependency.

## Design-relevant conclusions for the extension

This final section is the input to the design plan. It states the recommended programming model, the dependency decisions, the default and excluded techniques, and the open decisions with a recommendation each.

### Recommended programming model

The extension should present one concept pair, **owner-authored input** and **server-owned state**, exposed through a Godot node and a Rust derive rather than through annotations or codegen. In GDScript, a `NetSync`-style child node (the netfox `RollbackSynchronizer` and stock `MultiplayerSynchronizer` shape, which Godot users already know) lists `state_properties` and `input_properties` as property paths with per-property options (quantisation, interpolate/snap, send mode, visibility tag); in Rust, a `#[derive]` on a `GodotClass` marks fields the same way. Both feed one Rust core that polls the values once per network tick, because the engine offers no hook on arbitrary property writes and the stock synchronizer polls too ([Object](https://docs.godotengine.org/en/stable/classes/class_object.html)). Gameplay code lives in a single virtual callback, `_net_tick(delta, tick, is_fresh)`, registered by the extension with `#[func(virtual)]` so GDScript overrides it like `_physics_process`; the body is ordinary movement code, as netfox demonstrates, and `is_fresh` guards one-shot effects during resimulation ([godot_api](https://docs.rs/godot/latest/godot/register/attr.godot_api.html); [RollbackSynchronizer](https://foxssake.github.io/netfox/latest/netfox/nodes/rollback-synchronizer/)). The default mode is server-authoritative state synchronisation with client-side prediction and rollback of the owner's kinematic bodies, no determinism required (the Snapnet/netfox/lightyear `Check` model), with remote entities interpolated on a tick-decoupled render timeline and corrections blended through decaying error offsets. The host is a client of itself (one loopback peer, no `is_server()` branches in user code, modelled on Fusion `GameMode.Single` and Godot's `OfflineMultiplayerPeer`), so single-player and the listen-server host run the same code path ([Fusion topologies](https://doc.photonengine.com/fusion/current/manual/network-topologies); [High-level multiplayer](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)). Spawning uses the engine's own `instantiate()`/`add_child()`/`queue_free()` on the owner; the extension assigns a stable net id, and one reliable, ordered *entity action* message creates, parents and initialises the replica before any update or RPC can target it (the lightyear actions-versus-updates split), eliminating the "Node not found" race class ([replication logic](https://raw.githubusercontent.com/cBournhonesque/lightyear/main/book/src/concepts/advanced_replication/replication_logic.md)). RPCs are typed, route in the attribute (`SendTo`-style targets: server, owner, everyone, all-but-me, specified), carry a trailing sender/tick info parameter, accept struct arguments, may return a value awaitably, default to reliable like GDScript's `@rpc`, and are addressed by net id plus method name hash so they need not be declared identically on both sides ([NGO RPC](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.4/manual/advanced-topics/message-system/rpc.html); [PurrNet](https://github.com/PurrNet/PurrNet); [godot-proposals](https://github.com/godotengine/godot-proposals/issues?q=label%3Atopic%3Amultiplayer)). Authority is one `owner` per entity, server by default, replicated when it changes, inherited by children unless overridden, with per-entity transfer rules (not transferable / request / take) and server-enforced writes that roll back rejected changes, after Normcore and NGO's DA flags ([Normcore](https://docs.normcore.io/room/ownership-and-lifetime-flags); [NGO ownership](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.4/manual/basics/ownership.html)). A separate, non-tick *reliable keyed state* (Colyseus-style declared fields sent on change, with per-client `view` tags) covers lobby, score, inventory and chat without touching the tick loop ([Colyseus Schema](https://docs.colyseus.io/state/schema)).

### Crates to build on versus avoid

The core crate must compile on `wasm32-unknown-emscripten` with `experimental-wasm-nothreads`, which rules out `std::thread`, wasm-bindgen and any crate that opens sockets; the core is a sans-IO state machine that takes packets in `poll()` and returns packets to send, so it runs identically on native and web ([godot-rust book](https://godot-rust.github.io/book/toolchain/export-web.html)). Native-only transport crates live behind a Cargo feature in a separate `MultiplayerPeerExtension` crate and are never part of the web build.

| Crate | Verdict | Reason |
|---|---|---|
| `godot` (gdext 0.5.x) | build on | the only Rust binding; `IMultiplayerApiExtension`, `IMultiplayerPeerExtension`, `#[func(virtual)]`, `#[rpc]` all present ([gdext](https://github.com/godot-rust/gdext)) |
| `postcard` | build on (wire format of control/entity-action messages) | stable, `no_std`, serde, the ecosystem default in replicon and lightyear ([postcard](https://crates.io/crates/postcard)) |

| `bitcode` | avoid as wire format (optional internal snapshot encoding only) | smallest output but "stable format across major versions" is a non-goal ([bitcode](https://raw.githubusercontent.com/SoftbearStudios/bitcode/main/README.md)) |

Threading rule: the core never uses `experimental-threads`; all `Gd<T>` access happens on the main thread inside `_physics_process`/`poll()`; a native transport may run a Rust thread that exchanges plain bytes with the main thread through channels and never touches Godot objects, as gdext's own docs recommend ([gdext threading docs](https://godot-rust.github.io/docs/gdext/master/src/godot/__docs.rs.html)).

### Techniques to make default

Default on: a fixed network tick driven from `_physics_process` at `physics_ticks_per_second` (60), because netfox's `physics_factor` workaround and the unmerged manual-stepping PR show any other cadence fights `move_and_slide()` ([netfox caveats](https://foxssake.github.io/netfox/latest/netfox/tutorials/rollback-caveats/)); tick-buffered inputs sent to the server with redundancy of the last few inputs per packet and server-side repeat-last-input on loss (FishNet, lightyear, Riot) ([Riot Games](https://www.riotgames.com/en/news/peeking-valorants-netcode)); input broadcast off (netfox's bandwidth and anti-cheat reasoning); client prediction with rollback-and-replay of the owner's kinematic entities, max rollback window ~20 ticks, rollback on mismatch (`Check`) rather than every tick; most-recent-state replication for `state_properties` with per-field dirty masks, delta against the last acknowledged baseline and no retransmission (Tribes/Quake 3/Fiedler), with entity actions and events on a reliable ordered channel ([Tribes paper](https://www.gamedevs.org/uploads/tribes-networking-model.pdf); [gafferongames](https://gafferongames.com/post/state_synchronization/)); a per-client byte budget with a priority accumulator (owner's entity highest, interacting entities next, at-rest lowest); quantisation defaults per type (positions to millimetres, smallest-three quaternions) overridable per property; snapshot interpolation of remote entities on a render timeline one jitter-buffer behind, with decaying error offsets for corrections and a teleport threshold ([N4E GhostField](https://docs.unity3d.com/Packages/com.unity.netcode@1.6/manual/ghostfield-synchronize.html)); bounded server-side rewind for hit tests when a `lag_compensated` flag is set on a query, capped near 250 ms; atomic entity actions with late-join replay; host-as-client; a cheap per-tick state hash exchanged between peers as telemetry (not as a halt), with a sync-test mode that resimulates each tick and diffs hashes; a bandwidth and latency meter panel in-game from day one ("metering is king"); a network-emulation layer with Unreal's knobs and presets inside the extension since Godot has none; and documentation that the test matrix includes non-60 Hz refresh rates and the host role ([FishNet issues](https://github.com/FirstGearGames/FishNet/issues)).

### Techniques to leave out, and why

Leave out: deterministic lockstep or GGRS rollback over Godot's physics or arbitrary GDScript, because neither Godot Physics nor Jolt-in-Godot promises determinism and physics cannot be stepped manually ([godot-jolt #794](https://www.github.com/godot-jolt/godot-jolt/discussions/794)); rollback of RigidBodies (server-owned, interpolated, frozen on non-owners as the forum workaround does, like N4E making interpolated ghosts kinematic) ([forum: RigidBody glitch](https://forum.godotengine.org/t/muliplayer-syncronizer-on-client-glitches-between-two-locations/142803)); IL-weaving or codegen-style property interception, which the engine cannot support and which breaks on renames elsewhere; CRDT or local-first state for gameplay (prototypes only, "rare" in practice); learned motion prediction (pays only at ≥300 ms intervals); EVE-style time dilation, Replication-Graph-scale spatial graphs and obstacle-aware interest management (MMO-scale problems; a radius/room scope suffices); Trailing State Synchronization (mirrored-server architecture, no library precedent); any bundled hosting, matchmaking or relay service (Hathora shut down May 2026, PlayFab cut its free tier, Multiplay ended direct operation; target Agones-compatible dedicated servers and existing Steam/EOS relays through peers instead) ([Crux](https://crux.supercraft.host/blog/hathora-shut-down-where-to-go-after-may-2026/)); a persistence database à la SpacetimeDB (out of scope by its own critics' assessment); host migration in v1 (Destiny-class complexity, no Godot precedent); and a Rust-side Steam binding when GodotSteam's peer already exists.

### Open design decisions, each with a recommendation

1. **Transport ownership.** Wrap `SceneMultiplayer` in a Rust `MultiplayerAPIExtension`, carry the extension's protocol over `send_bytes`/`peer_packet`, and compose with every existing peer (ENet, WebRTC, Steam, Nakama) versus shipping an own `MultiplayerPeerExtension` over renet/quinn. *Recommendation:* wrap first; this is the only path that reaches web exports and Steam on day one, and the `MultiplayerPeerExtension` over renet becomes a native-only phase-2 crate (it would be the first publicly documented one) ([MultiplayerAPIExtension](https://docs.godotengine.org/en/stable/classes/class_multiplayerapiextension.html); [SceneMultiplayer](https://docs.godotengine.org/en/stable/classes/class_scenemultiplayer.html)).
2. **Coexistence with stock `@rpc`, `MultiplayerSpawner` and `MultiplayerSynchronizer`.** Forward their `_rpc` and `object_configuration_add` calls to the wrapped `SceneMultiplayer` untouched (the docs' `LogMultiplayer` pattern) so existing scenes keep working, versus replacing them. *Recommendation:* forward; the extension's nodes are additive and a project can migrate one scene at a time.
3. **Entity identity.** Own stable net ids versus NodePath versus Godot 4.6 unique Node IDs. *Recommendation:* own ids (u32, owner-allocated ranges), with the spawn action carrying scene path, parent id and initial state; NodePath is the root cause of the "Node not found" class; 4.6 node ids are promising but undocumented for networking and would raise the minimum API.
4. **Declaring replicated properties.** Child node with property-path lists (GDScript parity) plus a Rust derive, versus a convention or a future engine `@sync` annotation. *Recommendation:* both node and derive now, since an extension cannot add GDScript annotations; keep the property list editable in the inspector and also settable in code (`add_state("velocity")`), answering proposals #9406 and #8662 in spirit ([godot-proposals](https://github.com/godotengine/godot-proposals/issues?q=label%3Atopic%3Amultiplayer)).
5. **Dirty tracking.** Poll every tick versus require writes through an extension accessor. *Recommendation:* poll (the only option for arbitrary GDScript nodes), compare against the last sent value per field to build dirty masks, and offer an optional `mark_dirty()` fast path for Rust classes; measure the Variant-conversion cost early since no primary number exists.
6. **Default replication mode.** State sync with prediction and rollback-on-mismatch versus GGRS-style rollback-everything versus plain interpolation. *Recommendation:* state sync + prediction for the owner's kinematic entities, interpolation for the rest; deterministic rollback is an opt-in mode for library-owned simulations (Rust-side game logic using `fixed`/`libm` math, optionally Rapier `enhanced-determinism`), enabled explicitly at project start because it cannot be retrofitted ([coherence blog](https://coherence.io/blog/tradecraft/tentacle-tango)).
7. **Tick placement and rate.** Inside `_physics_process` at the physics tick versus an independent loop with `max_ticks_per_frame` (netfox default). *Recommendation:* physics-synced simulation at 60 Hz with a separately configurable send rate (default equal to the tick, budget-limited by the priority accumulator), and interpolation on `_process` with `Engine.get_physics_interpolation_fraction`-style blending done by the extension, not by Godot's physics interpolation ([physics interpolation](https://docs.godotengine.org/en/stable/tutorials/physics/interpolation/physics_interpolation_introduction.html)).
8. **Reliability for state.** Tribes-style notification-based most-recent-state versus replicon-style resend-until-acked versus a reliable channel. *Recommendation:* most-recent-state with per-field masks and acked-baseline deltas for `state_properties`; resend-until-acked for the reliable keyed state; a reliable ordered channel for entity actions and events.
9. **Wire format.** postcard versus bitcode versus rkyv for messages; hand-rolled bit-packing for snapshots. *Recommendation:* postcard for control and action messages, hand-rolled bit-packing with quantisation for state snapshots, LZ4 optional; version the protocol with a hash exchanged at handshake (replicon's `ProtocolHash`, naia's protocol hash) ([bevy_replicon docs](https://docs.rs/bevy_replicon/latest/bevy_replicon/)).
10. **Default authority and the shared-authority mode.** Server-authoritative with input-to-server versus Fusion-Shared/Roblox-style client ownership by default. *Recommendation:* server-authoritative by default; a per-entity `client_owned` rule for co-op and prototyping, labelled as trusting clients, with a Roblox-style ownership overlay in the editor debugger so the trade-off is visible ([Roblox](https://create.roblox.com/docs/physics/network-ownership)).
11. **Physics.** Predict kinematic bodies only; RigidBodies server-owned, frozen and interpolated on non-owners; optional Fiedler-style per-object authority with ownership sequence numbers for cooperative physics in a later package. *Recommendation:* as stated; never promise rollback of engine physics ([gafferongames VR](https://gafferongames.com/post/networked_physics_in_virtual_reality/)).
12. **Local lag / adaptive delay.** Fixed input-delay ticks only (every rollback library) versus a continuous, optionally adaptive and gradual delay. *Recommendation:* ship `input_delay_ticks` (default 0) in v1 and an experimental `adaptive_delay` that ramps gradually during interactions, the one evidence-backed novelty no library offers ([Tokey et al. 2026](https://web.cs.wpi.edu/~claypool/papers/adaptive-fdg-26/paper.pdf)).
13. **Minimum Godot API level.** `api-4-3` (script-overridable extension virtuals, `on_get_property_list`, 2D physics interpolation) versus `api-4-5` (main-loop callbacks) versus `api-4-6` (unique node ids). *Recommendation:* 4.3 as `compatibility_minimum`, driving the tick from a node rather than main-loop callbacks; revisit when 4.6 adoption makes unique node ids and the JSON-defined interface the norm ([godot-rust version policy](https://godot-rust.github.io/book/toolchain/godot-version.html)).
14. **Mixed-language RPC defaults.** Follow gdext's `#[rpc]` default (`unreliable`) or GDScript's (`reliable`). *Recommendation:* the extension's own RPC layer defaults to reliable like GDScript, and the docs call out the gdext mismatch for anyone still using stock `#[rpc]` ([godot_api](https://docs.rs/godot/latest/godot/register/attr.godot_api.html)).
15. **Interest management.** Rooms plus a per-entity radius and a `visibility_filter` callable (the stock synchronizer's shape) versus a spatial grid. *Recommendation:* rooms + radius + callable in v1; a grid only if a project needs hundreds of entities per client, since the budgeted priority accumulator already degrades gracefully.
16. **Debug tooling scope.** Which of hash telemetry, sync-test, input recording and replay, ownership overlay, meter panel and network emulation ship in v1. *Recommendation:* meter panel, emulation, hash telemetry and the ownership overlay in v1 (each is small and addresses a cited pain); recorded-input replay and sync-test with the deterministic mode.
17. **Web export verification.** Whether to attempt any Rust transport under Emscripten. *Recommendation:* do not; make the web build pass with the core alone over Godot's `WebRTCMultiplayerPeer` and `WebSocketPeer`, and treat a build experiment with renet2's WebTransport client under Emscripten as research, not a plan dependency ([godot-rust book](https://godot-rust.github.io/book/toolchain/export-web.html)).
